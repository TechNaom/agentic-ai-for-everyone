Every chapter from 1 through 11 handed you a problem that already told you which mechanism to build: Chapter 1's problem needed a loop, Chapter 6's problem needed a guardrail, Chapter 9's problem needed a supervisor. Real problems don't arrive pre-labeled. A VP hands you a paragraph describing a business process and asks, "what should we build, and why not something simpler?" This chapter is about answering that question in writing, defensibly, using nothing but the eleven chapters of mechanisms you already have.

1. Hand-off from Chapters 1-11: from building mechanisms to choosing among them

Chapters 1-11 each answered "how do I build X." This chapter answers "given a problem, should I build X at all, and if so, how much of it." Nothing from any prior chapter is redefined below -- every mechanism is referenced by name, by the function or concept that already exists for it.

What is... an architecture DECISION, as distinct from a mechanism? A mechanism (memory, a guardrail, a retry policy) is a tool in a toolbox. An architecture decision is the claim "for THIS problem, tool X is load-bearing and tool Y is not, and here is why" -- made explicit, in writing, before any code exists. Chapters 1-11 taught you to build every tool. This chapter teaches you to choose, defensibly, which ones a given problem actually needs.

2. Why this chapter runs no live model call, and says so

Per this course's own reliability policy, a live call is run when a chapter's content genuinely needs one. Chapters 1-11 needed live calls because they taught a model's own behavior (tool selection, argument drift, reflection quality, prompt-injection response). This chapter teaches a DECISION PROCESS applied to written problem descriptions -- the thing being exercised is the reader's judgment, not a model's behavior. Forcing in a live call here would not serve the chapter's own point, so this session made none, honestly, rather than padding in a call for its own sake.

Go deeper This mirrors a real architecture practice: a design review happens BEFORE a model is ever called, against a written problem statement and a written proposal. The live-model skills from Chapters 1-11 are exactly what you'd reach for once a chosen architecture starts getting built -- this chapter sits one layer above that, at the point where the decision is still only on paper.

3. The decision framework: four questions, in order

Every architecture decision in this chapter answers four questions, always in this order, because each later question depends on the answer to the one before it:

Sections 4-9 below walk all four questions against one real worked problem. Section 10 adds a fifth, cross-cutting check -- a "smell test" -- that catches the two most common mistakes: choosing MORE architecture than a problem needs, and choosing LESS than it needs.

4. Question 1 -- problem characterization: is this a single- or multi-agent problem?

Chapter 9 taught you how to BUILD supervisor/worker dispatch once you already know you need it. This chapter teaches the test for whether you need it at all.

characterize_problem.py
def characterize_problem(problem):
    """problem is a dict of yes/no problem FACTS (not a vibe). Returns a
    verdict and the single strongest reason, so the decision is always
    traceable to one concrete fact, not a blended impression."""
    if problem.get("distinct_specialized_subtasks") and problem.get("subtasks_can_run_independently"):
        return {"multi_agent_justified": True,
                "reason": "distinct, specialized subtasks that can proceed "
                           "independently -- a single agent would need to "
                           "context-switch between unrelated skill sets"}
    if problem.get("requires_concurrent_independent_actors"):
        return {"multi_agent_justified": True,
                "reason": "multiple independent actors must act at the same "
                           "time on a shared resource (Ch10's coordination "
                           "problem, not Ch9's dispatch problem)"}
    return {"multi_agent_justified": False,
            "reason": "one agent, multiple tools, is sufficient -- the "
                       "subtasks share state and don't need independent "
                       "concurrent actors"}

print(characterize_problem({"distinct_specialized_subtasks": False,
                             "subtasks_can_run_independently": False,
                             "requires_concurrent_independent_actors": False}))
Output (real, executed) 
{'multi_agent_justified': False, 'reason': "one agent, multiple tools, is sufficient -- the subtasks share state and don't need independent concurrent actors"}

This function doesn't decide from a topic ("this sounds complicated, so multi-agent"). It decides from two concrete facts: do the subtasks need genuinely different skills that can proceed independently (Chapter 9's case), or does the problem need multiple actors acting concurrently on shared state (Chapter 10's case)? If neither fact is true, the default is single-agent -- the architecture decision equivalent of Chapter 3's "cheapest, most decisive signal first" tool-selection ordering.

5. Worked example: Copperfield Municipal Utilities' outage-response problem

Copperfield Municipal Utilities, a fictional regional electric utility, wants an agent to handle two request types from its customer portal: (1) "my power is out" outage reports, which need a grid-status lookup and, if confirmed, an automatic restoration-ticket creation; and (2) "my bill looks wrong" billing disputes, which need an account lookup, a usage-history comparison, and -- only above a $75 disputed amount -- a human-approved credit.

copperfield_characterization.py
copperfield_problem = {
    "distinct_specialized_subtasks": False,   # both request types read/write
                                               # the same customer+grid state
    "subtasks_can_run_independently": False,
    "requires_concurrent_independent_actors": False,  # one customer, one
                                                        # conversation at a time
}
verdict = characterize_problem(copperfield_problem)
print(f"multi_agent_justified: {verdict['multi_agent_justified']}")
print(f"reason: {verdict['reason']}")
Output (real, executed) 
multi_agent_justified: False
reason: one agent, multiple tools, is sufficient -- the subtasks share state and don't need independent concurrent actors

This matches Chapters 1-8's own CareBot and LedgerBot (single agent, multiple tools) rather than Chapter 9's CityScout or Chapter 10/11's peer-agent pairs. The two request types don't need independent actors -- they need one agent that correctly selects among four tools (Chapter 3's own skill) and applies the right guardrail before the one genuinely risky action (the credit).

6. Question 2 -- mechanism selection: the Chapter 1-11 inventory, as a lookup

Once a problem is characterized, the second question is which of the remaining ten mechanisms (the loop itself and planning are assumed for ANY agent) are load-bearing. This is answered per-mechanism, against stated problem facts, not by habit or by copying the last design.

mechanism_tests.py
MECHANISM_TESTS = {
    "memory (Ch4)": lambda p: p.get("facts_must_persist_across_separate_sessions", False),
    "reflection (Ch5)": lambda p: p.get("has_a_hard_to_verify_free_text_output", False),
    "guardrails (Ch6)": lambda p: p.get("has_an_irreversible_or_costly_action", False),
    "reliability measurement (Ch7)": lambda p: p.get("failures_are_costly_enough_to_measure", False),
    "cost control (Ch8)": lambda p: p.get("runs_at_volume_or_has_a_cost_ceiling", False),
    "multi-agent dispatch (Ch9)": lambda p: p.get("multi_agent_justified", False),
    "peer communication (Ch10)": lambda p: p.get("multi_agent_justified", False) and p.get("requires_concurrent_independent_actors", False),
    "operating layer (Ch11)": lambda p: p.get("runs_unattended", False),
}

def select_mechanisms(problem):
    return {name: test(problem) for name, test in MECHANISM_TESTS.items()}

print(select_mechanisms({"facts_must_persist_across_separate_sessions": False}))
Output (real, executed) 
{'memory (Ch4)': False, 'reflection (Ch5)': False, 'guardrails (Ch6)': False, 'reliability measurement (Ch7)': False, 'cost control (Ch8)': False, 'multi-agent dispatch (Ch9)': False, 'peer communication (Ch10)': False, 'operating layer (Ch11)': False}

Each test is a one-line, named, checkable claim -- the same discipline Chapter 1's tool schemas and Chapter 6's guardrail allowlist used. An architect who can't state WHICH fact makes a mechanism load-bearing hasn't finished the decision yet.

8. Question 3 -- a reliability/cost budget, reusing Chapter 7 and 8's own vocabulary

Once guardrails, reliability measurement, and cost control are confirmed load-bearing, the architect states NUMBERS, not just "we'll measure it" -- reusing Chapter 7's `pass_at_k`/`run_harness` and Chapter 8's `is_within_budget`/`cost_per_success` unchanged.

reliability_cost_budget.py
import importlib.util, os

def _load(name, rel_path, repo_root):
    spec = importlib.util.spec_from_file_location(name, os.path.join(repo_root, rel_path))
    mod = importlib.util.module_from_spec(spec); spec.loader.exec_module(mod)
    return mod

REPO_ROOT = os.path.abspath(os.path.join(os.getcwd()))
ch7 = _load("ch7", "chapters/chapter-07-evaluating-agent-reliability/project/solution.py", REPO_ROOT)
ch8 = _load("ch8", "chapters/chapter-08-cost-and-latency-control-of-agent-loops/project/solution.py", REPO_ROOT)

def reliability_cost_budget(problem):
    """Stakes-driven, not arbitrary: a costlier failure mode gets a
    HIGHER required success rate and a LOWER per-run cost ceiling."""
    if problem.get("has_an_irreversible_or_costly_action"):
        return {"min_task_success_rate": 0.95, "max_cost_per_run": 0.08,
                "reused_from": "Ch7 pass_at_k threshold; Ch8 is_within_budget max_cost"}
    return {"min_task_success_rate": 0.85, "max_cost_per_run": 0.15,
            "reused_from": "Ch7 pass_at_k threshold; Ch8 is_within_budget max_cost"}

print(reliability_cost_budget(copperfield_problem))
print("is_within_budget(3, 0.05, max_steps=6, max_cost=0.08) ->",
      ch8.is_within_budget(3, 0.05, 6, 0.08))
Output (real, executed) 
{'min_task_success_rate': 0.95, 'max_cost_per_run': 0.08, 'reused_from': 'Ch7 pass_at_k threshold; Ch8 is_within_budget max_cost'}

Copperfield's credit-approval path gets a tighter budget (95% success floor, 8-cent ceiling) than a lower-stakes path would -- the exact same `is_within_budget` function Chapter 8 built and Chapter 9 reused unchanged a second time now gets reused a THIRD time, at the architecture-decision layer, to turn a stated budget into a checkable gate rather than an aspiration.

9. Question 4 -- the trade-off defense: what this design gives up

A design review never accepts "we chose X" alone -- it asks "why not Y," and expects the cost of NOT choosing Y stated plainly.

tradeoff_defense.py
TRADEOFFS_REJECTED = [
    {"alternative": "supervisor/worker multi-agent split (Ch9), one agent "
         "per request type",
     "why_rejected": "both request types read/write the SAME customer and "
         "grid state; splitting them adds Ch9's dispatch/attribution "
         "overhead with no independent-execution benefit, and risks the "
         "exact race Ch10's claim-check exists to prevent, for no reason",
     "cost_of_not_choosing_it": "none material -- the single-agent design "
         "loses nothing Copperfield's problem actually needs"},
    {"alternative": "skip reflection (Ch5) entirely, since it tested as "
         "not load-bearing",
     "why_rejected": "N/A -- this IS the chosen design, not an alternative",
     "cost_of_not_choosing_it": "if a FUTURE request type adds a hard-to-"
         "verify free-text output (e.g., a written dispute summary), "
         "reflection becomes load-bearing again and must be re-added, not "
         "assumed permanently unnecessary"},
]
for t in TRADEOFFS_REJECTED:
    print(t["alternative"], "->", t["why_rejected"][:60] + "...")
Output (real, executed) 
supervisor/worker multi-agent split (Ch9), one agent per request type -> both request types read/write the SAME customer and grid...
skip reflection (Ch5) entirely, since it tested as not load-bearing -> N/A -- this IS the chosen design, not an alternative...

Note the second entry's shape: a trade-off defense also states what would RE-OPEN a closed decision later. An architecture decision is a snapshot against stated facts, not a permanent verdict -- if Copperfield later adds a request type with a hard-to-verify output, Section 6's `has_a_hard_to_verify_free_text_output` fact flips, and reflection becomes load-bearing again.

10. The architecture-smell checklist: catching over- and under-engineering

Two mistakes recur in every architecture review: choosing MORE mechanism than a problem needs (over-engineering -- cost and complexity with no corresponding benefit) and choosing LESS than it needs (under-engineering -- a real failure mode with no mechanism guarding it). A smell check catches both from the SAME selected-mechanisms dict, automatically.

architecture_smell_check.py
def architecture_smell_check(problem, selected):
    flags = []
    if selected.get("multi-agent dispatch (Ch9)") and not problem.get("distinct_specialized_subtasks"):
        flags.append("OVER-ENGINEERED: multi-agent chosen with no distinct "
                     "specialized subtasks -- Ch9's own dispatch overhead "
                     "buys nothing here")
    if problem.get("has_an_irreversible_or_costly_action") and not selected.get("guardrails (Ch6)"):
        flags.append("UNDER-ENGINEERED: an irreversible/costly action exists "
                     "with NO guardrail -- Ch6's fail-safe-default lesson "
                     "applies directly")
    if problem.get("runs_unattended") and not selected.get("operating layer (Ch11)"):
        flags.append("UNDER-ENGINEERED: runs unattended with no operating "
                     "layer -- no idempotency, no timeout, no log; Ch11's "
                     "central finding (a retried call can drift its own "
                     "arguments) applies with nothing to catch it")
    if selected.get("reflection (Ch5)") and not problem.get("has_a_hard_to_verify_free_text_output"):
        flags.append("OVER-ENGINEERED: reflection chosen with no hard-to-"
                     "verify output -- Ch5's own lesson is that retry is "
                     "not reflection; reflection on a checkable fact is "
                     "just an extra call with no benefit")
    return flags

print(architecture_smell_check(copperfield_problem, select_mechanisms(copperfield_problem)))
Output (real, executed) 
[]

Zero flags on Copperfield's final design -- every load-bearing mechanism is backed by a stated fact, and no mechanism was chosen without one.

12. A contrasting worked example: when multi-agent genuinely IS justified

Copperfield's problem characterized as single-agent. Not every problem does. Contrast it against Chapter 11's own Harrowgate Logistics Exchange (DockScout/YardScout) and Wrenfield Dispatch Alliance (ClaimScout/ShipScout) -- both genuinely needed two independent, concurrently-acting peer agents, which is exactly why Chapters 9-11 built them that way.

Harrowgate's two concurrently-acting agents on one shared shipment queue is exactly the shape Chapter 10's claim-check and Chapter 11's idempotency keys were built for; Copperfield's single conversational flow is not. An architect who reaches for Chapter 9-10's machinery on every problem, or never reaches for it on any problem, has skipped Section 4's characterization step -- this is why it comes first.

14. Budget sensitivity: three stakes tiers, same formula

Section 8 stated two numbers for one problem. A real architecture practice states a RULE that produces the right numbers across many problems, not one hand-picked pair.

budget_tiers.py
STAKES_TIERS = [
    ("low (informational only, no money/safety impact)", {"has_an_irreversible_or_costly_action": False, "failures_are_costly_enough_to_measure": False}),
    ("medium (Copperfield's own tier)", {"has_an_irreversible_or_costly_action": True, "failures_are_costly_enough_to_measure": True}),
    ("high (irreversible AND runs unattended, e.g. Harrowgate)", {"has_an_irreversible_or_costly_action": True, "runs_unattended": True}),
]
for label, facts in STAKES_TIERS:
    b = reliability_cost_budget(facts)
    print(f"{label}: min_success={b['min_task_success_rate']}, max_cost={b['max_cost_per_run']}")

medium (Copperfield's own tier): min_success=0.95, max_cost=0.08
high (irreversible AND runs unattended, e.g. Harrowgate): min_success=0.95, max_cost=0.08

The current two-tier formula from Section 8 already separates "has an irreversible/costly action" from "does not" -- the high tier shows the SAME tier applies once any irreversible action exists, whether or not the system also runs unattended. A real extension (left as this chapter's exercises material) would add a third, tighter tier for problems that are BOTH irreversible and unattended at once.

20. Assembling the Architecture Decision Record

The four questions above are not a private thought process -- they are a document, in a fixed shape, that a reviewer who wasn't in the room can read and evaluate.

build_adr.py
def build_adr(name, problem, verdict, selected, budget, tradeoffs, flags):
    lines = [f"ARCHITECTURE DECISION RECORD -- {name}", "=" * 60,
              "", "CONTEXT", problem.get("_context", "(see problem statement)"),
              "", "DECISION",
              f"  multi-agent: {verdict['multi_agent_justified']} ({verdict['reason']})"]
    for mech, needed in selected.items():
        if needed:
            lines.append(f"  load-bearing: {mech}")
    lines += ["", "RELIABILITY/COST BUDGET",
              f"  min_task_success_rate: {budget['min_task_success_rate']}",
              f"  max_cost_per_run: {budget['max_cost_per_run']}",
              "", "ALTERNATIVES CONSIDERED AND REJECTED"]
    for t in tradeoffs:
        lines.append(f"  - {t['alternative']}: {t['why_rejected']}")
    lines += ["", "SMELL CHECK", f"  flags: {flags if flags else 'none'}"]
    return "\n".join(lines)

copperfield_problem["_context"] = "Outage reports and billing disputes via one customer portal."

                 characterize_problem(copperfield_problem),
                 select_mechanisms(copperfield_problem),
                 reliability_cost_budget(copperfield_problem),
                 TRADEOFFS_REJECTED,
                 architecture_smell_check(copperfield_problem, select_mechanisms(copperfield_problem))))

23. GenAI Builder Thought Process

When you ask an AI assistant to help design an agent architecture for a new problem, the single highest-value question to ask it back is not "what should I build" -- it's "what problem FACTS are you assuming, and which of my eleven mechanisms does each one rule in or out?" An AI that jumps straight to a multi-agent diagram without naming the fact that justifies it has skipped Section 4's characterization step, exactly the way a human architect would be called out for doing in a real design review.

prompt_for_review.txt
"Here is my problem statement: [paste it]. Before proposing an
architecture, state the specific facts that would make this a
multi-agent problem per Chapter 9-10's own tests (distinct
specialized subtasks that run independently, OR concurrent
independent actors on shared state), and say explicitly whether
THIS problem has those facts. Then, for each of Chapters 4-8's
mechanisms, name the one fact that makes it load-bearing or not.
Do not propose a design before answering both of those."

This forces the same ordering Section 3's framework uses -- characterization before mechanism selection -- and makes an AI's own shortcuts (jumping to a design before stating the facts that justify it) visible immediately.

25. Points to remember

  • An architecture DECISION is a traceable claim ("mechanism X is load-bearing BECAUSE fact Y"), not a vibe -- the same discipline Chapter 1's tool schemas and Chapter 6's guardrails already required at the mechanism level.
  • The four-question order matters: characterize (single- vs. multi-agent) before selecting mechanisms, select mechanisms before stating a budget, state a budget before defending trade-offs.
  • Chapter 9's dispatch and Chapter 10's peer communication are only load-bearing when a problem has distinct independently-runnable subtasks OR concurrent independent actors on shared state -- not by default, and not by habit.
  • A reliability/cost budget (Ch7's pass_at_k, Ch8's is_within_budget) should scale with a problem's actual stakes -- a costlier failure mode gets a tighter budget, stated as a number, not an aspiration.
  • A smell check catches both over-engineering (mechanism chosen with no supporting fact) and under-engineering (a real risk fact with no supporting mechanism) from the same selected-mechanisms dict.
  • An Architecture Decision Record assembles all four questions plus the smell check into one document a reviewer who wasn't in the room can evaluate.
  • This chapter's project closes a five-session-deferred L3 Independent project commitment -- see Section 14 and this chapter's own quality audit for the explicit decision.
  • This chapter deliberately ran no live model call -- the skill being exercised is the reader's judgment against written problem facts, not a model's own behavior.
