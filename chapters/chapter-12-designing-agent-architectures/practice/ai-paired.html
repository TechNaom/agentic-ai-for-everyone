Now Pair With an AI

A ninth scenario, not in the eight above: an unnamed logistics company's dispatch-review system, "ScopeCreep" (the specific company is left unnamed on purpose, the same way Chapter 11's "NotaryBot" scenario did), got an architecture proposal from an AI assistant with two real, layered problems in the same design review. First: the proposal split a single conversational request type (order-status lookups) into THREE separate agents "for separation of concerns," with no distinct specialized subtasks and no concurrent independent actors anywhere in the problem -- pure over-engineering. Second, in the SAME proposal: the system's one genuinely irreversible action (auto-cancelling an order after three failed delivery attempts) was given no human-approval checkpoint at all -- pure under-engineering, in the same document as the first mistake.

Step 1: Diagnose it yourself, first

Before reading further: name both problems using this chapter's vocabulary (one is a smell-check over-engineering flag, the other is a smell-check under-engineering flag) and state the specific fact that each one violates. There's no grading here, just your own reasoning to compare against Step 3.

Step 2: Ask an AI assistant

Thought process: this scenario has two layered mistakes in one proposal (unjustified multi-agent AND a missing guardrail), so the prompt needs to ask for every distinct issue, not just one -- a shallow prompt like "review this architecture" invites an answer that fixates on the more dramatic-sounding three-agent split and never checks whether the one truly risky action (auto-cancellation) has a guardrail at all.

Write the prompt you'd give an AI assistant:

Paste your prompt into your assistant of choice and compare its answer against the critique below.
Show a strong version of this prompt 
Here's an architecture proposal for a logistics dispatch-review agent: order-status lookups are split across three separate agents "for separation of concerns," and orders are auto-cancelled after three failed delivery attempts with no approval step. Run this chapter's architecture-smell check against it: for each mechanism chosen, state the SPECIFIC fact (distinct independently-runnable subtasks, or concurrent independent actors on shared state) that would justify it, or flag it as over-engineered if no such fact exists. Separately, name any irreversible or costly action with NO guardrail, and flag it as under-engineered. Do not stop after finding the first issue -- find every distinct one.

Step 3: Critique what came back

What a complete diagnosis catches
  • Problem 1 (unjustified multi-agent split): this chapter's own Section 10-11 architecture-smell check flags exactly this pattern -- multi-agent chosen with no distinct specialized subtasks that can run independently. Order-status lookups for ONE request type is a single-agent, multiple-tools problem (the same shape as Copperfield's own two request types), not three agents that would need Chapter 9's own dispatch/attribution overhead for no independent-execution benefit.
  • Problem 2 (missing guardrail on auto-cancellation): this chapter's own Section 10-11 smell check also flags an irreversible/costly action with no guardrail. Auto-cancelling an order is exactly the kind of action Chapter 6's fail-safe-default lesson says needs a human-approval checkpoint before it fires, not after a customer complains.
  • A shallow AI answer often catches only the more visible mistake (the dramatic three-agent split) and misses that the SAME proposal has a second, independent under-engineering problem sitting right next to it.

Compare the AI's answer against your own Step 1 notes and the two-problem breakdown above. Did it catch both the over-engineering AND the under-engineering flag, or did it fixate on one and miss the other?
