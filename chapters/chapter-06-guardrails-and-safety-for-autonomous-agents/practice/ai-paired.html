Chapter 6 Practice — Solo → AI-Paired → Critique 15 min

Now Pair With an AI

A ninth scenario, not in the eight above: "EscrowBot", a real-estate closing assistant at a fictional title company (left unnamed on purpose, the same way Chapter 5's RenewBot scenario did — a small scenario doesn't need an invented company). EscrowBot can release funds from escrow once a closing checklist is complete. Two real, layered problems were observed in the same trace. First: EscrowBot's "guardrail" was a system-prompt instruction ("never release funds unless the checklist tool confirms complete") with no code anywhere actually checking the checklist tool's return value before calling release_funds -- the model usually remembered to check, but on one real run, a differently-worded request caused it to call release_funds without ever calling the checklist tool first. Second, in a completely different case: a genuine code-level guardrail correctly refused a release because the checklist wasn't complete -- but the approval-service callback it depended on threw a timeout exception, and the exception handler had a bug that treated any exception as "approved" instead of "denied," so the release went through anyway.

Step 1: Diagnose it yourself, first

Before reading further: name the two distinct problems here using this chapter's vocabulary (one is about a check that was never actually enforced in code at all; the other is about a real code-level check that existed but failed OPEN instead of failing SAFE) and write your own fix for each. There's no grading here, just your own reasoning to compare against Step 3.

Step 2: Ask an AI assistant

Thought process: this scenario has two layered problems (a system-prompt-only guardrail AND a fail-open bug in a real code-level check), so the prompt needs to ask the AI to identify both, not just one — a shallow prompt like "why did my agent release funds it shouldn't have" invites a single, incomplete answer.

Write the prompt you'd give an AI assistant:

Paste your prompt into your assistant of choice and compare its answer against the critique below.
Show a strong version of this prompt 
Here's my agent EscrowBot, which can release escrow funds once a closing checklist is complete: [paste the scenario above]. Identify EVERY distinct guardrail problem in this description, not just the first one you notice -- there are two -- and name each using this chapter's vocabulary (a check that exists only as a system-prompt instruction with nothing enforcing it in code, versus a real code-level check that fails OPEN instead of failing SAFE when its own dependency errors). Propose a concrete, specific fix for each.

Step 3: Critique what came back

What a complete diagnosis catches
  • Problem 1 (system-prompt-only guardrail): telling the model "never release funds unless the checklist confirms complete" is not a guardrail — it's an instruction the model can forget or misapply under a different phrasing, exactly as this chapter's own live Sections 11-12 demonstrated with a different injected instruction. The fix is a real code check: `dispatch_release()` must itself call the checklist tool and inspect its result before allowing `release_funds()` to run, regardless of what the model's own reasoning concluded.
  • Problem 2 (fails open, not safe): a real code-level check existed, but its exception handler had the fail-safe logic backwards — treating "the approval service errored" as "approved" instead of "not approved." The fix is Section 14's rule applied literally: any exception from an approval dependency must resolve to denial, never to approval, and this needs a test that actually simulates the error path, not just the happy path.
  • A shallow AI answer often catches only Problem 2 (the more obviously "buggy-looking" code) and misses that Problem 1 is a structural issue — there was never a real guardrail there to begin with, just text a model happened to usually follow.

Compare the AI's answer against your own Step 1 notes and the two-problem breakdown above. Did it catch both? Did it propose the right fix for each — moving the check into enforced code, and fixing the fail-safe direction — or did it conflate the two into one vague "add more error handling" suggestion?
