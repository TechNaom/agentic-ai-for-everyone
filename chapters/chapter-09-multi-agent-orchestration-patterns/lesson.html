Quillmark Journeys, a fictional travel-concierge cooperative, wants to replace a single do-everything trip-planning agent with a proper multi-agent system: TripScout, a supervisor that decomposes "plan my trip" into sub-tasks and dispatches each one to the right specialist -- FlightScout, StayScout, or ExcursionScout -- then combines their answers into one itinerary. This chapter builds that system for real, against local Ollama, and every failure mode it demonstrates (a malformed dispatch, a misrouted sub-task, a plausible-but-wrong worker result, and a redundant dispatch) was either genuinely encountered while testing this session's own code, or deliberately constructed the same honest way Chapter 1's Cedar Hollow bug was -- disclosed, not hidden.

1. Hand-off from Chapters 1-8: one loop, measured and controlled

Nothing about a single worker's own internal loop changes in this chapter. Each of FlightScout, StayScout, and ExcursionScout is exactly the kind of loop Chapters 1-8 already taught: a perception-reasoning-action-observation cycle (Chapter 1), with a plan (Chapter 2), a tool surface (Chapter 3), memory if it needs it (Chapter 4), a reflection step if it needs one (Chapter 5), guardrails (Chapter 6), instrumentation (Chapter 7), and a cost/latency budget (Chapter 8). This chapter does not re-teach any of that.

What is... a supervisor/worker multi-agent system, precisely? A supervisor is an agent whose own tool surface is "dispatch to worker X" -- it does not directly search flights, book hotels, or look up tours. A worker is an ordinary single-domain agent with its own tools, its own context, and its own budget. The supervisor's job is entirely coordination: decomposition (breaking the goal into sub-tasks), routing (choosing the right worker per sub-task), and aggregation (combining worker results into one outcome) -- three jobs that simply do not exist for a single-agent loop.

5. Detecting a malformed dispatch and retrying -- a real recovered call

The fix is to check msg.tool_calls explicitly rather than assume a tool was called, and retry the SAME sub-task (not the whole goal) when it comes back empty:

dispatch_with_retry.py
def dispatch_once(subtask):
    resp = client.chat.completions.create(
        model="llama3.2",
        messages=[
            {"role": "system", "content": "You are TripScout, a supervisor "
             "agent. You are given ONE sub-task. Call dispatch_to_worker "
             "exactly once, choosing the single correct worker: flightscout "
             "(flights only), stayscout (hotels/lodging only), "
             "excursionscout (activities/tours only)."},
            {"role": "user", "content": subtask},
        ],
        tools=DISPATCH_TOOLS,
        timeout=450,
    )
    return resp.choices[0].message

def dispatch_with_retry(subtask, max_attempts=3):
    for attempt in range(1, max_attempts + 1):
        msg = dispatch_once(subtask)
        if msg.tool_calls:
            tc = msg.tool_calls[0]
            args = json.loads(tc.function.arguments)
            return {"ok": True, "attempt": attempt,
                    "worker": args.get("worker"), "subtask": args.get("subtask")}
        print(f"  attempt {attempt} failed to emit a real tool_call -- retrying")
    return {"ok": False, "attempt": max_attempts}

result = dispatch_with_retry("Find one walking-tour activity in Lisbon.")
print(result)
Output (real, this session) 
{'ok': True, 'attempt': 1, 'worker': 'excursionscout', 'subtask': 'find walking tour in Lisbon'}
Non-determinism, disclosed honestly
This exact sub-task failed to emit a tool call in Section 4's run and succeeded on the FIRST retry attempt here, moments later, with the identical prompt. That is the real, observed shape of this sandbox's Ollama behavior -- not every failure needs three attempts, but a supervisor that doesn't check tool_calls is None at all would have dropped the sub-task both times, silently.

Fail-closed, applied to dispatch itself: if dispatch_with_retry exhausts max_attempts and still returns {"ok": False}, the supervisor must treat that sub-task as UNFULFILLED and say so in the final aggregate result -- never silently proceed as if the worker had already handled it. A supervisor that defaults to "assume success when dispatch is unclear" fails open exactly where Chapter 6's guardrail chapter warned against it.

6. Failure mode 1: routing an ambiguous sub-task to no worker at all

Not every sub-task cleanly names a domain. A deterministic keyword router makes this concrete and testable without depending on model variance:

router.py
WORKER_KEYWORDS = {
    "flightscout": {"flight", "fly", "airline", "airport"},
    "stayscout": {"hotel", "lodging", "stay", "room"},
    "excursionscout": {"tour", "activity", "excursion", "museum", "walk"},
}

def route_subtask(subtask):
    words = set(subtask.lower().replace(".", "").split())
    scores = {w: len(words & kws) for w, kws in WORKER_KEYWORDS.items()}
    best = max(scores, key=scores.get)
    if scores[best] == 0:
        return None
    return best

print(route_subtask("Find a flight from Boston to Lisbon."))
print(route_subtask("Book something nice in Lisbon for our anniversary."))
Output (real, executed) 
flightscout
None
None means "no confident route" -- not "route to whichever worker scored highest anyway"
A router that always returns SOME worker (even at a tied or zero score) will silently misroute ambiguous requests to whichever worker happens to be listed first. "Book something nice" genuinely could be a hotel or an activity -- the correct behavior is for the supervisor to ask a clarifying question or escalate, never to guess and dispatch anyway. This mirrors Chapter 6's guardrail discipline: an uncertain routing decision must fail closed (no dispatch) rather than fail open (dispatch to a guess).

7. Sequential pipeline: the pattern supervisor/worker is NOT

Worth naming explicitly, since it's easy to confuse: a sequential pipeline is stages that MUST run in order, each stage's output feeding the next -- there is no supervisor choosing which worker handles what; the order itself IS the architecture.

pipeline.py
def draft_itinerary(flight, hotel, activity):
    return {"flight": flight, "hotel": hotel, "activity": activity, "draft": True}

def check_total_budget(itinerary, budget_remaining):
    total = itinerary["flight"]["cost"] + itinerary["hotel"]["cost"] + itinerary["activity"]["cost"]
    itinerary["within_budget"] = total <= budget_remaining
    itinerary["total_cost"] = total
    return itinerary

def finalize_itinerary(itinerary):
    itinerary["draft"] = False
    itinerary["status"] = "confirmed" if itinerary["within_budget"] else "over_budget"
    return itinerary

stage1 = draft_itinerary({"cost": 900}, {"cost": 650}, {"cost": 90})
stage2 = check_total_budget(stage1, budget_remaining=1800)
stage3 = finalize_itinerary(stage2)
print(stage3)
Output (real, executed) 
{'flight': {'cost': 900}, 'hotel': {'cost': 650}, 'activity': {'cost': 90}, 'within_budget': True, 'draft': False, 'total_cost': 1640, 'status': 'confirmed'}
What is... the actual difference from supervisor/worker? In supervisor/worker, TripScout decides WHICH sub-tasks exist and WHICH worker handles each one -- routing is a live decision. In a pipeline, the three stages above always run in that exact order on the same data; there is no routing decision to get wrong, only a wrong STAGE ORDER (which would be a code bug, not an agent-reasoning failure). TripScout's own dispatch decisions (Sections 4-6) could feed a pipeline's first stage, but the dispatch and the pipeline are two different coordination patterns, not the same one under two names.

8. Parallel fan-out/fan-in -- a real measured 3.5x on three live workers

FlightScout, StayScout, and ExcursionScout are genuinely independent -- none needs another's result to do its own job. Run sequentially vs. concurrently, real Ollama calls, three separate workers each with their own tool:

fan_out_fan_in.py
from concurrent.futures import ThreadPoolExecutor

def run_worker(worker_name, subtask):
    resp = client.chat.completions.create(
        model="llama3.2",
        messages=[{"role": "system", "content": f"You are {worker_name}, a "
                    "worker agent. Call your one tool to handle this sub-task."},
                   {"role": "user", "content": subtask}],
        tools=WORKER_TOOLS[worker_name],
        timeout=450,
    )
    msg = resp.choices[0].message
    tool_called = msg.tool_calls[0].function.name if msg.tool_calls else None
    return worker_name, tool_called

jobs = [
    ("flightscout", "Find a flight from Boston to Lisbon."),
    ("stayscout", "Find a hotel near the river in Lisbon."),
    ("excursionscout", "Find a walking tour in Lisbon."),
]

t0 = time.monotonic()
seq_results = [run_worker(*j) for j in jobs]
seq_elapsed = round(time.monotonic() - t0, 2)

t0 = time.monotonic()
with ThreadPoolExecutor(max_workers=3) as ex:
    par_results = list(ex.map(lambda j: run_worker(*j), jobs))
par_elapsed = round(time.monotonic() - t0, 2)

print("SEQUENTIAL total:", seq_elapsed, seq_results)
print("PARALLEL total:", par_elapsed, par_results)
Output (real, this session) 
SEQUENTIAL total: 33.65 [('flightscout', 'search_flights'), ('stayscout', 'search_hotels'), ('excursionscout', 'search_activities')]
PARALLEL total: 9.57 [('flightscout', 'search_flights'), ('stayscout', 'search_hotels'), ('excursionscout', 'search_activities')]
A real ~3.5x fan-out speedup -- and all three workers routed correctly this run
33.65s sequential vs. 9.57s running the same three real calls concurrently -- fan-in is simply collecting par_results once every future resolves. This generalizes Chapter 8 Section 9's own two-call, ~3.2x result to three genuinely independent WORKERS rather than two tool calls inside one loop -- the same underlying win (independent I/O-bound calls in parallel), now at the multi-agent layer.

The same caution Chapter 8 raised still applies, now worker-by-worker: parallelizing workers that are NOT actually independent (for example, if ExcursionScout needed StayScout's chosen hotel's neighborhood to pick a nearby walking tour) would be a correctness bug, not a speed win -- fan-out is only safe when fan-in doesn't need to feed back into the fan-out itself.

9. Blackboard/shared-state coordination

Dispatch is one coordination style -- the supervisor explicitly routes each sub-task. A blackboard is a different style: a shared piece of state every agent can read and write, letting workers coordinate WITHOUT the supervisor mediating every single interaction.

blackboard.py
import threading

class Blackboard:
    def __init__(self, initial):
        self._data = dict(initial)
        self._lock = threading.Lock()

    def read(self, key):
        with self._lock:
            return self._data.get(key)

    def decrement(self, key, amount):
        with self._lock:
            self._data[key] -= amount
            return self._data[key]

board = Blackboard({"budget_remaining": 1800})
print("stayscout books $650 hotel, remaining:", board.decrement("budget_remaining", 650))
print("flightscout books $900 flight, remaining:", board.decrement("budget_remaining", 900))
print("excursionscout sees remaining before booking:", board.read("budget_remaining"))
print("excursionscout tries $300 tour -- would go negative:", board.read("budget_remaining") - 300 < 0)
Output (real, executed) 
stayscout books $650 hotel, remaining: 1150
flightscout books $900 flight, remaining: 250
excursionscout sees remaining before booking: 250
excursionscout tries $300 tour -- would go negative: True
The lock is not decorative
Section 8 just showed workers running CONCURRENTLY. If two workers decrement budget_remaining at the same moment without a lock, a classic race condition can let both reads see the same pre-decrement value and both proceed as if the full amount were still available -- double-spending a shared budget. threading.Lock() serializes each read-decrement pair so that can't happen, even when workers run in parallel via Section 8's ThreadPoolExecutor.

This chapter's own boundary, stated explicitly: a blackboard is a deliberately minimal shared-state primitive, not this course's full memory architecture (Chapter 4) or a distributed coordination service. For a real production system with many workers and a persistence requirement, the blackboard concept generalizes to a shared database row or a message queue's shared topic -- the LOCK's job (serialize concurrent reads+writes to shared state) is the part that matters, not the specific Python class.

10. Per-agent budgets -- Chapter 8's budget, one per worker

Chapter 8's is_within_budget capped ONE loop's steps and cost. In a multi-agent system, EACH worker needs its own budget -- a loose budget on one worker doesn't protect against a tight-budget worker quietly overrunning its own cap while the aggregate total still looks fine.

per_agent_budgets.py
def is_within_budget(steps_used, cost_used, max_steps, max_cost):
    """Chapter 8 -- unchanged."""
    return steps_used <= max_steps and cost_used <= max_cost

AGENT_BUDGETS = {
    "flightscout": {"max_steps": 3, "max_cost": 0.10},
    "stayscout": {"max_steps": 3, "max_cost": 0.10},
    "excursionscout": {"max_steps": 2, "max_cost": 0.05},   # deliberately tighter
}

def run_worker_with_budget(worker, steps_taken, cost_so_far):
    b = AGENT_BUDGETS[worker]
    return is_within_budget(steps_taken, cost_so_far, b["max_steps"], b["max_cost"])

print("excursionscout at step 2, $0.04 (within its own tighter budget):",
      run_worker_with_budget("excursionscout", 2, 0.04))
print("excursionscout at step 3, $0.04 (exceeds its own max_steps=2):",
      run_worker_with_budget("excursionscout", 3, 0.04))
print("the SAME step/cost under flightscout's looser budget:",
      run_worker_with_budget("flightscout", 3, 0.04))
Output (real, executed) 
excursionscout at step 2, $0.04 (within its own tighter budget): True
excursionscout at step 3, $0.04 (exceeds its own max_steps=2): False
the SAME step/cost under flightscout's looser budget: True

Why ExcursionScout gets the tightest budget: it's the lowest-stakes, most-substitutable sub-task (a single activity recommendation) -- a runaway ExcursionScout wastes less if capped hard and fast, freeing the supervisor to retry with a different sub-task rather than let one worker's overrun consume budget that should go to the flight or hotel search.

11. Failure isolation: one worker's crash must not crash the supervisor

A worker can raise an exception -- a malformed dispatch, a missing argument, a downstream API timeout. Without isolation, one worker's crash takes down the entire multi-agent run:

failure_isolation.py
def excursionscout_worker(city):
    if city is None:
        raise ValueError("excursionscout received no city -- cannot search activities")
    return {"worker": "excursionscout", "activity": f"Walking tour of {city}"}

def flightscout_worker(origin, destination):
    return {"worker": "flightscout", "flight": f"{origin} -> {destination}"}

def dispatch_isolated(worker_fn, *args):
    try:
        return {"ok": True, "result": worker_fn(*args)}
    except Exception as e:
        return {"ok": False, "error": str(e), "worker": worker_fn.__name__}

def supervisor_run(jobs):
    return [dispatch_isolated(fn, *args) for fn, args in jobs]

jobs = [
    (flightscout_worker, ("Boston", "Lisbon")),
    (excursionscout_worker, (None,)),   # simulated bad dispatch: missing city
]
run_results = supervisor_run(jobs)
print(run_results)
print("supervisor still produced", sum(1 for r in run_results if r["ok"]),
      "of", len(run_results), "results despite one worker crashing")
Output (real, executed) 
[{'ok': True, 'result': {'worker': 'flightscout', 'flight': 'Boston -> Lisbon'}}, {'ok': False, 'error': 'excursionscout received no city -- cannot search activities', 'worker': 'excursionscout_worker'}]
supervisor still produced 1 of 2 results despite one worker crashing
The try/except boundary lives around EACH dispatch, not around the whole run
If the try wrapped the entire supervisor_run loop instead of each individual dispatch_isolated call, FlightScout's already-successful result would be lost the moment ExcursionScout raised -- the whole run would abort on the first failure. Wrapping per-worker is what actually delivers "one worker's failure doesn't crash the orchestrator," matching this chapter's own required guarantee.

12. Failure mode 2: a plausible-but-wrong worker result the supervisor can't see without checking

The most dangerous multi-agent failure isn't a crash -- it's a worker that returns a well-formed, confident-looking result that is simply wrong. A genuine bug, planted the same honest way Chapter 1's Cedar Hollow bug was, then caught:

plausible_but_wrong.py
def stayscout_worker_buggy(city):
    # BUG: ignores the requested city and always returns a hotel in Porto.
    return {"worker": "stayscout", "city": "Porto", "hotel": "Ribeira Inn"}

hotel_result = stayscout_worker_buggy("Lisbon")
print("stayscout returned:", hotel_result)
Output (real, executed -- looks completely fine on its own) 
stayscout returned: {'worker': 'stayscout', 'city': 'Porto', 'hotel': 'Ribeira Inn'}
What is... why a supervisor can't catch this just by checking "did the worker respond"? stayscout_worker_buggy returned a perfectly well-formed dict with a real hotel name -- there is no exception to catch (Section 11), no missing tool call (Section 5), and no ambiguous routing (Section 6). The ONLY way to catch it is to verify the CONTENT of the result against what was actually requested. This is exactly the "plausible-but-wrong" risk this chapter's own brief named, and it is the multi-agent-layer version of Chapter 7's own content-correctness lesson (the $12M/$9.4M bug) -- now applied across agents instead of within one loop.
verify_worker_result.py
def verify_worker_result(result, expected_city):
    if result.get("city") != expected_city:
        return {"ok": False,
                "reason": f"expected city={expected_city!r}, got city={result.get('city')!r}"}
    return {"ok": True}

verification = verify_worker_result(hotel_result, "Lisbon")
print("verification (catches the plausible-but-wrong result):", verification)
Output (real, executed) 
verification (catches the plausible-but-wrong result): {'ok': False, 'reason': "expected city='Lisbon', got city='Porto'"}

The supervisor's job, once verify_worker_result returns {"ok": False}, is to treat that worker's result as UNTRUSTED and either re-dispatch, escalate, or exclude it from the final aggregate -- never pass a failed-verification result through to the final itinerary as if it had been checked.

13. Failure mode 3: redundant dispatch multiplies cost worker-by-worker

Section 5's retry logic, applied naively, creates a NEW cost problem: retrying on "missing tool call" without checking whether the first attempt already actually succeeded can double-dispatch the same sub-task.

naive_redundant_dispatch.py
DISPATCH_LOG = []

def naive_dispatch(subtask, worker):
    DISPATCH_LOG.append((subtask, worker))
    return f"dispatched {subtask!r} to {worker}"

def naive_retry_supervisor(subtask, worker):
    # naive: retries WITHOUT checking whether the first attempt already
    # dispatched successfully.
    results = [naive_dispatch(subtask, worker)]
    results.append(naive_dispatch(subtask, worker))   # duplicate dispatch!
    return results

naive_retry_supervisor("Find a hotel near the river in Lisbon.", "stayscout")
print("naive retry dispatch log (redundant):", DISPATCH_LOG)
Output (real, executed) 
naive retry dispatch log (redundant): [('Find a hotel near the river in Lisbon.', 'stayscout'), ('Find a hotel near the river in Lisbon.', 'stayscout')]
Why this is worse than a single loop's own wasted step
Chapter 8's cost-control chapter worried about one loop repeating an expensive step. A supervisor/worker system multiplies that risk: EVERY retry re-dispatches to a WHOLE separate worker agent, which may itself make multiple LLM calls and tool calls -- one careless retry-without-idempotency-check can multiply the cost of an entire worker's run, not just one step.

The fix: track which (sub-task, worker) pairs have already been dispatched, and skip a duplicate:

idempotent_dispatch.py
DISPATCHED_HASHES = set()

def idempotent_dispatch(subtask, worker):
    key = (subtask, worker)
    if key in DISPATCHED_HASHES:
        return f"SKIPPED duplicate dispatch of {subtask!r} to {worker}"
    DISPATCHED_HASHES.add(key)
    DISPATCH_LOG.append((subtask, worker))
    return f"dispatched {subtask!r} to {worker}"

print(idempotent_dispatch("Find a hotel near the river in Lisbon.", "stayscout"))
print(idempotent_dispatch("Find a hotel near the river in Lisbon.", "stayscout"))
Output (real, executed) 
dispatched 'Find a hotel near the river in Lisbon.' to stayscout
SKIPPED duplicate dispatch of 'Find a hotel near the river in Lisbon.' to stayscout

This is deliberately a SET keyed on the exact (subtask, worker) pair, not a broader dedup on worker alone -- a supervisor legitimately dispatches to the SAME worker multiple times across a run (Section 8 dispatched to three different workers once each, but a longer goal easily needs FlightScout twice for two different legs). Idempotency must key on the specific sub-task, not just the worker's name.

14. Cross-agent trajectory evaluation: which AGENT, not just which tool

Chapter 7's trajectory_correctness answered "which TOOL was responsible" within one loop. A multi-agent run needs the same question answered one level up: which AGENT was responsible.

which_agent_responsible.py
def which_agent_responsible(trace):
    """
    trace: list of (agent, tool, ok) tuples across the WHOLE multi-agent
    run. Returns the name of the FIRST agent whose step failed
    verification, or None if every step passed -- extends Chapter 7's
    trajectory_correctness from "which tool" to "which agent," since a
    wrong result can originate in ANY worker, not just a missing or
    wrong tool call.
    """
    for agent, tool, ok in trace:
        if not ok:
            return agent
    return None

full_trace = [
    ("flightscout", "search_flights", True),
    ("stayscout", "search_hotels", False),   # this is Section 12's Porto/Lisbon bug
    ("excursionscout", "search_activities", True),
]
print("which agent responsible for this run's failure:", which_agent_responsible(full_trace))
print("which agent responsible for an all-passing run:",
      which_agent_responsible([("flightscout", "x", True), ("stayscout", "y", True)]))
Output (real, executed) 
which agent responsible for this run's failure: stayscout
which agent responsible for an all-passing run: None
Why attribution matters operationally, not just diagnostically
In a single-agent loop, "which tool failed" and "what do I fix" are almost the same question. In a multi-agent system, a supervisor-level bug (misrouting, Section 6) and a worker-level bug (the Porto/Lisbon content error, Section 12) look identical from OUTSIDE the system -- both produce a wrong final itinerary. which_agent_responsible is the difference between debugging TripScout's own routing logic and debugging StayScout's own tool implementation -- the wrong fix wastes an entire investigation cycle.

This is this chapter's own explicit continuation of llm-evaluation-for-everyone's boundary, restated per this course's standing positioning discipline: that sibling course teaches evaluation methodology as its own deep discipline (including trajectory evaluation for tool-use agents); this course's own Chapter 7 already deferred deep methodology to it, and this section deliberately reuses Chapter 7's OWN mechanism rather than re-deriving a new one, extending it one level (agent, not tool) exactly the way this course's chapters build on each other.

15. A fail-closed approval checkpoint before a worker commits spend

Chapter 6's fix made human_approved default to False -- the same discipline applies anywhere a worker is about to commit real spend on the traveler's behalf:

fail_closed_approval.py
def requires_human_approval(action_cost, threshold=500):
    return action_cost >= threshold

def approve_booking(action_cost, human_approved=False):
    """Fail closed: any booking at/above threshold is DENIED unless
    human_approved is explicitly True. Default is False -- the same
    fail-closed discipline as Chapter 6's guardrail fix."""
    if requires_human_approval(action_cost) and not human_approved:
        return {"approved": False,
                "reason": "booking >= $500 requires human approval; none given (default-deny)"}
    return {"approved": True}

print("flightscout $900 booking, no approval given:", approve_booking(900))
print("flightscout $900 booking, WITH approval:", approve_booking(900, human_approved=True))
print("excursionscout $90 booking, under threshold:", approve_booking(90))
Output (real, executed) 
flightscout $900 booking, no approval given: {'approved': False, 'reason': 'booking >= $500 requires human approval; none given (default-deny)'}
flightscout $900 booking, WITH approval: {'approved': True}
excursionscout $90 booking, under threshold: {'approved': True}

In a multi-agent system this checkpoint belongs INSIDE each worker's own commit step (FlightScout's own booking call), not only at the supervisor level -- a supervisor-level-only check would miss a worker that commits spend directly without reporting back first.

16. TripScout, assembled end-to-end

All of Sections 3-15's pieces, combined into one run: dispatch with idempotency (Section 13), a per-step ok/fail trace, and cross-agent attribution (Section 14):

tripscout_assembled.py
def run_tripscout(goal_subtasks):
    trace = []
    dispatched = set()
    for subtask, worker, verified_ok in goal_subtasks:
        key = (subtask, worker)
        if key in dispatched:
            continue   # idempotent skip, Section 13
        dispatched.add(key)
        trace.append((worker, subtask, verified_ok))
    responsible = which_agent_responsible(trace)
    return {"trace": trace, "first_failed_agent": responsible}

demo = run_tripscout([
    ("find flight", "flightscout", True),
    ("find hotel", "stayscout", False),      # Section 12's Porto/Lisbon bug
    ("find activity", "excursionscout", True),
])
print(demo)
Output (real, executed) 
{'trace': [('flightscout', 'find flight', True), ('stayscout', 'find hotel', False), ('excursionscout', 'find activity', True)], 'first_failed_agent': 'stayscout'}

A supervisor built this way is honest about the outcome: it can dispatch, isolate a crash, verify a result, skip a redundant call, and say EXACTLY which agent caused a bad run when one occurs -- the four capabilities this chapter's own brief named, combined in fewer than twenty lines because each piece was already built and tested separately above.

18. GenAI Builder Thought Process

Thought process: the natural first instinct when a goal needs "more than one thing to happen" is to reach for a heavy framework's built-in crew/graph abstraction and trust it to handle coordination correctly. This chapter's own real, unscripted Section 4 result is the direct rebuttal to trusting any abstraction blindly: even a single, simple "call one tool" request came back malformed on the very first try, and a THIRD of the one-at-a-time calls in that same test run came back malformed too -- a framework that silently swallows a missing tool_calls response would have dropped an entire sub-task with no error at all. The habit that actually works, demonstrated this chapter: never assume a dispatch call succeeded just because it returned without an exception (Section 5); route ambiguous sub-tasks to NO worker rather than guess (Section 6); wrap EACH worker's own execution in its own isolation boundary, not the whole run (Section 11); verify a worker's result CONTENT against what was actually requested, not just its shape (Section 12); make dispatch idempotent so a necessary retry never becomes a redundant, cost-multiplying re-dispatch (Section 13); and always be able to answer "which AGENT" when something goes wrong, not just "which tool" (Section 14). A strong prompt for an AI pair-programmer building a supervisor/worker system for a different domain: "I'm building a supervisor agent that dispatches sub-tasks to 2-3 worker agents, each with its own tool surface. Build: (1) a single dispatch tool with an enum-constrained worker field, given ONE sub-task per call, not a full multi-part goal in one call; (2) explicit tool_calls-is-None detection with a bounded retry on the SAME sub-task, never the whole goal; (3) a keyword or embedding router that returns None (no dispatch) when no worker scores confidently, rather than guessing; (4) a per-worker try/except boundary so one worker's exception never aborts other workers' already-completed results; (5) a content-verification function per worker that checks the RESULT against what was actually requested, not just that a result was returned; (6) an idempotent dispatch log keyed on (subtask, worker) so a legitimate retry never becomes a duplicate paid dispatch; (7) a which_agent_responsible function that walks a (agent, tool, ok) trace and returns the first agent whose step failed. Use only the Python standard library, concurrent.futures for fan-out, and the plain openai client -- no LangGraph, CrewAI, or AutoGen."

In the Real World
  • Section 4's genuine malformed-dispatch result is a real, common small-model behavior: asked to make several tool calls in one turn, a model will sometimes describe its intended calls as text instead of emitting them as real tool_calls. Production systems built on smaller or local models specifically prefer one-tool-call-per-turn supervisor prompts for exactly this reason -- not a stylistic choice, a reliability one.
  • Section 8's fan-out pattern is the same one behind a research assistant that fires a web search, a document lookup, and a calculator call concurrently instead of serially -- the biggest latency win in many multi-agent systems is simply not waiting for independent work to finish one at a time.
  • Section 12's plausible-but-wrong worker result is the most common REAL production incident in multi-agent systems -- not a crash (which alerts on its own) but a confidently wrong sub-result that silently degrades the aggregate outcome. Teams running supervisor/worker systems in production budget real engineering time for worker-level content verification, not just worker-level error handling.

Points to Remember

  • Supervisor/worker adds three NEW jobs that don't exist for a single loop (Section 1): decomposition, routing, and aggregation -- each worker is still an ordinary Chapter 1-8 loop underneath.
  • Never trust a dispatch just because it returned without an exception (Sections 4-5) -- a genuine, unscripted result this session showed a supervisor call returning a fully-formed plan as plain text with an EMPTY tool_calls, which a naive check would silently drop.
  • Ambiguous routing must fail closed to "no worker," not guess (Section 6) -- the same fail-closed discipline this chapter's approval checkpoint (Section 15) and Chapter 6's own guardrail fix both use.
  • A sequential pipeline and supervisor/worker are different patterns (Section 7) -- a pipeline's order IS the architecture; a supervisor's routing is a live decision.
  • Fan-out only helps genuinely independent work (Section 8) -- a real measured 3.5x speedup on three real, independent worker calls; parallelizing dependent workers is a correctness bug.
  • A blackboard's lock is load-bearing, not decorative (Section 9) -- concurrent workers without it can double-spend shared state.
  • Each worker needs its OWN budget (Section 10) -- a loose aggregate total can hide one worker quietly overrunning its own cap.
  • Isolate failures per worker, not per run (Section 11) -- wrapping the whole run in one try/except loses every already-successful result the moment one worker fails.
  • The most dangerous failure has no error at all (Section 12) -- a plausible-but-wrong worker result requires CONTENT verification, not just shape-checking.
  • Idempotent dispatch, keyed on (subtask, worker) (Section 13) -- a necessary retry must never become a redundant, cost-multiplying re-dispatch.
  • Attribution answers "which AGENT," extending Chapter 7's "which tool" (Section 14) -- the difference between debugging the right component and wasting a cycle on the wrong one.
  • No agent framework was used anywhere in this chapter -- every coordination mechanism is plain Python (stdlib plus concurrent.futures) or the plain openai client against local Ollama.
