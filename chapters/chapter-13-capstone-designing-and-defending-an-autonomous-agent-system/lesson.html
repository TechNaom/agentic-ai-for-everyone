2. Why this chapter runs no live model call, and says so

Chapter 12 ran no live Ollama call because the skill it exercised -- judgment against written problem facts -- is not a model's live behavior. This chapter's own capstone has the SAME property: characterizing a multi-component problem, selecting mechanisms, stating a budget, and proving a reference implementation meets that budget are all architecture judgment and proof-of-design, exactly like Chapter 12's own L3 project (Driftlight), which also implemented real memory/guardrail/idempotency code with zero live model calls. A live call here would illustrate nothing the deterministic harness below doesn't already prove, and would make grading depend on a running Ollama server for no benefit -- so this session made none, honestly, the same disclosed decision Chapter 12 made.

Go deeper Contrast this with a hypothetical capstone that instead asked "build a real agent LOOP that plans, calls tools, and reflects on a live model's own output for a brand-new task." THAT capstone would genuinely need a live call, because the thing being proven would be the model's actual behavior, not just the architecture around it. This capstone's own deliverable is the architecture and its proof, not a model's live reasoning -- which is why the "live call or not" decision has to be made explicitly, every time, rather than defaulted either way.

4. The problem: Thornwick Marketplace Collective

Thornwick Marketplace Collective is a fictional online marketplace connecting independent makers to buyers, built from three distinct, specialized components:

  • Buyer Concierge -- conversational: product Q&A, order placement, return requests. A buyer's stated allergy or preference at one order must correctly inform every LATER, separate order.
  • Maker Fulfillment -- processes maker-side packing confirmations and inventory decrements, batched OVERNIGHT, with no staff watching.
  • Fraud & Dispute Review -- evaluates chargeback disputes; refunds above a threshold need explicit human approval, and the written resolution explanation sent to a maker or buyer is free text that can't be checked by a simple rule.

Buyer Concierge and Maker Fulfillment both read and write the SAME shared inventory ledger -- a buyer's checkout and the overnight fulfillment batch can both try to claim the same sku's last unit at the same time. This is the fact that makes Thornwick genuinely different from every one of Chapter 12's own worked examples.

14. Implementing memory (Ch4): a buyer preference that survives a separate session

memory_store.py
class MemoryStore:
    """Same JSON-file-backed, read-modify-write shape as Ch4's CoachBot
    and Ch12's own Driftlight MemoryStore."""

    def __init__(self, path):
        self.path = path
        if not os.path.exists(path):
            with open(path, "w") as f:
                json.dump({}, f)

    def set_preference(self, buyer_id, allergy):
        data = self._read(); data[buyer_id] = {"allergy": allergy}; self._write(data)

    def get_preference(self, buyer_id):
        record = self._read().get(buyer_id)
        return record["allergy"] if record else None

mem_path = tempfile.mktemp(suffix=".json")
session_1 = MemoryStore(mem_path)
session_1.set_preference("B-100", "shellfish")
del session_1                                   # the first session ends
session_2 = MemoryStore(mem_path)                # a GENUINELY separate instance
print(f"get_preference('B-100') from a separate session -> {session_2.get_preference('B-100')!r}")
Output (real, executed)

15. Implementing peer coordination (Ch10): a claim-check that prevents overselling

This is the mechanism no prior chapter's worked example combined with memory, reflection, and guardrails all at once -- Thornwick's own central proof.

inventory_ledger.py
class InventoryLedger:
    def try_claim(self, sku, qty, claimed_this_tick):
        """claimed_this_tick is a set shared across BOTH racing actors in
        a single simulated instant -- the lock. A sku already claimed
        this tick is rejected outright, before even checking stock."""
        if sku in claimed_this_tick:
            return {"claimed": False, "reason": "sku already claimed this tick"}
        data = self._read_data()
        available = data.get(sku, 0)
        if available < qty:
            return {"claimed": False, "reason": "insufficient stock"}
        claimed_this_tick.add(sku)
        data[sku] = available - qty
        self._write_data(data)
        return {"claimed": True, "remaining": data[sku]}

ledger = InventoryLedger(tempfile.mktemp(suffix=".json"))
ledger.set_stock("SKU-LAST", 1)       # exactly one unit left
tick = set()
buyer_claim = ledger.try_claim("SKU-LAST", 1, tick)       # Buyer Concierge
maker_claim = ledger.try_claim("SKU-LAST", 1, tick)       # Maker Fulfillment, SAME tick
print("Buyer Concierge claim:", buyer_claim)
print("Maker Fulfillment claim (same tick):", maker_claim)
Output (real, executed) 
Buyer Concierge claim: {'claimed': True, 'remaining': 0}
Maker Fulfillment claim (same tick): {'claimed': False, 'reason': 'sku already claimed this tick'}

Exactly one unit existed; exactly one claim won. This is NOT an unlocked "read stock, then decrement" sequence -- the lock (claimed_this_tick) rejects the second claim BEFORE it ever re-checks stock, which is what makes this a claim-CHECK (Chapter 10's own fix) rather than a race with a lucky outcome.

16. Implementing guardrails (Ch6): a fail-closed refund gate

GUARDRAIL_REFUND_THRESHOLD = 40.00

def apply_refund(dispute_id, amount, human_approved=False):
    if amount > GUARDRAIL_REFUND_THRESHOLD and not human_approved:
        return {"applied": False, "reason": "blocked: exceeds guardrail threshold without human approval"}

approved = apply_refund("D-1", 60.00, human_approved=True)

print("approved:", approved)
print("small (no approval needed):", small)

17. Implementing the operating layer (Ch11): an idempotent overnight commit

commit_once.py
def idempotency_key(sku, order_id):
    return f"{sku}:{order_id}"      # keyed on what DEFINES the effect

def commit_once(key, committed_keys, effect_fn):
    if key in committed_keys:
        return {"replayed": True, "result": committed_keys[key]}
    result = effect_fn()
    committed_keys[key] = result
    return {"replayed": False, "result": result}

committed = {}
calls = {"n": 0}
def effect():
    calls["n"] += 1
    return {"committed": True}

key = idempotency_key("SKU-9", "order-77")
first = commit_once(key, committed, effect)
second = commit_once(key, committed, effect)     # simulates a RETRIED call
print("first commit:", first)
print("second (retried) commit:", second)
print("effect() actually called:", calls["n"], "time(s)")
Output (real, executed) 
first commit: {'replayed': False, 'result': {'committed': True}}
second (retried) commit: {'replayed': True, 'result': {'committed': True}}
effect() actually called: 1 time(s)

A network blip retrying the SAME overnight fulfillment call -- unwatched, since Maker Fulfillment runs with no staff present -- replays the first result instead of committing the side effect a second time, exactly Chapter 11's own fix.

18. Implementing reflection (Ch5): a grounded check on free text

grounded_reflect.py
REQUIRED_DISPUTE_FACTS = ["order_id", "amount", "resolution"]

def grounded_reflect(explanation_text, required_facts=REQUIRED_DISPUTE_FACTS):
    missing = [fact for fact in required_facts if fact not in explanation_text]
    return (len(missing) == 0, missing)

good = "order_id D-11, amount 55.00, resolution denied"
bad = "We looked into this and decided it was fine."
print("good explanation ->", grounded_reflect(good))
print("bad explanation ->", grounded_reflect(bad))
Output (real, executed) 
good explanation -> (True, [])
bad explanation -> (False, ['order_id', 'amount', 'resolution'])

This is "retry is not reflection" (Chapter 5's own lesson) applied to free text: the check looks for SPECIFIC required facts, not just that an explanation exists. A fluent paragraph mentioning none of them still fails -- which is exactly what distinguishes reflection from a bare re-ask.

19. Multi-agent dispatch (Ch9): why three components, not three copies of one agent

Chapter 9's own dispatch mechanism is a routing/attribution concern: a supervisor sends each incoming request to the specialized worker that owns it, and every result is traceable back to which worker produced it. Thornwick's own three components ARE that pattern -- Buyer Concierge, Maker Fulfillment, and Fraud & Dispute Review each own a distinct queue of work, and nothing routes an order-placement request to the fraud reviewer or a dispute to the buyer-facing agent.

24. GenAI Builder Thought Process

When you ask an AI assistant to design a multi-component system, the highest-value follow-up is not "what should the architecture look like" -- it's "which TWO facts, independently, justify multi-agent here, and do they both hold, or just one?" An AI that jumps to a tidy three-box diagram without naming which of Chapter 9's or Chapter 10's own tests apply -- or worse, applies both without checking either -- has skipped the characterization step this chapter's own Section 6 insists on doing explicitly.

prompt_for_capstone_review.txt
"Here is my multi-component problem: [paste it]. Before proposing an
architecture, state separately whether (a) the components have
distinct, specialized subtasks that can run independently, and (b)
whether any two components act concurrently on the SAME shared
resource. Name which of (a)/(b) hold, with the specific fact for
each. Then, for every one of Chapters 4-11's mechanisms, name the
ONE fact that makes it load-bearing or not. Then show me the code
that PROVES your claim about the shared resource, not just a
paragraph asserting it's handled safely."

This forces the same two-part characterization Section 6 makes explicit, and -- critically -- demands PROOF for the coordination claim specifically, since that's the single most common place a plausible-sounding AI answer substitutes a confident sentence for a working claim-check.

26. Points to remember -- and the course's own closing note

  • An L4 Architecture Challenge differs from L3 in KIND, not just size: it has to plausibly need genuine multi-agent coordination, not just a bigger single-agent problem.
  • Chapter 9's dispatch justification (distinct, independently-runnable subtasks) and Chapter 10's coordination justification (concurrent independent actors on shared state) are SEPARATE facts -- a real system can need one, the other, both, or neither, and an architect has to check both, not stop at the first that fires.
  • A capstone that exercises every mechanism Chapters 1-11 built, on one system, proves the decision framework composes -- not just that it works on easy, mostly-independent worked examples.
  • "Defending" a design means proving each load-bearing mechanism with real, executed code -- a claim-check that actually races two concurrent claims, a memory store that actually survives a separate process, a guardrail that actually blocks by default -- not asserting the design is safe in prose.
  • This chapter imported Chapter 12's five framework functions unchanged, the third reuse of the same functions in this course (after Chapter 12's own exercises and Module 6's own assessment) -- a real architecture practice reuses its own decision tools, it doesn't reinvent them per project.
  • This chapter deliberately ran no live model call, for the same reason Chapter 12 did not: the skill being exercised is architecture judgment and proof-of-design against written facts, not a model's live behavior.
