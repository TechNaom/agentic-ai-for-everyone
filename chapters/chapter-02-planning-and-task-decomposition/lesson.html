Planning and Task Decomposition

Chapter 1's agent already planned — one step at a time, invisibly, buried inside each reasoning call. This chapter pulls planning out into its own visible, inspectable step, and shows two genuinely different ways to do it: decide the whole sequence up front, or decide only the next step and let each observation reshape what comes after. Neither is "better" in general. This chapter builds both, runs both against the same fictional firm, and shows a real case where each wins.

Alderleaf Research Group is a boutique market-research firm. Its analysts ask its agent, ScoutBot, two very different kinds of question. The first: "build a company snapshot for Brightwave Robotics" — profile, financials, news, competitors, always the same four sections, always in the same order. The second: "why did Brightwave Robotics' stock drop this week?" — a question where the right thing to check second depends entirely on what the news headlines say in step one. Chapter 1's run_agent() would handle both requests the same way: one tool-call decision per model turn, never looking further than one step ahead. That works, but it hides something worth seeing directly — that these two tasks have fundamentally different shapes, and a builder who can tell the difference writes a cheaper, more predictable agent for the first kind and a more adaptive one for the second.

1. Why planning needs to become visible

Chapter 1's loop never asked "what's the plan?" as its own question. Every iteration, the model looked at the conversation so far and picked the single next tool call — correct behavior, but the "plan" (such as it was) only ever existed one step at a time, invisible until you'd already run the whole loop and looked back at the trace. That's emergent planning, and it's exactly what this chapter's Section 7 names and keeps, because it's often the right choice. What Chapter 1 never built is the other option: asking the model to commit to a complete ordered sequence of steps before any of them run, so the plan is a real, inspectable object — a list you can print, log, review, and hand to a colleague before a single tool executes.

What is... a plan, as a first-class object? A list of steps — each naming a tool and its arguments — produced by one reasoning step, before execution starts, and (unlike Chapter 1's implicit per-turn choice) inspectable on its own, separately from the loop that will eventually run it.

This chapter does not re-teach the perception/reasoning/action/observation mechanics from Chapter 1 — the tools, the loop shape, the guard, the timeout wrapper all carry forward unchanged. What's new is the planning step itself: making it explicit, choosing between two real strategies for it, and knowing which strategy a given task actually calls for.

The first, tempting way to produce this list in production is a system prompt that just asks the model to describe the whole sequence as free-text JSON. Tested for real this session, that approach failed outright — asked to plan without the real tools= schema attached, the model invented plausible-sounding tool names ("CAD", "Materials Database", "Bill of Materials (BOM)") that don't exist anywhere in ScoutBot's actual four tools. Free text has nothing grounding it to what's real.

What is... the actual fix for this? Ground the plan in the same tools=TOOLS mechanism Chapter 1 already used for single-step tool calls. A model can return more than one tool call in a single turn's tool_calls list — that list, all decided in one reasoning call before any of them execute, is the fixed plan, and every entry is guaranteed to name a real tool because the API constrains it to the schema, not free text.

What's actually new here vs. Chapter 1
Chapter 1's model only ever returned one tool call per turn, because nothing asked it for more. Here, the same tools=TOOLS mechanism returns four tool calls in a single turn's tool_calls list — that whole list, decided before any of them execute, is the fixed plan. One reasoning call replaces what would otherwise be one call per step, the cost trade-off Section 9 measures directly.
The free-text failure was worth keeping, not hiding
The invented tool names above are a genuine, unscripted result from this session, not a manufactured cautionary tale — and they make the point sharper than a clean first-try success would have: a well-worded planning prompt is not enough on its own. What actually grounds a plan in reality is the same tool-calling API contract from Chapter 1, applied to get several calls back at once instead of one.

5. Executing a fixed plan

Once the plan exists as data, running it needs no further reasoning calls at all — just a loop over the list, executing each step and collecting results:

fixed_plan.py (continued)
TOOL_IMPLS = {
    "get_company_profile": get_company_profile,
    "get_financial_snapshot": get_financial_snapshot,
    "get_recent_news": get_recent_news,
    "get_competitor_list": get_competitor_list,
}

def assemble_report(company_name, sections):
    lines = [f"Company Snapshot: {company_name}", "=" * 40]
    for name, result in sections.items():
        lines.append(f"[{name}] {result}")
    return "\n".join(lines)

def run_fixed_plan(company_name, plan):
    sections = {}
    trace = []
    for item in plan:
        fn = TOOL_IMPLS[item["tool"]]
        result = fn(**item["args"])
        trace.append((item["step"], item["tool"], result))
        if "error" in result:
            print(f"[step {item['step']}] FAILED: {item['tool']} -> {result} -- re-planning needed")
            return None, trace
        sections[item["tool"]] = result
        print(f"[step {item['step']}] {item['tool']}({item['args']}) -> {result}")
    return assemble_report(company_name, sections), trace

Re-planning is not the same as emergent planning
The whole plan is still decided up front, both times — the plan just gets thrown out and rebuilt wholesale on failure, rather than adjusted one step at a time. Re-planning is a fixed-plan agent's answer to "the world didn't match my assumptions"; it's still fundamentally different from never having committed to a full plan in the first place, which is Section 7's subject.

7. Emergent planning: one step at a time

For the investigation request, committing to a full plan up front doesn't make sense — there's no way to know in advance whether step 2 should check financials, check the company profile, or check competitors, because that depends on what step 1's headlines say. The right shape here is what Chapter 1's loop already did implicitly: decide only the next step, act, observe, then decide the next next step.

emergent.py
def decide_next_step(company_name, history):
    """
    The reasoning step, made explicit: decide the SINGLE next action
    based on everything observed so far. Never looks more than one step
    ahead -- exactly what Chapter 1's run_agent() did inside each model
    call, written out here so the decision is visible on its own.
    """
    if not history:
        return {"tool": "get_recent_news", "args": {"company_name": company_name}}
    last_tool, last_args, last_result = history[-1]
    if last_tool == "get_recent_news":
        headlines = " ".join(last_result.get("headlines", [])).lower()
        if "resign" in headlines or "ceo" in headlines:
            return {"tool": "get_company_profile", "args": {"company_name": company_name}}
        if "earnings" in headlines:
            return {"tool": "get_financial_snapshot", "args": {"company_name": company_name}}
        return {"tool": "get_competitor_list", "args": {"company_name": company_name}}
    return None  # enough evidence -- stop
What is... "reasoning" doing here, deterministically? In a real deployment, decide_next_step is the model itself, called once per turn with the conversation so far — exactly Chapter 1's chat.completions.create(..., tools=TOOLS) pattern. It's written as a deterministic function here so the specific branch taken (news mentions "resign" → check the profile next) is guaranteed reproducible for this lesson, the same testability reason Chapter 1's guard demo used a FakeMessage stand-in rather than hoping a live model behaved a certain way on every run.

The loop that drives it, structurally identical to Chapter 1's run_agent(), renamed to make the emergent framing explicit:

emergent.py (continued)
def run_emergent_investigation(company_name, max_iterations=4):
    history = []
    for i in range(1, max_iterations + 1):
        step = decide_next_step(company_name, history)
        if step is None:
            print(f"[iteration {i}] enough evidence gathered -- stopping")
            break
        fn = TOOL_IMPLS[step["tool"]]
        result = fn(**step["args"])
        print(f"[iteration {i}] reasoned next step: {step['tool']}({step['args']}) -> observation: {result}")
        history.append((step["tool"], step["args"], result))
    return history

9. Head to head: call counts and adaptability

Running the snapshot task (Sections 4-5's home turf) the emergent way instead, one reasoning call per step:

compare.py
def decide_next_snapshot_step(company_name, history):
    tools_called = [h[0] for h in history]
    order = ["get_company_profile", "get_financial_snapshot", "get_recent_news", "get_competitor_list"]
    for tool in order:
        if tool not in tools_called:
            return {"tool": tool, "args": {"company_name": company_name}}
    return None

def run_emergent_snapshot(company_name, max_iterations=6):
    history, reasoning_calls = [], 0
    for i in range(1, max_iterations + 1):
        reasoning_calls += 1  # every iteration is its own "ask what's next" call
        step = decide_next_snapshot_step(company_name, history)
        if step is None:
            break
        fn = TOOL_IMPLS[step["tool"]]
        result = fn(**step["args"])
        history.append((step["tool"], step["args"], result))
    return history, reasoning_calls

hist, calls = run_emergent_snapshot("Brightwave Robotics")
print(f"Emergent-style snapshot: {calls} reasoning calls for a task whose order never varies.")
print("Fixed-plan snapshot: 1 reasoning call (the plan itself), 0 more between the 4 executions.")
Output (real)

Fixed-plan snapshot: 1 reasoning call (the plan itself), 0 more between the 4 executions.

Five model calls versus one, for identical tool executions and an identical final report. That gap is Section 8's subject of Chapter 8 in miniature (cost and latency control) — and it only shows up because the snapshot task's steps never actually depended on each other, so the extra four reasoning calls bought nothing.

10. A case where fixed planning wins

The snapshot task is that case, made precise: every section is needed regardless of what any other section returns, so there is nothing for a per-step reasoning call to adapt to. Four extra reasoning calls (Section 9) with zero behavioral difference in the tool sequence or the output is the signature of a task where fixed planning is strictly better — same result, a fifth of the reasoning cost, and a plan you can review and log before anything executes.

What is... the tell that a task wants a fixed plan? If you can write the full step sequence down correctly without running any of it first — and running it wouldn't change what you'd write — the task's steps are order-independent-of-outcome. That's a fixed-plan task, whether or not a human or a model produces the list.

11. A case where emergent planning wins

Now the reverse: pre-committing a fixed, two-step plan for the investigation task, decided before step 1's result is known:

wrong_fixed_plan.py
PRECOMMITTED_INVESTIGATION_PLAN = [
    {"step": 1, "tool": "get_recent_news", "args": {"company_name": "Brightwave Robotics"}},
    {"step": 2, "tool": "get_financial_snapshot", "args": {"company_name": "Brightwave Robotics"}},  # guessed
]
for item in PRECOMMITTED_INVESTIGATION_PLAN:
    fn = TOOL_IMPLS[item["tool"]]
    result = fn(**item["args"])
    print(f"[fixed step {item['step']}] {item['tool']} -> {result}")
Output (real) 
[fixed step 1] get_recent_news -> {'headlines': ['CEO Dana Ferris resigns effective immediately', 'Q2 earnings beat expectations']}
[fixed step 2] get_financial_snapshot -> {'stock_price': 41.2, 'weekly_change_pct': -12.4, 'revenue_m': 340}

Step 2 was locked in before step 1's headlines were known, and it guessed wrong: the headlines named a CEO resignation, not an earnings story, so the financial snapshot doesn't explain the stock drop at all. The correct step 2 (get_company_profile, per Section 8's real emergent run) was only knowable after seeing step 1's result — which is exactly what a fixed, up-front plan structurally cannot do.

This isn't a wrong-argument or hallucination failure
Both tool calls succeeded and returned real data — this is a wrong-plan failure, a new failure class this chapter introduces: the right tool to call next was knowable only from information the plan was built without. Re-planning (Section 6) could recover from this after noticing the mismatch, but emergent planning never makes the wrong commitment in the first place.

12. A decision heuristic: fixed vs. emergent

Sections 10-11 generalize into two yes/no questions a builder can ask about any task before writing the agent:

heuristic.py
def classify_planning_mode(task_description, steps_known_in_advance, later_steps_depend_on_earlier_results):
    if later_steps_depend_on_earlier_results:
        return "emergent"
    if steps_known_in_advance:
        return "fixed"
    return "emergent"  # default when steps aren't knowable up front either

cases = [
    ("Company snapshot report", True, False),
    ("Stock-drop investigation", False, True),
    ("New contractor onboarding checklist", True, False),
    ("Root-cause triage of a customer complaint", False, True),
]
for desc, known, depends in cases:
    print(desc, "->", classify_planning_mode(desc, known, depends))
Output (real) 
Company snapshot report -> fixed
Stock-drop investigation -> emergent
New contractor onboarding checklist -> fixed
Root-cause triage of a customer complaint -> emergent
What is... the actual decision rule, in one sentence? If a later step's correct choice can only be known after seeing an earlier step's real result, plan emergently; if the full sequence can be written correctly without running anything first, plan it fixed and save the reasoning calls.

13. Guardrails for re-planning

Chapter 1's max_iterations guard bounded a loop that might never stop calling tools. A fixed-plan agent that re-plans on every failure (Section 6) has the same unbounded-retry shape if nothing caps how many times it's allowed to throw the plan out and start over — so it needs its own bound, max_replans, built the same way:

guard_replan.py
def run_fixed_plan_with_replan_guard(company_name, plan, correction=None, max_replans=2):
    attempts = 0
    current_plan, current_name = plan, company_name
    while attempts <= max_replans:
        report, trace = run_fixed_plan(current_name, current_plan)
        if report is not None:
            return report, attempts
        attempts += 1
        if attempts > max_replans:
            print(f"[guard] hit max_replans={max_replans} -- giving up, returning to a human")
            return None, attempts
        if correction is None:
            print(f"[guard] no correction available -- stopping after {attempts} attempt(s)")
            return None, attempts
        print(f"[re-plan attempt {attempts}] trying corrected name '{correction}'")
        current_name = correction
        current_plan = [dict(item, args={"company_name": correction}) for item in plan]
    return None, attempts

Same guarantee, same limits, as Chapter 1's guard
max_replans guarantees the re-planning loop halts. It does not decide what correction to try — that's a separate concern (a real system might call a fuzzy-match lookup, ask a human, or give up immediately). And exactly like max_iterations, it says nothing about whether any side-effecting tool call made during those attempts was safe; Chapter 6 is still where the fuller guardrail set lives.

14. The finished dual-mode PlanBot

Both strategies, assembled into one file ScoutBot would actually run — fixed planning for the snapshot report, emergent planning for the investigation, sharing the same four tools:

planbot_agent.py
import json

COMPANY_PROFILES = {"brightwave robotics": {"sector": "industrial automation", "hq": "Portland, OR", "founded": 2014}}
FINANCIALS = {"brightwave robotics": {"stock_price": 41.20, "weekly_change_pct": -12.4, "revenue_m": 340}}
NEWS = {"brightwave robotics": ["CEO Dana Ferris resigns effective immediately", "Q2 earnings beat expectations"]}
COMPETITORS = {"brightwave robotics": ["Meridian Automation", "Coreflow Systems"]}

def get_company_profile(name):
    return COMPANY_PROFILES.get(name.strip().lower(), {"error": f"no profile for '{name}'"})
def get_financial_snapshot(name):
    return FINANCIALS.get(name.strip().lower(), {"error": f"no financials for '{name}'"})
def get_recent_news(name):
    k = name.strip().lower()
    return {"headlines": NEWS[k]} if k in NEWS else {"error": f"no news for '{name}'"}
def get_competitor_list(name):
    k = name.strip().lower()
    return {"competitors": COMPETITORS[k]} if k in COMPETITORS else {"error": f"no competitors for '{name}'"}

TOOL_IMPLS = {"get_company_profile": get_company_profile, "get_financial_snapshot": get_financial_snapshot,
              "get_recent_news": get_recent_news, "get_competitor_list": get_competitor_list}
FIXED_SNAPSHOT_ORDER = ["get_company_profile", "get_financial_snapshot", "get_recent_news", "get_competitor_list"]

def run_fixed_snapshot(company_name, max_replans=2, correction=None):
    name = company_name
    for attempt in range(max_replans + 1):
        sections, failed = {}, False
        for tool_name in FIXED_SNAPSHOT_ORDER:
            result = TOOL_IMPLS[tool_name](name)
            if "error" in result:
                failed = True
                break
            sections[tool_name] = result
        if not failed:
            return sections, attempt
        if correction is None or attempt >= max_replans:
            return None, attempt
        name = correction
    return None, max_replans

def decide_next_investigation_step(history):
    if not history:
        return "get_recent_news"
    last_tool, last_result = history[-1]
    if last_tool == "get_recent_news":
        headlines = " ".join(last_result.get("headlines", [])).lower()
        if "resign" in headlines or "ceo" in headlines:
            return "get_company_profile"
        if "earnings" in headlines:
            return "get_financial_snapshot"
        return "get_competitor_list"
    return None

def run_emergent_investigation(company_name, max_iterations=4):
    history = []
    for _ in range(max_iterations):
        next_tool = decide_next_investigation_step(history)
        if next_tool is None:
            break
        result = TOOL_IMPLS[next_tool](company_name)
        history.append((next_tool, result))
    return history

if __name__ == "__main__":
    sections, replans = run_fixed_snapshot("Brightwave Robotics")
    print(f"FIXED-PLAN snapshot ({replans} re-plans needed):")
    for name, result in sections.items():
        print(f"  {name}: {result}")
    print()
    history = run_emergent_investigation("Brightwave Robotics")
    print(f"EMERGENT investigation ({len(history)} adaptive steps):")
    for name, result in history:
        print(f"  {name}: {result}")

15. GenAI Builder Thought Process

Thought process: the natural first instinct when a task needs "planning" is to reach for a single, general-purpose planner and use it everywhere — but Sections 9-11 show that's a real cost, not a neutral default: applying fixed planning to an emergent task locks in wrong steps, and applying emergent planning to a fixed task burns four extra reasoning calls for identical output. The discipline this chapter teaches isn't "always plan up front" or "always plan step by step" — it's asking Section 12's one question (does a later step's correct choice depend on an earlier step's real result?) before choosing either. A strong prompt for an AI pair-programmer extending this chapter's agent: "I have two tasks against the same four tools: Task A needs every tool called once, in a fixed order that never changes. Task B needs only some tools, and which ones depends on what an earlier tool call returns. Write a fixed-plan executor for Task A that builds the full step list before executing anything, and a separate one-step-at-a-time emergent loop for Task B that decides its next tool call only after seeing the previous result. Do not use an agent framework — plain Python and, where a real reasoning step is needed, the openai client against local Ollama."

In the Real World
  • Coding agents plan emergently almost by necessity: a fix's next step depends entirely on what the previous edit's test run revealed. A CI/CD deployment agent, by contrast, often plans fixed: build, test, stage, promote — the same four steps every time, worth writing down once and reusing.
  • The wrong-plan failure in Section 11 (both tool calls succeeded, the plan itself was still wrong) is easy to miss in a production trace precisely because nothing errored — it only shows up when someone checks whether the final answer actually addressed the question asked.
  • max_replans is the planning-layer sibling of Chapter 1's max_iterations — the same discipline (bound anything that might retry) applied one layer up, at the level of whole plans instead of single tool calls.

Points to Remember

  • A fixed, up-front plan is a full ordered list of steps decided in one reasoning call before any tool executes; an emergent plan decides only the single next step, repeatedly, after seeing each observation — exactly what Chapter 1's loop already did implicitly.
  • The decision rule: if a later step's correct choice can only be known after seeing an earlier step's real result, plan emergently; if the full sequence can be written correctly without running anything first, plan it fixed and save the reasoning calls.
  • A fixed plan costs one reasoning call regardless of step count; an emergent loop costs roughly one reasoning call per step. This chapter measured a real 5-to-1 gap on a task where that extra cost bought nothing.
  • A wrong-plan failure (every tool call succeeds, but the plan itself locked in the wrong step before an earlier result was known) is a distinct failure class from Chapter 1's wrong-tool-choice or wrong-argument failures — and it is exactly the failure mode a fixed plan is structurally exposed to that emergent planning avoids.
  • Re-planning (rebuilding a fixed plan wholesale after a step fails) is not the same thing as emergent planning (never committing to a full plan at all) — both are legitimate, but they solve different problems and need their own guard (max_replans), the same discipline as Chapter 1's max_iterations applied one layer up.
  • No agent framework was used anywhere in this chapter — both planning strategies are plain Python and, where a live reasoning step is needed, the plain openai client against local Ollama.
