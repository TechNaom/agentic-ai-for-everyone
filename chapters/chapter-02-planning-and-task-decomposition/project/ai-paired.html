Chapter 2 Project — Solo → AI-Paired → Critique 20 min

Now Pair With an AI

You already built RouteBot's fixed-plan-with-re-planning executor yourself. Now try the reverse: describe the same task to an AI assistant without showing it your own solution, and review what it hands back with the same scrutiny you'd bring to a teammate's pull request before merging it into Cobblestone Courier Co.'s real dispatch system.

Step 1: Have the AI build it independently

Thought process: the prompt needs to specify the re-planning behavior explicitly and concretely (what triggers a re-plan, what happens when the correction also fails, what the return value should be when nothing recovers it) or the AI is likely to produce a function that "mostly works" on the happy path but handles the exhausted-guard case ambiguously — exactly the class of gap this exercise is designed to surface.

Write the prompt you'd give an AI assistant:

Paste your prompt into your assistant of choice, save its response separately, and compare it against the checklist below before looking at this project's own solution.py.
Show a strong version of this prompt 
Write a Python function run_fixed_dispatch(order_id, max_replans=2, correction=None) implementing a fixed-plan executor with a re-planning guard. It runs three steps in order -- verify_delivery_address(order_id), calculate_route(order_id), dispatch_driver(order_id) -- each from a TOOL_IMPLS dict, each returning a dict that may contain an "error" key on failure. If all three succeed, return (a dict of {tool_name: result}, the attempt number used). If any step fails: if `correction` is not None and the attempt count hasn't reached max_replans, rebuild the WHOLE plan using `correction` as the new order_id and retry from step 1. If correction is None, or max_replans is exhausted, return (None, attempt_number) and stop -- do not retry forever. Do not use any agent framework.

Step 2: Review it against this checklist

What a rushed AI-generated re-planning loop tends to get wrong
  • Retrying a partial plan instead of the whole plan. A common mistake is resuming from the step that failed rather than rebuilding the full three-step sequence from the corrected order_id — check whether the generated code re-runs all three steps on a re-plan, the same "whole plan gets thrown out and rebuilt" behavior the lesson's Section 6 insists on.
  • Off-by-one on max_replans. Does exhausting the guard happen after exactly max_replans extra attempts, or one too many/too few? Compare the returned attempt count against the self-check's own Check 2 and Check 3 expectations.
  • Conflating "no correction available" with "correction failed too." These are different situations — the generated code should give up cleanly and immediately when correction is None, without treating that as just another retry-until-max_replans case.

Now compare the AI's code against solution.py in this same folder. Where do they differ? Is the AI's version genuinely equivalent, or does it handle one of the three watch-outs above differently — and is that difference actually a bug, or a legitimate different design choice?
