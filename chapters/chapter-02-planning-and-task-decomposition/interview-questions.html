Chapter 2 Interview Questions ~20 min

Interview Questions: Planning and Task Decomposition

Grouped by level — beginner, intermediate, senior, architect. Each includes a strong answer, a red flag, a follow-up, and what the question actually proves.

1. (Beginner) What's the difference between a fixed, up-front plan and emergent planning?

Strong answer: A fixed plan is a complete ordered list of steps decided in a single reasoning call, before any tool has executed. Emergent planning decides only the single next step, over and over, after seeing each new observation — it never commits to more than one step ahead. Chapter 1's run_agent() already did emergent planning implicitly; this chapter makes the choice between the two explicit.

Red flag: Says one is "smarter" or "more advanced" than the other in general, rather than describing them as suited to different task shapes.

Follow-up: "Which one did Chapter 1's agent use, even though the chapter never called it that?"

What this proves: Understands these as two named strategies, not a single evolving "better" technique.

2. (Beginner) In the lesson, why was a fixed plan the right choice for the company-snapshot task?

Strong answer: Every section (profile, financials, news, competitors) was needed regardless of what any other section returned — nothing about the profile changes whether the financials are worth fetching. Since the full step order could be written correctly without running anything first, planning it up front cost one reasoning call instead of one per step, with an identical result.

Red flag: Says "because there were only four tools" — the tool count isn't the reason; the lack of dependency between the steps is.

Follow-up: "What would have to be true about the four tools for an emergent plan to actually be necessary here?"

What this proves: Locates the real reason for the design choice, not a surface-level correlation.

3. (Beginner) What is a "wrong-plan failure," and how is it different from a wrong-argument failure?

Strong answer: A wrong-argument failure (Chapter 1) is a correct tool called with a mismatched argument. A wrong-plan failure is when every tool call in a fixed plan succeeds — real data comes back for each one — but the plan itself locked in the wrong step before an earlier step's result was actually known, so the sequence as a whole doesn't answer the question. Nothing errors; the final answer is just built from the wrong evidence.

Red flag: Conflates it with a tool-execution failure, since no error message ever appears in this failure mode.

Follow-up: "How would you even notice a wrong-plan failure in a production log, if nothing threw an error?"

What this proves: Recognizes that a "successful" trace can still represent a wrong plan.

4. (Intermediate) Walk through the lesson's investigation example and explain why a fixed plan would have failed it.

Strong answer: The task was "why did the stock drop." Step 1 (check the news) revealed a CEO resignation. The correct step 2 (check the company profile) was only knowable after reading that headline — a fixed plan built before step 1 ran would have had to guess step 2, and the lesson's own pre-committed guess (check financials) turned out wrong, since the real story was leadership, not earnings.

Red flag: Describes the failure as "the tool didn't work" rather than "the plan committed to the wrong step before it had the information to make that choice."

Follow-up: "Could re-planning after step 2 have caught this? What would it need to notice?"

What this proves: Can trace a plan-level failure back to when the information that would have prevented it became available.

5. (Intermediate) What does max_replans guard against, and how is it different from max_iterations?

Strong answer: max_iterations (Chapter 1) bounds how many times a loop can call a tool and reason again before giving up. max_replans bounds how many times a fixed plan can be thrown out wholesale and rebuilt from scratch after a step fails — a different unit of retry (whole plans, not individual steps), but the same discipline: without it, a persistent failure with an available-looking correction could retry indefinitely.

Red flag: Treats them as interchangeable or redundant.

Follow-up: "Could a system need both guards active in the same run? Sketch when."

What this proves: Distinguishes guard scope (step-level vs. plan-level) rather than treating "guardrail" as one undifferentiated concept.

6. (Intermediate) The lesson measured 5 reasoning calls for an emergent-style snapshot versus 1 for a fixed plan. Is that gap always this large?

Strong answer: No — it scales with the number of steps in the task. A fixed plan always costs one reasoning call regardless of step count; an emergent loop costs roughly one call per step (plus one to recognize it's done). A two-step task would show a much smaller gap than the four-step snapshot did; a twenty-step task would show a much larger one. The lesson's 5-to-1 ratio is this specific task's number, not a universal constant.

Red flag: Quotes "5x cheaper" as if it were a fixed, general property of fixed planning.

Follow-up: "At what step count would the emergent version's reasoning-call cost roughly equal the fixed plan's savings from avoiding one wrong-plan failure?"

What this proves: Reasons about the cost trade-off quantitatively instead of repeating a memorized number.

7. (Senior) A team wants one universal planning strategy for their whole agent platform, to keep the codebase simple. How do you respond?

Strong answer: That trades correctness or cost for uniformity in whichever direction is wrong for at least some of their tasks — this chapter showed both failure directions concretely: forcing an emergent task into a fixed plan produces wrong-plan failures (Section 11), and forcing a fixed-shaped task through emergent planning burns reasoning calls for no behavioral benefit (Section 9). The right invariant isn't "one strategy" — it's a shared interface (both strategies use the same tools and the same result shape) with the strategy itself chosen per task type, ideally by the heuristic in Section 12.

Red flag: Picks a single "safe default" strategy for everything without acknowledging the cost on the other task type.

Follow-up: "Could the same agent switch strategies mid-task? What would trigger that?"

What this proves: Pushes back on false simplicity when it costs real correctness or real money.

8. (Senior) How would you detect a wrong-plan failure in production, given that no tool call errors?

Strong answer: Since nothing throws, detection has to happen at the outcome level, not the execution level: does the final answer actually address what was asked, evaluated either by a held-out rubric, a reflection/self-check step (Chapter 5's subject), or human spot review of a sample of traces. Logging the plan itself as a first-class, inspectable object (this chapter's whole point in Section 1) is a precondition for this — you can't review a plan for correctness if it was never written down anywhere.

Red flag: Assumes tool-level success monitoring alone would catch this class of failure.

Follow-up: "What would you log about a fixed plan, specifically, to make a wrong-plan failure reviewable after the fact?"

What this proves: Understands that observability for planning failures needs a different signal than observability for execution failures.

9. (Senior) When is re-planning (Section 6) the right fix, versus switching the whole task to emergent planning?

Strong answer: Re-planning is the right fix when the plan's shape was right and only an input was wrong — the Section 6 example, where correcting one argument and re-running the same four steps fixed it completely. Switching to emergent planning is the right fix when the plan's shape itself was wrong — when a genuinely different step, not just a corrected argument, was needed, which is what Section 11's example showed. Diagnosing which one you're looking at (bad input vs. bad plan) determines which fix actually applies.

Red flag: Treats re-planning as a general-purpose fix for any planning failure.

Follow-up: "Could a single system implement max_replans retries that fall back to emergent planning once the limit is hit?"

What this proves: Diagnoses precisely enough to choose between two genuinely different remedies, not just "try again."

10. (Architect) Design a rule your team could use, before writing any agent code, to decide whether a new task needs fixed or emergent planning.

Strong answer: Ask one question up front: can the full, correct step sequence be written down without executing anything first, and would executing it not change what you'd have written? If yes, plan it fixed — the cost savings (Section 9) are real and the risk of a wrong-plan failure (Section 11) is near zero, since nothing about the sequence depends on unknown results. If no — if any later step's correct identity depends on an earlier step's actual result — plan it emergently, since a fixed plan there is structurally exposed to wrong-plan failures no amount of re-planning after the fact fully prevents. This should be a one-time design decision per task category, not a per-run coin flip, since a task category's shape (dependent or not) doesn't usually change run to run.

Red flag: Proposes a rule based on task complexity, tool count, or "how important" the task is, rather than the actual dependency structure between steps.

Follow-up: "How would you handle a task category that's usually fixed-shaped but occasionally needs one adaptive step in the middle?"

What this proves: Can generalize this chapter's two worked examples into a reusable design principle, not just recall the two examples themselves.
