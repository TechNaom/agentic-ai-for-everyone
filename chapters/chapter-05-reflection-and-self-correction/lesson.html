Reflection and Self-Correction

Chapters 1-4 built an agent that reasons, calls tools, recovers from tool failure, and carries state across sessions. Every one of those agents still does the exact same thing on its very first draft: it returns it. Nothing in this course so far checks a response against anything before handing it back. This chapter adds that missing check — reflection: a second, genuinely separate step that evaluates a draft response against a standard (correctness, completeness, policy compliance) and revises it before it's returned, as a designed architectural component, not the model "trying harder" inside one bigger prompt. Advanced tier, opening Module 3 — everything below is demonstrated for real this chapter: two genuine live-model failures this session did not script, a deterministic verifier that catches what a live self-critique call missed, and a real before/after correction applied to Chapter 4's own CareBot project.

Briarcliff Bike Rentals is a fictional bike rental shop. Its rental assistant, BikeBot, answers customer questions about price and eligibility: standard bikes are $8/hour with no age minimum, electric bikes are $15/hour and require the renter to be at least 16. A customer asks a two-part question — is this allowed, and how much would it cost — and BikeBot has to get both parts right, every time, with real money and real policy on the line. This chapter runs BikeBot's own draft responses through a real local model, catches a real failure this session did not script, and builds the architectural layer that catches it: a second, distinct step that checks a draft against the actual rate card and the actual policy before it's ever shown to a customer.

1. What reflection actually is, defined against Chapters 1-4

Every agent this course has built so far ends the same way: the model produces something, and that something is returned. Chapter 1's run_agent() loop keeps going until the model stops calling tools, then returns its last message. Chapter 3 adds retry-on-failure for a tool call that errors. Chapter 4 adds memory so a later session can pick up where an earlier one left off. None of that checks whether the model's own final answer is actually right.

What is... reflection? A second, deliberately separate step that evaluates a draft response (or draft action) against some standard — correctness, completeness, policy compliance — after a first pass has already produced it, and revises it if the standard isn't met. The key word is separate: reflection is not the model "thinking harder" inside one bigger prompt, and it is not re-asking the same question and hoping a different answer comes back (Section 9 shows exactly why that fails). It's an explicit, testable check with its own inputs, its own pass/fail criteria, and its own decision about whether to revise.
What is... NOT reflection? A bigger, more careful-sounding system prompt ("think step by step and double-check your work") is not reflection — it's still one pass, with no separate step that can independently catch what that one pass got wrong. Neither is re-running the identical prompt a second time hoping randomness produces a better answer (Section 9). Reflection requires a second, distinct evaluation against a standard, not just more effort spent on the first one.

This chapter reuses Chapters 1-3's tool-calling and Chapter 4's memory mechanics without re-teaching them — BikeBot doesn't need tools or persisted memory to demonstrate reflection cleanly, so this chapter keeps it simple on purpose: one draft, one check, one possible revision.

The real, unscripted failure here
The policy half is correct — BikeBot correctly refuses the electric-bike rental for a 15-year-old. Nothing in Chapters 1-4's own mechanisms would catch this — the loop ended, the model stopped calling tools (there are none here), and the response was returned as-is.

4. A minimal, grounded reflection step

The fix isn't a better prompt — it's a second, separate function that re-derives the correct facts independently of whatever the draft says, then compares:

bikebot_core.py
import re

def check_policy(bike_type, age):
    violations = []
    if bike_type == "electric" and age < MIN_AGE_ELECTRIC:
        violations.append(f"electric bikes require the renter to be at least {MIN_AGE_ELECTRIC}; this renter is {age}")
    return violations

def extract_dollar_amount(text):
    # Take the LAST dollar figure in the text, not the first -- a draft
    # often states a per-hour rate before it states the actual total, and
    # an earlier version of this function used re.search() (first match)
    # and misread "$8/hour x 7 hours = $56" as claiming $8, a real bug
    # caught while testing Section 6's own draft against this function.
    matches = re.findall(r"\$(\d+(?:\.\d{1,2})?)", text)
    return float(matches[-1]) if matches else None

def verify_draft(draft_text, bike_type, hours, age):
    correct_price = compute_price(bike_type, hours)
    violations = check_policy(bike_type, age)
    stated_price = extract_dollar_amount(draft_text)
    problems = []
    if stated_price is None:
        problems.append("draft doesn't state a clear dollar amount")
    elif stated_price != correct_price:
        problems.append(f"draft states ${stated_price}, correct price is ${correct_price}")
    return {"correct_price": correct_price, "violations": violations, "problems": problems}
What is... "grounded" about this check? verify_draft() never reads the draft's own claimed price and trusts it — it independently recomputes correct_price from RATE_CARD and hours, the same way it would whether or not a draft existed at all, and only then compares. This is the difference this chapter's Section 12 will show mattering: a check grounded in real, independently-derived facts catches things a model reviewing its own words in isolation can miss.

Run against BikeBot's own real Section 3 draft:

check_section3_draft.py
draft = "I'm afraid we can't allow a 15-year-old to rent an electric bike... Would you like me to calculate the total cost for a 3-hour rental on a standard bike?"
print(verify_draft(draft, "standard", 3, 15))
Output (real) 
{'correct_price': 24, 'violations': [], 'problems': ["draft doesn't state a clear dollar amount"]}

Exactly the real gap Section 3 identified by reading it — now caught by code, not by a human noticing.

5. Applying it: catching a real arithmetic error

The Section 3 draft had an incomplete-answer problem, not a math error — an honest result, not manufactured. To show the verifier catching the other named failure class (an actual wrong number), this section uses a deliberately-naive deterministic draft generator — clearly labeled as such, not disguised as a live call — the same "naive baseline" technique Chapter 4's Section 3 used for its own no-memory failure:

naive_draft.py
def draft_response(bike_type, hours, age):
    """Deliberately naive: always states a price, one dollar short of correct."""
    wrong_price = compute_price(bike_type, hours) - 1
    return f"That'll be ${wrong_price} total for {hours} hour(s) on a {bike_type} bike. Enjoy your ride!"

draft = draft_response("standard", 5, 30)
print(draft)
print(verify_draft(draft, "standard", 5, 30))
Output (real) 
That'll be $39 total for 5 hour(s) on a standard bike. Enjoy your ride!
{'correct_price': 40, 'violations': [], 'problems': ["draft states $39.0, correct price is $40"]}

Now the revise half — the verifier found exactly one problem, so the correction rewrites only what was wrong:

revise_price.py
def revise_for_price(draft_text, bike_type, hours):
    correct_price = compute_price(bike_type, hours)
    return f"Corrected: ${correct_price} total for {hours} hour(s) on a {bike_type} bike."

result = verify_draft(draft, "standard", 5, 30)
if result["problems"]:
    revised = revise_for_price(draft, "standard", 5)
    print("BEFORE:", draft)
    print("AFTER: ", revised)
Output (real) 
BEFORE: That'll be $39 total for 5 hour(s) on a standard bike. Enjoy your ride!
AFTER:  Corrected: $40 total for 5 hour(s) on a standard bike.

8. Two kinds of self-correction: revise vs. gather more evidence

Every example so far revises the text of a response. That's one kind of self-correction. The other kind — genuinely different, not a smaller version of the same thing — is deciding the draft can't be fixed by rewording at all, and a different tool or more information is needed first:

What is... revise-the-answer correction? Reflection determines the draft's core facts or wording are wrong, and rewrites the response using facts it already has access to — Section 5's price correction, Section 14's CareBot correction. No new information is gathered; the fix is entirely in how the existing facts are stated.
What is... gather-more-evidence correction? Reflection determines the draft is unreliable not because it worded something wrong, but because it never had the right information to answer at all — and the fix is calling a different tool, or the same tool with different arguments, not rewording. This is the same category of decision Chapter 3's tool-selection material covered, but reflection is what triggers that decision after a draft already exists, rather than before one is attempted.
correction_kind.py
def classify_correction_kind(problem_description):
    text = problem_description.lower()
    if "wrong number" in text or "wrong price" in text or "incomplete" in text or "policy" in text:
        return "revise-the-answer correction"
    if "no data" in text or "doesn't know" in text or "needs to look up" in text or "unavailable slot" in text:
        return "gather-more-evidence correction"
    return "unclear -- needs a human to classify"

print(classify_correction_kind("draft states the wrong price"))
print(classify_correction_kind("draft assumes a bike model that isn't in the rate card -- BikeBot doesn't know this bike's rate and needs to look up a real rate card entry"))
print(classify_correction_kind("draft recommends an unavailable slot"))
Output (real) 
revise-the-answer correction
gather-more-evidence correction

Every correction in this chapter's own BikeBot and CareBot examples is a revise-the-answer correction — genuinely gathering more evidence (a real second tool call triggered by reflection) is closer to Chapter 3's own tool-selection material than reflection's own core mechanism, so this chapter names the distinction clearly without building a full worked example of the second kind.

9. A real anti-pattern: retry is not reflection

A common mistake, easy to fall into because it looks like reflection from the outside: when a draft is wrong, just re-ask the model the exact same question again and hope a different, better answer comes back by chance. No independent check runs against anything:

retry_not_reflection.py
def fake_reflection_via_retry(bike_type, hours, age, attempts=3):
    """ANTI-PATTERN: re-runs the SAME naive draft generator, with no
    grounded check in between, and just hopes a later attempt is right."""
    results = []
    for i in range(attempts):
        draft = draft_response(bike_type, hours, age)  # naive_draft.py, Section 5
        results.append(draft)
    return results

for d in fake_reflection_via_retry("standard", 5, 30):
    print(d)
Output (real) 
That'll be $39 total for 5 hour(s) on a standard bike. Enjoy your ride!
That'll be $39 total for 5 hour(s) on a standard bike. Enjoy your ride!
That'll be $39 total for 5 hour(s) on a standard bike. Enjoy your ride!
Why this is a demonstrable failure, not a strawman
This deterministic draft generator is a stand-in for a live model call that makes the same class of arithmetic slip on repeated attempts — a real, common outcome, since the same prompt against the same model tends to reproduce the same reasoning error, not a randomly different one. Retrying without a grounded check gets the wrong answer three times instead of once. The fix isn't "try again" — it's Section 4's verify_draft(), which catches the error regardless of how many times the naive draft is regenerated.

10. Bounding reflection iterations

Reflection that revises, checks again, revises again, indefinitely, is Chapter 1's own runaway-loop risk wearing a new outfit — the fix is the same shape as Chapter 1's max_iterations guard, applied to correction attempts instead of tool calls:

bounded_reflect.py
def reflect_on_response(draft_text, bike_type, hours, age, max_reflections=2):
    attempt = draft_text
    for i in range(max_reflections):
        result = verify_draft(attempt, bike_type, hours, age)
        if not result["problems"]:
            return attempt, i, False  # converged -- no escalation needed
        attempt = revise_for_price(attempt, bike_type, hours)
    # Ran out of attempts -- check once more, escalate if still wrong.
    final = verify_draft(attempt, bike_type, hours, age)
    if not final["problems"]:
        return attempt, max_reflections, False
    return "This request needs a human to review before a final answer is given.", max_reflections, True

print(reflect_on_response("That'll be $39 total for 5 hour(s) on a standard bike.", "standard", 5, 30))
Output (real) 
('Corrected: $40 total for 5 hour(s) on a standard bike.', 1, False)
Why the returned attempt count is 1, not 0
The loop checks the current attempt before revising it, so the first iteration (i=0) finds the original wrong draft, revises it, and only the second iteration (i=1) checks the corrected draft and finds it clean — one real revision took two loop passes to confirm, which is exactly the number this function reports. Reading the loop's own return value, not assuming it, is what caught this: an earlier draft of this paragraph claimed 0 here before this session actually ran the code.
What is... the guarantee this bound gives, and what it doesn't? max_reflections guarantees the loop terminates and control returns to something (a caller, a human queue) within a fixed number of attempts — it does not guarantee the draft ends up correct. An adversarial or persistently-wrong draft still gets escalated, not silently returned wrong, which is the entire point: a bounded loop that gives up honestly beats an unbounded one that never returns, and beats a "successful"-looking loop that quietly ships a wrong answer.

11. When reflection should NOT run

Section 6's clean, correct draft didn't need reflection to be correct — but it still ran the check, which cost one extra function call. At scale, across every request, that adds up: this chapter names the trade-off honestly and previews Chapter 8's fuller treatment (cost and latency control), the same "preview, not full treatment" pattern Chapter 4 used for its own token-budget section referencing Chapter 8.

should_reflect.py
def should_reflect(request_kind):
    """A crude, honest first cut: reflect only where a wrong answer has a
    real cost AND a checkable standard exists. Chapter 8 covers a fuller,
    measured version of this trade-off -- this is this chapter's own,
    narrower version of the same idea."""
    HIGH_STAKES_CHECKABLE = {"price_quote", "policy_eligibility", "booking_confirmation"}
    LOW_STAKES_OR_UNCHECKABLE = {"store_hours", "small_talk", "general_faq"}
    if request_kind in HIGH_STAKES_CHECKABLE:
        return True
    if request_kind in LOW_STAKES_OR_UNCHECKABLE:
        return False
    return False  # default to NOT reflecting when unsure -- see cost note below

for kind in ["price_quote", "store_hours", "policy_eligibility", "small_talk"]:
    print(kind, "->", should_reflect(kind))
Output (real) 
price_quote -> True
store_hours -> False
policy_eligibility -> True
small_talk -> False
Why default to NOT reflecting when unsure
Reflection's cost (Section 7's live call took 40.8 seconds; Section 4's deterministic check is near-instant but still extra code to run and maintain) is only worth paying when a wrong answer has a real cost AND there's something concrete to check it against. "What are your hours" has no arithmetic to get wrong and a trivially fixed answer — running a full reflection pass on it, the way this chapter's own practice bank's FormBot scenario does, doubles cost for zero benefit. This is a narrow, honest first cut at the decision, not a general policy — Chapter 8 treats the cost/latency trade-off as its own subject in full.

12. A genuine limit: right diagnosis, wrong fix

Look again at Section 7's own real REVISED text — this is not a hypothetical:

The live critic correctly named the problem and still didn't fix it
Section 7's second model call correctly identified that the draft was incomplete (VERDICT: INCOMPLETE, and the REASON is accurate). But its own REVISED text still never states the actual 3-hour total ($24) — it repeats the per-hour rate ($8) and asks the same deferred question in slightly different words, and verify_draft() correctly reads that lone "$8" as the draft's claimed price, which is wrong for a 3-hour rental. This is a genuine, unscripted result, not a manufactured failure: a live self-critique call diagnosed the right problem class and still failed to guarantee the fix, because nothing forced it to actually compute and state the number. This is exactly why Section 4's grounded, deterministic check exists as a backstop — verify_draft() catches this revised draft's remaining gap immediately, with no ambiguity, because it never trusted the draft's own wording in the first place. A production reflection step that relies solely on a second model call's own say-so, with no grounded check anywhere in the loop, would have shipped this "fixed" draft as complete.

13. Generalizing into reflect_and_revise()

Sections 4-12 generalize into one function combining a grounded price check and a policy check — the same shape Chapter 4's Section 13 used to compose its own memory mechanisms, now composing reflection's:

reflect_and_revise.py
def reflect_and_revise(draft_text, bike_type, hours, age):
    result = verify_draft(draft_text, bike_type, hours, age)
    if not result["problems"] and not result["violations"]:
        return draft_text, False  # nothing wrong -- Section 6's case

    revised = draft_text
    if any("price" in p for p in result["problems"]) or any("dollar amount" in p for p in result["problems"]):
        revised = revise_for_price(revised, bike_type, hours)
    if result["violations"]:
        revised += f" Note: {result['violations'][0]}; this rental cannot proceed as requested."
    return revised, True

print(reflect_and_revise("That'll be $44 total for 3 hour(s) on a electric bike.", "electric", 3, 15))
print(reflect_and_revise("$8/hour x 7 hours = $56. You would owe $56.", "standard", 7, 30))
Output (real) 
('Corrected: $45 total for 3 hour(s) on a electric bike. Note: electric bikes require the renter to be at least 16; this renter is 15; this rental cannot proceed as requested.', True)
('$8/hour x 7 hours = $56. You would owe $56.', False)

One function, one grounded standard, correctly revising the wrong case and correctly leaving the right one untouched.

14. Extending CareBot: a real before/after correction

Chapter 4's own L2 Assisted project (Hollowridge Wellness Clinic's CareBot, in chapters/chapter-04-memory-and-state/project/) shipped reflect_on_response(draft_response, context) as a labeled no-op, wired into run_visit_session() exactly where a real reflection step belongs. This chapter fills that body in for real, applying this exact chapter's mechanism to CareBot's own domain — the concrete proof this chapter's material is genuinely extending the L2 project, not just teaching an unrelated new scenario:

chapter-04-memory-and-state/project/solution.py
BLOCKING_CONDITION_PHRASES = [
    "chest pain", "can't breathe", "cannot breathe", "severe allergic reaction",
    "unresolved", "suicidal", "difficulty breathing",
]

def is_blocking_condition(text):
    return any(p in text.lower() for p in BLOCKING_CONDITION_PHRASES)

def reflect_on_response(draft_response, context):
    facts = context.get("facts", {})
    tool_trace = context.get("tool_trace", [])
    conditions = facts.get("conditions", [])
    blocking = [c for c in conditions if is_blocking_condition(c)]
    booked = any(name == "schedule_followup" and result.get("scheduled")
                 for name, result in tool_trace)
    if blocking and booked:
        flagged = "; ".join(blocking)
        return (
            f"I've noted a new, unresolved concern ({flagged}) in your file. "
            "Your requested follow-up has been provisionally scheduled, but "
            "it needs clinical review before it's finalized -- our care team "
            "will reach out if it needs to move sooner. Please do not treat "
            "this as a confirmed routine visit."
        )
    return draft_response

16. A pre-production checklist for reflection

Sections 3-15 generalize into a classifier, mirroring Chapter 4 Section 16's own checklist pattern, but for the reflection layer instead of the memory layer:

checklist.py
def classify_reflection_risk(scenario):
    if scenario.get("has_reflection_step") is False:
        return "no reflection at all -- Section 3's naive-baseline failure"
    if scenario.get("checks_against_grounded_facts") is False:
        return "ungrounded self-check -- Section 12's confident-but-wrong critique"
    if scenario.get("is_retry_not_reflection") is True:
        return "retry is not reflection -- Section 9's disguised-retry failure"
    if scenario.get("bounded") is False:
        return "unbounded reflection loop -- Section 10's runaway-correction risk"
    if scenario.get("runs_on_every_request") is True:
        return "reflection on everything -- Section 11's unnecessary-cost risk"
    return "no known risk pattern matched"

print(classify_reflection_risk({"has_reflection_step": False}))
print(classify_reflection_risk({"has_reflection_step": True, "checks_against_grounded_facts": False}))
print(classify_reflection_risk({"has_reflection_step": True, "checks_against_grounded_facts": True, "is_retry_not_reflection": True}))
print(classify_reflection_risk({"has_reflection_step": True, "checks_against_grounded_facts": True, "is_retry_not_reflection": False, "bounded": True, "runs_on_every_request": False}))

The five questions this classifier's branches encode:

  1. Does anything check the draft at all before it's returned? If not, Section 3's exact failure applies — nothing catches an incomplete or wrong answer, ever.
  2. Does the check compare against independently-derived facts, or just ask the model to review its own words? Section 12 showed a live self-critique call correctly naming a problem and still failing to fix it, with nothing grounded backing it up.
  3. Is "reflection" actually a second, distinct evaluation, or just the same prompt run again hoping for a better roll? Section 9's exact anti-pattern.
  4. Is there a hard cap on correction attempts, with an honest escalation path when it's hit? Section 10's guard, without which a stubborn draft can loop forever.
  5. Does reflection run selectively, or on every request regardless of stakes? Section 11's cost question — running it on everything trades latency and cost for benefit that, on a request like "what are your hours," never materializes.

17. GenAI Builder Thought Process

Thought process: the natural first instinct when adding "reflection" to an agent is to ask the model to "double-check its work" inside a bigger prompt — but Section 1 and Section 12 both show why that's not actually a separate check at all: a model reviewing its own words, with nothing grounded to compare against, can confidently agree with itself, or correctly name a problem and still fail to fix it. The two habits that actually work, demonstrated this chapter: ground the check in independently-derived facts whenever they exist (Sections 4-6, 13-14), and when they don't (a live self-critique call is the only option), still treat its output with the same scrutiny as any other model output, not as ground truth. A strong prompt for an AI pair-programmer extending this chapter's agent: "I have an agent that drafts a response, and I need a reflection step that checks it before it's returned. Write a verify_draft(draft_text, ...) function that independently recomputes every fact the draft claims (never parses the draft's own claim as if it were true) and returns a list of concrete problems, plus a reflect_and_revise(draft_text, ...) function that revises the draft only for the specific problems verify_draft found, with a max_reflections bound that escalates to a human instead of looping forever if the draft still fails after the bound is reached. Do not use an agent framework, and do not implement reflection as 'ask the model to check its own answer' with no grounded facts to compare against."

In the Real World
  • Section 12's exact failure pattern — a self-critique call correctly names a problem class but produces a "fix" that doesn't actually fix it — is one of the most common real gaps in production reflection systems, because it's easy to verify the diagnosis looks right in a demo without checking whether the revision actually satisfies the original standard.
  • Section 9's retry-disguised-as-reflection anti-pattern is common precisely because it's cheap to implement (just call the same function again) and looks like a fix when it occasionally works by chance — the failure only becomes visible under repeat, systematic testing, not a single demo run.
  • Section 11's cost question is why serious production agent systems route requests through a stakes/checkability classifier before deciding whether to run reflection at all, rather than either always running it (Section 6's wasted-cost case) or never running it (Section 3's uncaught-failure case).

Points to Remember

  • Reflection is a second, genuinely separate evaluation step — not a bigger prompt, not the model "thinking harder" in one pass — that checks a draft against a standard and revises it if the standard isn't met.
  • Grounded checks (independently-derived facts) catch what ungrounded ones miss — this chapter's own real Section 7/12 result showed a live self-critique call correctly diagnosing a problem and still failing to actually fix it, while the deterministic verify_draft() caught the same gap with no ambiguity.
  • Retry is not reflection (Section 9) — re-running the same prompt with no independent check tends to reproduce the same error, not fix it.
  • Reflection needs an iteration bound (Section 10), the same shape as Chapter 1's max_iterations guard, with an honest escalation path when the bound is hit rather than either looping forever or silently shipping a wrong answer.
  • Reflection is not free (Section 11) — it should run selectively, where a wrong answer has real cost and a checkable standard exists, not on every request regardless of stakes. Chapter 8 treats this cost/latency trade-off in full.
  • Revising an answer and gathering more evidence are two different kinds of self-correction (Section 8) — this chapter built the first in depth; the second is closer to Chapter 3's own tool-selection material.
  • Reflection revises what an agent says, not what a tool already did — Section 14's CareBot extension showed this limit directly: reflect_on_response() runs after schedule_followup() may have already fired, which is exactly the gap Chapter 6's guardrails are positioned to close.
  • No agent framework was used anywhere in this chapter — every function is plain Python and, where a live reasoning step was genuinely needed (Sections 3, 6, 7), the plain openai client against local Ollama, the same pattern Chapters 1-4 used.
