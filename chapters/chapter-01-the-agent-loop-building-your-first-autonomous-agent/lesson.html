The Agent Loop: Building Your First Autonomous Agent

A single LLM call answers one question. An agent decides, acts, observes what happened, and decides again — on its own, until the job is done. This chapter builds that loop from nothing, against a real local model, and breaks it on purpose so you see exactly why each piece exists.

Northbeam Outdoors runs a small chain of trailhead kiosks. Hikers type a question into a terminal — "is Eagle Ridge open?", "what's the trail status and the weather at Cedar Hollow?" — and expect a real, current answer, not a guess. The team's first attempt was a single call to an LLM with the trail name stuffed into the prompt. It read fluently. It was also completely made up: the model had no way to know today's trail status, so it invented something plausible-sounding instead. This chapter builds TrailBot, Northbeam's real fix — not a bigger prompt, but a different architecture: a model that can look things up, decide what to look up next based on what it just learned, and know when it's done. That architecture is what this whole course calls an agent, and this chapter builds one, piece by piece, against a real model, with every line of code actually run.

1. What makes this an agent?

Every agent in this course, no matter how sophisticated it eventually gets, runs the same four-step loop:

What is... the agent loop? Perception — the agent receives a task or a new piece of information. Reasoning — the model decides what to do next given everything it knows so far. Action — it does something in the world (usually: calls a tool). Observation — it sees the result of that action, which becomes new information for the next reasoning step. Then the loop repeats, using the observation as the next perception, until the model decides it has enough to answer and stops.

The single sentence that matters most in this chapter: a loop where the model's own output decides whether another iteration happens is what turns a language model into an agent. If the calling code decides how many times to call the model, and the model never sees its own previous actions' results, you have a script that calls an LLM — not an agent. Section 2 proves this by building the non-agent first.

What actually happened
The model correctly refused to invent a trail status — which is the right behavior for a model with no real data source. But it's still useless to a hiker standing at the kiosk. The problem isn't the model being "not smart enough." The problem is architectural: this call has no way to look anything up. There's no action step and no observation step — just one perception and one reasoning step, then done.
What is... perception without action? A model that can only read a prompt and write a reply has perception and reasoning, but no action and no observation. It's a text completion, not an agent — no matter how good the prose is.

3. Giving the agent hands: tools

An agent needs a real way to act. For TrailBot, that means two plain Python functions backed by Northbeam's own trail and weather data — no framework, just functions the model will later be allowed to call.

tools.py
TRAIL_STATUS = {
    "eagle ridge": {"status": "open", "difficulty": "moderate", "last_updated": "2026-09-22"},
    "cedar hollow": {"status": "closed", "reason": "storm damage", "last_updated": "2026-09-20"},
    "blue spring loop": {"status": "open", "difficulty": "easy", "last_updated": "2026-09-23"},
}

def get_trail_status(trail_name: str) -> dict:
    key = trail_name.strip().lower()
    if key not in TRAIL_STATUS:
        return {"error": f"no trail on file named '{trail_name}'"}
    return TRAIL_STATUS[key]

What is... a tool, from an agent's point of view? Any function with a name, a description, and a defined input the model can be told about and asked to invoke. The function itself never touches the model — it's ordinary Python. What makes it a "tool" is that the model gets to decide, at run time, whether and how to call it. That decision is what Section 5 adds.

4. Describing tools to the model

The model can't call a Python function directly — it can only produce text. So each tool gets described as a JSON schema: a name, a description, and the shape of its arguments. The model's job becomes picking a name and filling in arguments that match the schema.

When the model decides to call a tool, it usually has nothing to say yet — it hasn't seen the result. Content and tool_calls are, in effect, two different kinds of reply the model can give at each reasoning step.
call.function.arguments is a string, not a dict
The model produces JSON as text. Your code is responsible for parsing it with json.loads — and, as Section 9 shows, for handling the case where the text is a plausible-looking value that doesn't actually match your data.

6. Turning a decision into an observation

A tool call by itself doesn't answer the hiker's question — nothing has actually been looked up yet. The action step means executing the function for real, and the observation step means handing the result back to the model as new information.

execute_and_observe.py
result = get_trail_status(**args)
print("Tool called:", call.function.name, args)
print("Tool result:", result)
Output (real) 
Tool called: get_trail_status {'trail_name': 'Eagle Ridge'}
Tool result: {'status': 'open', 'difficulty': 'moderate', 'last_updated': '2026-09-22'}

That result now has to go back into the conversation, as a new message with role "tool", tagged with the same tool_call_id the model used to ask for it — this is what lets the model connect the observation to the action that produced it.

execute_and_observe.py (continued)
messages.append(msg)  # the model's own tool-call turn
messages.append({
    "role": "tool",
    "tool_call_id": call.id,
    "content": json.dumps(result),
})
print("messages now has", len(messages), "turns:")
for m in messages:
    role = m["role"] if isinstance(m, dict) else m.role
    print(" -", role)
Output (real) 
messages now has 3 turns:
 - user
 - assistant
 - tool

Calling the model a second time with this extended history is the second reasoning step — the one that actually answers the hiker:

response2 = client.chat.completions.create(model="llama3.2:latest", messages=messages, tools=TOOLS)
print("Final answer:", response2.choices[0].message.content)

That's the whole loop, run once by hand: perceive the question, reason to a tool call, act by running the function, observe the result, reason again to a final answer. Section 7 turns this by-hand sequence into a reusable function that can repeat as many times as the task needs.

7. Generalizing into a loop

Real questions can need more than one tool call — "is Cedar Hollow open, and what's the weather there" needs both tools. The loop has to keep going, feeding each observation back in, until the model stops asking for tools and gives a final answer instead.

agent.py
TOOL_IMPLS = {"get_trail_status": get_trail_status, "get_weather": get_weather}
SYSTEM = ("You are TrailBot, a hiking assistant. Use tools to answer with "
          "real data; never guess a trail's status or the weather.")

def run_agent(user_message, max_iterations=4):
    messages = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": user_message}]
    for i in range(1, max_iterations + 1):
        response = client.chat.completions.create(model="llama3.2:latest", messages=messages, tools=TOOLS)
        msg = response.choices[0].message
        messages.append(msg)

        if not msg.tool_calls:
            print(f"[iteration {i}] model returned a final answer, loop stops")
            return msg.content

        for call in msg.tool_calls:
            args = json.loads(call.function.arguments)
            fn = TOOL_IMPLS[call.function.name]
            result = fn(**args)
            print(f"[iteration {i}] action: {call.function.name}({args}) -> observation: {result}")
            messages.append({"role": "tool", "tool_call_id": call.id, "content": json.dumps(result)})

    print(f"[guard] hit max_iterations={max_iterations} without a final answer -- stopping anyway")
    return None
Where perception/reasoning/action/observation live in this function
Perception is messages growing with each new fact. Reasoning is each client.chat.completions.create call. Action is fn(**args). Observation is the {"role": "tool", ...} message appended right after. The for i in range(...) loop is what makes this an agent instead of the one-shot call from Section 2: the number of reasoning steps isn't fixed in advance — it's however many the model's own tool calls demand, up to the guard.
Why max_iterations exists at all
Nothing above guarantees the model eventually stops asking for tools. Section 10 shows exactly what that looks like and why the guard is not optional.

9. Diagnosing and fixing a wrong-argument failure

Look closely at what the model actually asked for: {'trail_name': 'Cedar Hollow trail'} — it appended the word "trail" to the name, because the user wrote "Cedar Hollow trail." That's a completely reasonable thing for a human to write and a completely reasonable thing for the model to pass along — but TRAIL_STATUS's key is exactly "cedar hollow", with nothing extra, so the lookup misses.

What is... a wrong-argument failure? Not a wrong tool choice (the model correctly picked both get_trail_status and get_weather) and not a hallucinated result — the model never claimed to know the answer without checking. It's a mismatch between the free-text argument the model naturally produces and the exact-match data your tool expects. This is one of the most common real agent failures, precisely because each half looks correct in isolation.

The fix belongs in the tool, not in trying to out-prompt the model into never adding a suffix — a real system will always see messy arguments, so the tool should be the one place that tolerates them.

tools.py (fix)
def _normalize(name: str) -> str:
    key = name.strip().lower()
    for suffix in (" trail", " loop", " trailhead"):
        if key.endswith(suffix):
            key = key[: -len(suffix)]
    return key

print("--- _normalize on messy model-generated arguments ---")
for name in ["Cedar Hollow trail", "Blue Spring Loop", "eagle ridge trailhead", "  Cedar Hollow  "]:
    print(f"{name!r} -> {_normalize(name)!r}")
Output (real) 
--- _normalize on messy model-generated arguments ---
'Cedar Hollow trail' -> 'cedar hollow'
'Blue Spring Loop' -> 'blue spring'
'eagle ridge trailhead' -> 'eagle ridge'
'  Cedar Hollow  ' -> 'cedar hollow'

Wiring _normalize into both tools and re-running the exact same question:

10. Guardrails: stopping a runaway loop

What happens if the model never decides it has enough information, and keeps requesting the same tool call forever? Real models occasionally do this — especially smaller, local ones. Simulating it with a stub that always asks for one more tool call, so this is reproducible without waiting on an actual runaway model:

guard_demo.py
class FakeMessage:
    """Simulates a model that NEVER stops calling a tool."""
    def __init__(self):
        self.content = None
        self.tool_calls = [make_fake_call("get_weather", {"location": "cedar hollow"})]

def run_agent_with_guard(user_message, max_iterations=4):
    for i in range(1, max_iterations + 1):
        msg = FakeMessage()  # stands in for a model that always wants another tool
        if not msg.tool_calls:
            return msg.content
        for call in msg.tool_calls:
            args = json.loads(call.function.arguments)
            result = TOOL_IMPLS[call.function.name](**args)
            print(f"[iteration {i}] action: {call.function.name}({args}) -> observation: {result}")
    print(f"[guard] hit max_iterations={max_iterations} -- loop stopped on purpose, no runaway")
    return None

run_agent_with_guard("What's the weather at Cedar Hollow?", max_iterations=3)
Output (real) 
[iteration 1] action: get_weather({'location': 'cedar hollow'}) -> observation: {'condition': 'rain', 'high_f': 54, 'low_f': 44}
[iteration 2] action: get_weather({'location': 'cedar hollow'}) -> observation: {'condition': 'rain', 'high_f': 54, 'low_f': 44}
[iteration 3] action: get_weather({'location': 'cedar hollow'}) -> observation: {'condition': 'rain', 'high_f': 54, 'low_f': 44}
[guard] hit max_iterations=3 -- loop stopped on purpose, no runaway
Without max_iterations
This exact loop shape runs forever: every iteration, the fake model asks for the same tool again, and the calling code has no independent way to know the task is actually done. In a real deployment that's not just a bad user experience — every iteration is another paid or compute-costed model call (Chapter 8's subject) and, if the tool has side effects (booking, sending, deleting), every iteration could repeat that side effect too.
Why this guard is necessary but not sufficient
max_iterations guarantees the loop halts. It does not guarantee the agent did the right thing before halting, does not stop it from calling a destructive tool inside those iterations, and does not stop a human-approval-worthy action from happening unsupervised. Chapter 6 builds the fuller guardrail set (approval checkpoints, sandboxing, rate limits) this chapter's single iteration cap is only the first layer of.

11. Handling this sandbox's Ollama hang

The very first call in this chapter (Section 2) took 138 seconds. That's not unusual for this environment specifically: this sandbox's local Ollama install has shown an intermittent hang, with one observed call during this course's own build taking 432 seconds. A production agent loop that blocks indefinitely on a single reasoning step is its own reliability failure — so every call in a real agent needs an explicit timeout, and the calling code needs to decide what "no answer in time" means for that step.

timeout_wrapper.py
from openai import APITimeoutError, APIConnectionError

def call_with_budget(client, seconds_budget, **kwargs):
    bounded_client = client.with_options(timeout=seconds_budget)
    try:
        return bounded_client.chat.completions.create(**kwargs)
    except (APITimeoutError, APIConnectionError) as exc:
        print(f"[budget] no response within {seconds_budget}s ({type(exc).__name__}) -- treat as illustrative, move on")
        return None

Proving the guard actually fires, by pointing the client at a closed port with a tight 2-second budget:

timeout_wrapper.py (continued)
demo_client = OpenAI(base_url="http://localhost:9/v1", api_key="ollama")
result = call_with_budget(
    demo_client, seconds_budget=2,
    model="llama3.2:latest",
    messages=[{"role": "user", "content": "ping"}],
)
print("result:", result)
Output (real) 
[budget] no response within 2s (APIConnectionError) -- treat as illustrative, move on
result: None
Go Deeper: why 450 seconds, specifically, in this course's own build process

This course's own build treats any single live model call as illustrative, not gate-load-bearing, and budgets up to 450 seconds for it precisely because of the 432-second hang observed once already — enough headroom to let a genuinely slow-but-working call finish, without ever idle-waiting past a point where the call has clearly failed. A production agent should budget far tighter than 450 seconds per step (this number is specific to this sandbox's own quirks, not a general recommendation) and always have a defined fallback — retry once, degrade to a cached answer, or surface a clear error — for when the budget runs out. Chapter 8 covers latency control as its own subject in depth.

12. The finished agent

Putting every piece from this chapter into one file — tools, schemas, the loop, and the guard — is TrailBot as Northbeam would actually run it:

trailbot_agent.py
import json
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

TRAIL_STATUS = {
    "eagle ridge": {"status": "open", "difficulty": "moderate", "last_updated": "2026-09-22"},
    "cedar hollow": {"status": "closed", "reason": "storm damage", "last_updated": "2026-09-20"},
    "blue spring loop": {"status": "open", "difficulty": "easy", "last_updated": "2026-09-23"},
}
WEATHER = {
    "north bend": {"condition": "clear", "high_f": 68, "low_f": 47},
    "cedar hollow": {"condition": "rain", "high_f": 54, "low_f": 44},
}

def _normalize(name):
    key = name.strip().lower()
    for suffix in (" trail", " loop", " trailhead"):
        if key.endswith(suffix):
            key = key[: -len(suffix)]
    return key

def get_trail_status(trail_name):
    return TRAIL_STATUS.get(_normalize(trail_name), {"error": f"no trail on file named '{trail_name}'"})

def get_weather(location):
    return WEATHER.get(_normalize(location), {"error": f"no weather on file for '{location}'"})

TOOL_IMPLS = {"get_trail_status": get_trail_status, "get_weather": get_weather}
TOOLS = [
    {"type": "function", "function": {"name": "get_trail_status",
        "description": "Look up whether a named hiking trail is open or closed.",
        "parameters": {"type": "object", "properties": {"trail_name": {"type": "string"}}, "required": ["trail_name"]}}},
    {"type": "function", "function": {"name": "get_weather",
        "description": "Look up current weather conditions for a named location.",
        "parameters": {"type": "object", "properties": {"location": {"type": "string"}}, "required": ["location"]}}},
]
SYSTEM = "You are TrailBot, a hiking assistant. Use tools to answer with real data; never guess a trail's status or the weather."

def run_agent(user_message, max_iterations=4):
    messages = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": user_message}]
    for i in range(1, max_iterations + 1):
        response = client.chat.completions.create(model="llama3.2:latest", messages=messages, tools=TOOLS)
        msg = response.choices[0].message
        messages.append(msg)
        if not msg.tool_calls:
            return msg.content
        for call in msg.tool_calls:
            args = json.loads(call.function.arguments)
            result = TOOL_IMPLS[call.function.name](**args)
            messages.append({"role": "tool", "tool_call_id": call.id, "content": json.dumps(result)})
    return None  # guard: max_iterations reached without a final answer

if __name__ == "__main__":
    print(run_agent("Is Cedar Hollow trail open, and what's the weather like there?"))

13. GenAI Builder Thought Process

Thought process: the temptation building an agent's first version is to reach for a framework immediately — LangGraph, CrewAI, AutoGen — because "agent" sounds like it needs one. This chapter deliberately built the loop from four plain ingredients (a client, a tools list, a Python for loop, and two dict lookups) specifically so the mechanism is never hidden. Once you can see that an "agent" is a for loop that stops when the model's own output says stop, you can evaluate what any framework is actually doing under the hood — and you can debug it when it misbehaves, because Section 9's wrong-argument failure is a bug in your normalize function, not a framework internals mystery. A strong prompt for an AI pair-programmer building this exact chapter's agent: "Write a minimal Python agent loop against the OpenAI-compatible client pointed at local Ollama. Define two tool functions with JSON schemas, run a for-loop that calls the model with tools, executes any tool_calls it returns, appends the result as a role:'tool' message tagged with tool_call_id, and stops when the model returns content with no tool_calls or after max_iterations. Do not use any agent framework — plain openai client and stdlib only."

In the Real World
  • Every "AI agent" product you've heard of — a coding agent, a research agent, a customer-support agent — runs some version of exactly this loop underneath, however many extra layers (memory stores, multi-agent handoffs, tool registries) sit on top of it.
  • The wrong-argument failure in Section 9 is one of the single most common real-world agent bugs reported in production systems: the model's tool choice is correct, the arguments are reasonable-looking, and the failure only shows up in the tool's own error path — exactly why every tool needs to be defensive about its own inputs.
  • The max_iterations guard is the simplest member of a whole guardrail family (Chapter 6) that every production agent needs before it's allowed to run unsupervised against real systems, real money, or real users.

Points to Remember

  • An agent is a loop — perception, reasoning, action, observation — where the model's own output decides whether another iteration happens. A single LLM call, however well-prompted, is not an agent.
  • Tools are plain functions described to the model as a JSON schema; the model can only produce a tool name and JSON arguments as text — your code parses, executes, and feeds the real result back as a role: "tool" message.
  • A wrong-argument failure (correct tool, plausible-but-mismatched argument) is different from a wrong-tool-choice failure or a hallucinated answer — diagnose which one you're looking at before you fix it, and fix it in the tool, since messy arguments are the normal case, not the exception.
  • An iteration guard (max_iterations) is necessary to stop a runaway loop, but is not sufficient on its own to make an agent safe to run unsupervised — it only guarantees the loop halts, not that every action taken before it halted was safe.
  • Live model calls in this sandbox can hang for minutes; wrap every call with an explicit timeout and a defined fallback rather than idle-blocking, and treat a captured transcript as the source of truth over a live re-run.
  • No agent framework was used anywhere in this chapter — the loop, the tool dispatch, and the guard are plain Python and the plain openai client, on purpose, so the mechanism stays visible.
