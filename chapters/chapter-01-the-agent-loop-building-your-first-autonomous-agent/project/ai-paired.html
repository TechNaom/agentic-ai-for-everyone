Chapter 1 Project — Solo → AI-Paired → Critique 20 min

Now Pair With an AI

You already built SlipBot's loop yourself. Now try the reverse: describe the same task to an AI assistant without showing it your own solution, and review what it hands back with the same scrutiny you'd bring to a teammate's pull request before merging it into Wavecrest Marina's real system.

Step 1: Have the AI build it independently

Thought process: the prompt needs to specify the guard requirement explicitly and concretely (what should happen at max_iterations, and what the return value should be) or the AI is likely to produce a loop that "mostly works" on the happy path but handles the runaway case ambiguously — exactly the class of gap this exercise is designed to surface.

Write the prompt you'd give an AI assistant:

Paste your prompt into your assistant of choice, save its response separately, and compare it against the checklist below before looking at this project's own solution.py.
Show a strong version of this prompt 
Write a Python function run_agent(slip_id, model, max_iterations=4) implementing an agent loop. `model` has a .step(iteration, slip_id, last_observation) method returning an object with .content and .tool_calls (a list of objects with .function.name and .function.arguments, a JSON string). If .tool_calls is empty, that's the final answer -- return (content, trace). Otherwise, for each tool call: parse the arguments, execute the matching function from a TOOL_IMPLS dict, append (name, args, result) to a trace list, and use the last result as last_observation for the next .step() call. If max_iterations is reached with no final answer, return (None, trace). Do not use any agent framework.

Step 2: Review it against this checklist

What a rushed AI-generated loop tends to get wrong
  • Off-by-one on the guard. A common mistake is looping max_iterations + 1 times, or returning (None, trace) one iteration too early or late — compare the returned trace's length against max_iterations exactly, the same way Check 4 in this project's own self-check does.
  • Silently swallowing a bad tool name. If call.function.name isn't in TOOL_IMPLS, does the generated code raise a clear error, or does it crash with an unhelpful KeyError three call frames deep? Neither is wrong per se, but an AI's first draft often doesn't handle this case at all.
  • Forgetting to update last_observation across multiple tool calls in one turn. If a turn requests more than one tool call, which result becomes "the" last observation for the next step? The generated code should make a deliberate choice here, not an accidental one.

Now compare the AI's code against solution.py in this same folder. Where do they differ? Is the AI's version genuinely equivalent, or does it handle one of the three watch-outs above differently — and is that difference actually a bug, or a legitimate different design choice?
