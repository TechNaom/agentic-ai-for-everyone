def trajectory_correctness(trace, expected):
    """Chapter 7, Section 7 -- right tool, right order, collapsing
    consecutive self-recovering duplicates."""
    tool_names = [t for t, _ in trace]
    filtered = [t for t in tool_names if t in expected]
    collapsed = []
    for t in filtered:
        if not collapsed or collapsed[-1] != t:
            collapsed.append(t)
    return collapsed == expected

3. Token/cost accounting per loop step

What is... per-step accounting, and why per-step, not per-run? Logging tokens in, tokens out, dollar cost, model used, and latency for EVERY individual tool-selection/model step inside a run -- not just one total at the end. A per-run total can't tell you which step is expensive; a per-step log can, which is what Sections 5-11's techniques each need to target correctly.
accounting.py
def count_tokens_approx(text):
    """Stdlib-only approximation: ~4 chars/token, floor 1. Disclosed as
    an approximation, not a real tokenizer -- good enough for relative
    before/after comparison, not for billing reconciliation."""
    return max(1, len(text) // 4)

MODEL_RATES = {
    "cheap":  {"in": 0.05, "out": 0.15},   # $ per 1K tokens, illustrative
    "strong": {"in": 1.00, "out": 3.00},   # $ per 1K tokens, illustrative
}

def step_cost(tokens_in, tokens_out, model="cheap"):
    rates = MODEL_RATES[model]
    return round((tokens_in / 1000) * rates["in"] + (tokens_out / 1000) * rates["out"], 6)

def log_step(step_log, tool_name, prompt_text, response_text, model="cheap", latency_s=0.0):
    tin = count_tokens_approx(prompt_text)
    tout = count_tokens_approx(response_text)
    cost = step_cost(tin, tout, model)
    step_log.append({"tool": tool_name, "tokens_in": tin, "tokens_out": tout,
                      "model": model, "cost": cost, "latency_s": round(latency_s, 4)})
    return step_log[-1]

log = []
log_step(log, "search_archive", "Find the bridge budget record for 2024.", str({"text": "..."}), model="cheap", latency_s=0.8)
log_step(log, "verify_source_credibility", "Is city-council-minutes credible?", "high", model="strong", latency_s=1.9)
print("step log:", log)
print("total cost so far:", round(sum(s["cost"] for s in log), 6))

5. Step/token/time/cost budgets -- fail-closed hard caps

What is... a fail-closed budget? A hard cap that, once exceeded, DENIES every subsequent step rather than merely warning -- the same fail-closed discipline Chapter 6's guardrails used (default-deny, not default-allow). Distinct from Chapter 1's max_iterations (safety-motivated reasoning-step cap) and Chapter 6's action budget (a safety guardrail): this budget tracks dollars, tokens, AND wall-clock seconds, and exists to bound cost/latency, not to contain damage.
budget_guard.py
import time

class BudgetExceeded(Exception):
    pass

class BudgetGuard:
    def __init__(self, max_steps=None, max_tokens=None, max_seconds=None, max_cost=None):
        self.max_steps, self.max_tokens = max_steps, max_tokens
        self.max_seconds, self.max_cost = max_seconds, max_cost
        self.steps, self.tokens, self.cost = 0, 0, 0.0
        self.t_start = time.monotonic()

    def check_and_record(self, tokens_in, tokens_out, cost):
        self.steps += 1
        self.tokens += tokens_in + tokens_out
        self.cost += cost
        elapsed = time.monotonic() - self.t_start
        if self.max_steps is not None and self.steps > self.max_steps:
            raise BudgetExceeded(f"step budget exceeded: {self.steps} > {self.max_steps}")
        if self.max_tokens is not None and self.tokens > self.max_tokens:
            raise BudgetExceeded(f"token budget exceeded: {self.tokens} > {self.max_tokens}")
        if self.max_seconds is not None and elapsed > self.max_seconds:
            raise BudgetExceeded(f"time budget exceeded: {elapsed:.2f}s > {self.max_seconds}s")
        if self.max_cost is not None and self.cost > self.max_cost:
            raise BudgetExceeded(f"cost budget exceeded: ${self.cost:.4f} > ${self.max_cost}")
        return True

guard = BudgetGuard(max_steps=3, max_cost=0.01)
try:
    for i in range(5):
        guard.check_and_record(tokens_in=50, tokens_out=50, cost=0.004)
        print(f"step {i+1} allowed; running cost ${guard.cost:.4f}")
except BudgetExceeded as e:
    print("DENIED:", e)
Output (real, executed) 
step 1 allowed; running cost $0.0040
step 2 allowed; running cost $0.0080
DENIED: cost budget exceeded: $0.0120 > $0.01
Four budget types, one guard, checked together every step
A step budget alone would let one giant-token step through; a token budget alone would let 1,000 tiny steps through; a time budget alone would let an expensive-but-fast burst through. Checking all four on every single call (not just at the end of a run) is what makes this "fail-closed" rather than "fail-eventually" -- the cost cap above fired on the THIRD attempted step, denying it before it ran, not after tallying a final bill.
A real, disclosed design choice: raise, don't silently truncate
check_and_record raises BudgetExceeded rather than quietly returning a partial result -- the caller (Section 12's assembled loop) decides what "deny" means for its own task (stop and report partial progress, or escalate), the same separation Chapter 6's dispatcher used between detecting a violation and deciding the response.

6. Early termination: stop as soon as the goal is already met

What is... early termination, here specifically? Checking, after every step, whether the trace so far already satisfies Chapter 7's own trajectory_covers_goal -- and if so, stopping immediately instead of continuing to whatever iteration cap exists. This is a cost/latency lever, not a correctness one: it never changes WHETHER a run succeeds, only how many extra, unnecessary steps a successful run pays for.
early_exit.py
def confident_enough(partial_trace, task):
    """Stop as soon as the trace already satisfies the goal -- no
    reason to keep running once the outcome-producing tool has fired."""
    fake_trace = [(t, None) for t in partial_trace]
    return trajectory_covers_goal(fake_trace, task)

def run_with_early_exit(task, rng, model="strong"):
    trace, step_log = [], []
    for step in task["expected_trajectory"]:
        latency = 0.4 + rng.random() * 1.2
        log_step(step_log, step, f"step for {task['id']}", step, model=model, latency_s=latency)
        trace.append(step)
        if confident_enough(trace, task):
            break
    return trace, step_log

rng = random.Random(5)
trace2, slog2 = run_with_early_exit(TASKS[0], rng)
print("early-exit trace:", trace2)
print("steps taken:", len(trace2), "vs. full expected trajectory:", len(TASKS[0]["expected_trajectory"]))

7. Model routing: cheap vs. strong, with a real measured gap

What is... model routing/tiering? Sending cheap, decisive, low-judgment steps to a smaller or cheaper model, and reserving a stronger (or more carefully-prompted) model for steps that genuinely require judgment. Section 2's live result already showed the real cost of getting this wrong: a ~20x latency gap between a capped, one-word decision and an open-ended reasoning call for the exact same step.
routing.py
CHEAP_ELIGIBLE = {"search_archive", "verify_source_credibility"}  # cheap, decisive lookups

def choose_model_for_step(step_name):
    """Route cheap, decisive lookups to the cheaper model; reserve the
    strong model for steps that need real judgment: cross_check_claim's
    content comparison, draft_citation's wording, escalate_to_editor's
    reasoning."""
    return "cheap" if step_name in CHEAP_ELIGIBLE else "strong"

for step in TASKS[0]["expected_trajectory"]:
    print(step, "->", choose_model_for_step(step))

verify_source_credibility -> cheap
cross_check_claim -> strong

Why cross_check_claim stays on the strong tier
Chapter 7 Section 5's own real bug ($12M claim, $9.4M record, a naive word-overlap heuristic said "match") was a content-judgment failure. Routing that exact step to the cheapest, least-careful option available would make that bug MORE likely, not less -- model routing is about matching model strength to the step's actual difficulty, not simply making everything as cheap as possible.

A real production option this chapter names but does not call: a low-cost router like OpenRouter can pick the cheapest provider/model meeting a quality bar per request, and a fast-inference host like Groq can serve an open-weight model (e.g., a Llama variant) at very low per-token latency -- both conceptual options for a real "cheap" tier, mentioned here without a live paid call, matching this course's own no-paid-API policy.

8. Caching: don't pay twice for the same question

What is... caching, here specifically? Storing a tool call's result keyed by (tool name, arguments) and returning the cached result instead of recomputing/re-calling when the identical (tool, arguments) pair repeats -- across runs, across tasks, or within one long session. A fact-checking agent that gets asked about the same archived record twice should not do that lookup work twice.
cache.py
class ToolCache:
    def __init__(self):
        self.store = {}
        self.hits, self.misses = 0, 0

    def get_or_call(self, tool_name, args_key, compute_fn):
        key = (tool_name, args_key)
        if key in self.store:
            self.hits += 1
            return self.store[key], True
        self.misses += 1
        result = compute_fn()
        self.store[key] = result
        return result, False

cache = ToolCache()
def expensive_lookup():
    return ARCHIVE["bridge-budget-2024"]

r1, hit1 = cache.get_or_call("search_archive", "bridge-budget-2024", expensive_lookup)
r2, hit2 = cache.get_or_call("search_archive", "bridge-budget-2024", expensive_lookup)
r3, hit3 = cache.get_or_call("search_archive", "unemployment-q2", lambda: ARCHIVE["unemployment-q2"])
print("call1 cache hit:", hit1, "call2 cache hit:", hit2, "call3 cache hit:", hit3)
print("cache hits:", cache.hits, "misses:", cache.misses)
Output (real, executed) 
call1 cache hit: False call2 cache hit: True call3 cache hit: False
cache hits: 1 misses: 2
A real, disclosed limitation: cache invalidation is out of scope here
This minimal cache never expires or invalidates an entry -- fine for FactScout's own fixture archive (Chapter 7's ARCHIVE dict never changes mid-session), genuinely wrong for a source whose credibility or content can change over time. A production cache needs a TTL or an explicit invalidation trigger; that's a real gap, named rather than hidden, and out of this chapter's own scope (this chapter's job is showing caching's cost/latency effect, not building a production cache invalidation policy).

9. Parallel tool calls: a real measured 3.2x on two independent calls

What is... parallel tool calls, and when is it safe? Running two or more tool calls concurrently instead of one after another -- safe ONLY when the calls are genuinely independent (neither needs the other's result as input). search_archive and, separately, checking a known source's credibility from a fixed table are independent; cross_check_claim is NOT independent of search_archive's result, since it needs the actual record text.
live_parallel_vs_sequential.py
import time
from concurrent.futures import ThreadPoolExecutor

def quick_call(prompt):
    t0 = time.monotonic()
    r = client.chat.completions.create(
        model="llama3.2:latest", messages=[{"role": "user", "content": prompt}],
        extra_body={"keep_alive": "120m"}, max_tokens=5, temperature=0.0,
    )
    return time.monotonic() - t0, r.choices[0].message.content.strip()

t0 = time.monotonic()
a = quick_call("Say ONE")
b = quick_call("Say TWO")
seq_elapsed = time.monotonic() - t0
print("sequential total:", round(seq_elapsed, 2))

t0 = time.monotonic()
with ThreadPoolExecutor(max_workers=2) as ex:
    fa = ex.submit(quick_call, "Say ONE")
    fb = ex.submit(quick_call, "Say TWO")
    ra, rb = fa.result(), fb.result()
par_elapsed = time.monotonic() - t0
print("parallel total:  ", round(par_elapsed, 2))

A real 3.2x speedup on two genuinely independent live calls
Both calls hit the exact same local Ollama server -- this is not two separate machines, and a single-model local server still has finite concurrency, which is exactly why the parallel total (1.61s) isn't simply half the sequential total's already-fast per-call time; it reflects real, measured overlap, not a theoretical one. A production multi-provider setup (separate API endpoints with real independent capacity) would generally show an even larger gap.
The failure mode this section deliberately does NOT demonstrate
Running cross_check_claim in parallel with the search_archive call it depends on would either crash (no record yet) or silently run against stale/missing data -- parallelizing a dependent step is a correctness bug, not a speed win, and Section 12's assembled loop only parallelizes steps it has already confirmed are independent.

10. Latency percentiles: p50/p95, not just the mean

What is... p50/p95, and why not just report an average? p50 (the median) is the latency half of all runs beat; p95 is the latency 95% of runs beat -- meaning 1 in 20 runs is SLOWER than the reported p95. An average can look perfectly reasonable while hiding a long tail of genuinely bad runs that p95 exposes directly. A production SLO is almost always stated in p95 or p99 terms, not a mean, for exactly this reason.
percentiles.py
import math, random

def percentile(values, p):
    if not values:
        return None
    s = sorted(values)
    k = (len(s) - 1) * (p / 100)
    f, c = math.floor(k), math.ceil(k)
    if f == c:
        return s[int(k)]
    return s[f] + (s[c] - s[f]) * (k - f)

rng = random.Random(9)
latencies = [round(0.3 + rng.expovariate(1.0) * 0.4, 3) for _ in range(50)]
print("mean:", round(sum(latencies) / len(latencies), 3))
print("p50:", round(percentile(latencies, 50), 3))
print("p95:", round(percentile(latencies, 95), 3))
print("max:", max(latencies))
Output (real, executed -- seeded, reproducible with seed=9) 
mean: 0.591
p50: 0.52
p95: 1.209
max: 1.33
The mean (0.591) looks fine; p95 (1.209) tells a different story
The mean is dragged only slightly above the median by a handful of slow runs. p95 shows that a real 1-in-20 run is more than DOUBLE the mean -- a user or a downstream SLA that only tracks average latency would never see that tail coming, right up until it's the run someone is actually waiting on.

11. Timeouts and retries with backoff

What is... backoff, and how is this different from Chapter 3's retry policy? Chapter 3 built per-tool failure policies (timeout -> bounded retry; malformed output -> no retry; succeeds-but-wrong-answer -> independent verification). This chapter's retry-with-backoff is specifically about NOT hammering a slow/overloaded endpoint with immediate retries -- each retry waits longer than the last (exponential backoff), which is a cost/latency-shaping decision on top of Chapter 3's already-correct decision about WHETHER to retry at all.
retry_backoff.py
import time

class CallTimeout(Exception):
    pass

def call_with_retry_backoff(fn, max_attempts=3, base_delay=0.0, timeout_s=2.0):
    """base_delay=0.0 here for a fast, deterministic demo; real usage
    would sleep base_delay * 2**attempt between retries."""
    last_exc = None
    for attempt in range(max_attempts):
        try:
            t0 = time.monotonic()
            result = fn()
            if time.monotonic() - t0 > timeout_s:
                raise CallTimeout("exceeded timeout")
            return result, attempt + 1
        except (CallTimeout, ConnectionError) as e:
            last_exc = e
            if base_delay:
                time.sleep(base_delay * (2 ** attempt))
    raise last_exc

attempts_made = {"n": 0}
def flaky():
    attempts_made["n"] += 1
    if attempts_made["n"] < 3:
        raise ConnectionError("simulated transient failure")
    return "ok"

result, attempts = call_with_retry_backoff(flaky, max_attempts=5)
print("flaky result:", result, "attempts:", attempts)
Output (real, executed) 
flaky result: ok attempts: 3

Why exponential backoff specifically: a retry storm (many failing calls all retrying at the same fixed interval) can itself cause or worsen the latency spike Section 10's p95 is trying to catch -- doubling the delay each attempt spreads retries out instead of synchronizing them. Combined with Section 5's BudgetGuard, backoff's growing delays are exactly why a TIME budget (not just a step or cost budget) matters: three quick failures plus backoff can burn far more wall-clock time than three quick successes would.

def cost_per_success(results):
    """Chapter 7, Section 13 -- reused, unchanged."""
    out = {}
    for task_id, r in results.items():
        n = r["n_runs"]
        successes = round(r["task_success_rate"] * n)
        out[task_id] = round(r["total_cost"] / successes, 6) if successes else None
    return out

def classify_cost_control_gap(setup):
    if setup.get("tracks_per_step_cost") is False:
        return "no per-step accounting -- Section 3's exact gap, can't target anything"
    if setup.get("has_hard_budget") is False:
        return "no fail-closed budget -- a single bad run can run unbounded"
    if setup.get("has_early_exit") is False:

    if setup.get("measures_cost_per_success") is False:
        return "not measuring cost_per_success -- can't tell a real win from a false one"
    return "no known gap matched"

15. GenAI Builder Thought Process

Thought process: the natural first instinct when an agent loop is "too expensive" is to reach for the single biggest lever available -- swap to a cheaper model everywhere, or slash the iteration cap -- and call it solved. Section 13's own real numbers are the direct rebuttal to stopping there: routing and caching alone cut cost 51% and latency 92.3%, but a blind global cheap-model swap (routing EVERY step, including cross_check_claim, to the cheap tier) would have directly worsened the exact content-correctness risk Chapter 7 Section 5's own $12M/$9.4M bug already demonstrated. The habit that actually works, demonstrated this chapter: account for cost per step before touching anything (Section 3), add a fail-closed hard budget as a backstop (Section 5), let a loop stop the moment its goal is met (Section 6), route ONLY the steps that don't need real judgment to a cheaper tier (Section 7), cache ONLY genuinely repeatable lookups (Section 8), parallelize ONLY genuinely independent calls (Section 9), track the tail (p95) not just the mean (Section 10), and then re-measure with cost_per_success -- not cost-per-run -- to confirm the change is a real win, not a hidden regression (Section 13). A strong prompt for an AI pair-programmer building this for a different agent: "I have an agent loop that logs a step-by-step trace of (tool_name, result) pairs. Add cost/latency control: (1) a per-step accounting function that estimates tokens and dollar cost per step, tagged by which model tier handled it; (2) a fail-closed BudgetGuard class that tracks running steps, tokens, wall-clock seconds, and cost, and raises before allowing a step that would exceed any one of four configurable caps; (3) an early-exit check that stops the loop the instant the existing trace already satisfies the task's success condition; (4) a model-routing function that sends only a named allowlist of 'cheap-eligible' steps to a cheaper tier, defaulting everything else to the stronger tier; (5) a (tool_name, args)-keyed cache with hit/miss counters; (6) a latency percentile function (p50/p95) over a batch of run latencies; (7) a retry-with-exponential-backoff wrapper distinct from any existing per-tool failure-type retry policy. Then re-run my existing eval harness's cost_per_success function before and after, and report the real percentage change in both total cost and mean latency, not just an assertion that it improved. Use only the Python standard library plus the plain openai client -- no agent framework."

In the Real World
  • Section 2 and Section 7's ~20x latency gap between a capped one-word decision and an open-ended reasoning call for the same step is exactly why production teams often run TWO prompt styles for the same underlying step -- a tight, capped "classification" style for routing/decision steps and a longer, uncapped style reserved only for steps that genuinely need extended reasoning.
  • Section 9's parallel-tool-call speedup generalizes directly to a common production pattern: a research or support agent firing 3-5 independent lookups (a knowledge-base search, a user-history fetch, a status-API check) concurrently instead of serially, often the single biggest latency win available before touching model choice at all.
  • Section 13's own honest small-success-rate dip is a real, common shape: a cost/latency change that helps the aggregate cost_per_success number can still make one specific task slightly worse. A production rollout should check the metric per-task (as Section 13 did), not only the aggregate, before shipping a "the whole system got cheaper" change that quietly regresses one important task.

Points to Remember

  • Per-step accounting comes first (Section 3) -- every other technique needs to know which step is expensive before it can target it.
  • Budgets must fail closed (Section 5) -- a hard cap on steps, tokens, time, AND cost that DENIES the next step once exceeded, distinct from Chapter 1's max_iterations and Chapter 6's action budget.
  • Early exit saves cost/latency without changing correctness (Section 6) -- stop the moment the goal is already met, never a substitute for the budget.
  • Model routing must respect content difficulty, not just cost (Section 7) -- Chapter 7's own $12M/$9.4M bug is the reason cross_check_claim stays on the strong tier.
  • Caching has a real, disclosed limitation (Section 8) -- no invalidation built here; safe only for genuinely stable lookups.
  • Parallelize only genuinely independent calls (Section 9) -- a real measured 3.2x speedup on two live, independent Ollama calls; parallelizing a dependent step is a correctness bug, not a speed win.
  • Report p95, not just the mean (Section 10) -- the tail is what a real SLA cares about.
  • The only proof that any of this "worked" is re-measuring with cost_per_success (Section 13) -- a real before/after: 51.0% cost reduction, 92.3% latency reduction, with an honestly disclosed small per-task success dip that the metric still shows as a net win, not hidden.
  • No agent framework was used anywhere in this chapter -- every technique is plain Python (stdlib plus concurrent.futures) or the plain openai client against local Ollama.
