Chapter 8 — Solo → AI-Paired → Critique 20 min

Now Pair With an AI

You already worked the exercises yourself on Brambleford Analytics' InsightScout. Now a third scenario, Caldwell Ridge Observatory (a fictional astronomical research station) and its scheduling agent SkyScout, gets built a second way: by prompting an AI assistant for a cost/latency-control layer, and reviewing what it hands back with the same skepticism you'd bring to a coworker's pull request before trusting its reported savings.

Step 1: Design it yourself, first

SkyScout can check telescope availability, compute an observation window, validate weather conditions, or escalate a scheduling conflict to a human astronomer. Before reading further, sketch your own plan: which of SkyScout's steps are cheap/decisive enough to route to a cheaper model tier, which need to stay on a stronger tier, and which two steps (if any) could safely run in parallel because neither depends on the other's result? There's no grading here, just your own design to compare against Step 3.

Step 2: Ask an AI assistant to build the same thing

Thought process: the prompt needs to state explicitly that the budget must be FAIL-CLOSED (deny the next step, don't just warn) and that cost savings must be re-measured with a success-rate-aware metric -- otherwise a rushed AI answer tends to produce a budget that only logs a warning past the cap, and a "before/after" comparison that reports a raw cost delta with no check on whether success rate also changed, exactly the shortcut this chapter's own Section 13 explicitly ran cost_per_success to rule out.

Write the prompt you'd give an AI assistant:

Paste your prompt into your assistant of choice, save its response separately, and compare it against the checklist below before looking at this chapter's own lesson pattern.
Show a strong version of this prompt 
Write Python stdlib-only cost/latency-control code for an agent, SkyScout, with tools check_telescope_availability(telescope_id), compute_observation_window(target), validate_weather(site_id), and escalate_to_astronomer(reason). I need: (1) a per-step accounting function that estimates token cost per step tagged by a model tier ("cheap" or "strong"); (2) a FAIL-CLOSED BudgetGuard class that tracks running steps, tokens, wall-clock seconds, and dollar cost, and RAISES an exception before allowing a step that would exceed any configured cap -- it must not just log a warning and continue; (3) a model-routing function that sends only a named allowlist of cheap-eligible steps to the cheap tier; (4) a (tool_name, args)-keyed cache with hit/miss counters; (5) a percentile function for p50/p95 latency over a batch of runs. Then write a before/after harness that runs a small task set 20 times each way and reports the SAME success-rate-aware cost metric (cost divided by successful runs, not total runs) for both the before and after version, not just a raw cost or latency percentage. Use only the Python standard library -- no agent framework, no numpy or pandas.

Step 3: Review it against this checklist

What a rushed AI-generated cost/latency layer tends to get wrong
  • A budget that warns instead of denying. A shallow reading of "budget" often produces a class that logs print("warning: over budget") and keeps running anyway -- does the generated BudgetGuard-equivalent actually raise/return a hard denial BEFORE the over-budget step executes, the same fail-closed discipline this chapter's own Section 5 and Chapter 6's guardrails both insist on?
  • Reporting a raw cost or latency delta with no success-rate check. "It's 60% cheaper now" sounds like a finished answer -- but does the AI's before/after report actually recompute a cost-per-success-style metric, or does it silently assume success rate stayed the same without checking?
  • Routing every step to the cheap tier indiscriminately. An AI answer optimizing purely for "make it cheaper" may route everything to the cheap tier, including a step that clearly needs real judgment (validate_weather's safety-relevant call, for instance) -- does the routing function have a deliberate, named allowlist of cheap-eligible steps, or does it just route by "is this the first/simplest-looking step"?

Now compare the AI's code against this chapter's own lesson pattern (Sections 5-13) and against solution.py in the exercises folder. Where do they differ? Does the AI's version actually re-measure with a success-rate-aware cost metric before claiming a win, or does it stop at a raw percentage that this chapter's own Section 13 would have flagged as incomplete?
