Operating Agents in Production

Chapter 9 built dispatch. Chapter 10 built peer communication. Both chapters' agents ran once, by hand, with a human watching. This chapter closes Module 5 by asking the question production actually asks: what has to be true for this SAME system -- Harrowgate Logistics Exchange's DockScout and YardScout -- to run unattended, overnight, with nobody watching, and still be debuggable afterward? The answer is four mechanisms: retries that never re-commit a side effect, timeouts at three distinct layers, structured logs that let a bad run be attributed after the fact, and a run summary computed from those logs, not from counters that vanish on crash.

1. Hand-off from Chapters 9-10: coordinated once by hand vs. operated unattended

Chapters 9 and 10 answered "how do two or more agents work together correctly, for one run." Chapter 11 answers a different question: "what has to be added so that the SAME correct system can run many times, unattended, and still be trusted?" Nothing about dispatch, peer messaging, the claim-check, or deadlock detection changes. What's added sits AROUND those mechanisms: retries that wrap a call, timeouts that bound a call/agent/exchange, logs that record what happened, and a summary computed from those logs.

What is... "operating" an agent system, precisely? Building a multi-agent system (Chapters 9-10) answers "does it produce the right outcome." Operating it answers "does it keep producing the right outcome, unattended, across many runs, when something -- a slow call, a dropped connection, a process restart -- inevitably goes wrong partway through." The mechanisms are retries, timeouts, structured logging, and run summaries; none of them change what the agents decide, only how the SYSTEM around them behaves when a decision doesn't land cleanly.

4. A live call, read twice -- the real argument drift that motivates idempotency keys

This session ran the SAME request against DockScout's own live model twice in a row, simulating what a caller does when a first attempt's response is lost and it retries: "confirm shipment S-104 is claimed by you (DockScout)." Attempt 1 includes an extra "vehicle":"None" key that attempt 2 doesn't. Nothing was scripted to produce this; it's the model's own real output across two calls with an identical prompt. If a retry system de-duplicated by comparing the raw argument JSON string, these two calls would look like two DIFFERENT actions -- and a naive "retry on failure, re-send on no response" policy could commit the SAME confirmation twice. That's exactly the bug this chapter's idempotency key design (Section 5) is built to prevent.

5. Idempotency keys: committing a side effect exactly once

The fix is to key on the fields that actually DEFINE the side effect -- agent, shipment, and action -- not on the full argument payload a model happens to produce. A commit store keyed this way runs the real effect once, and any later call with the same key gets the FIRST result replayed, never a second commit.

idempotency.py
import threading

def idempotency_key(agent, shipment_id, action):
    """Keys on the fields that define the side effect, NOT the raw
    argument dict -- Section 4's own live result is the reason: two
    real calls for the 'same' action had different raw JSON."""
    return f"{agent}:{shipment_id}:{action}"

_committed_keys = {}
_committed_lock = threading.Lock()

def commit_once(key, effect_fn):
    with _committed_lock:
        if key in _committed_keys:
            return {"ok": True, "result": _committed_keys[key], "replayed": True}
        result = effect_fn()
        _committed_keys[key] = result
        return {"ok": True, "result": result, "replayed": False}

key = idempotency_key("dockscout", "S-104", "confirm_claim")
c1 = commit_once(key, lambda: "committed-S-104")
c2 = commit_once(key, lambda: "SHOULD NOT RUN AGAIN")
print("first commit: ", c1)
print("retried commit:", c2)
Output (real, executed) 
first commit:  {'ok': True, 'result': 'committed-S-104', 'replayed': False}
retried commit: {'ok': True, 'result': 'committed-S-104', 'replayed': True}
Code breakdown
idempotency_key
Built from (agent, shipment_id, action) -- exactly the fields Section 4's live drift did NOT change. The extra "vehicle" field never enters the key, so both of Section 4's real calls would map to the SAME key.
commit_once
The second call's effect_fn (the lambda that would print "SHOULD NOT RUN AGAIN") is never invoked. replayed: True is the caller's signal that this attempt is a retry echo, not a new commit.

6. Bounded retries with exponential backoff, wired to idempotency

A retry policy without a bound is a hang with extra steps (Chapter 1's own `max_iterations` lesson). This chapter's retry wrapper bounds attempts, backs off exponentially between them, and logs every attempt -- feeding Section 9's structured log, not an in-process counter.

retries.py
import time

class RetriesExhausted(Exception):
    pass

def call_with_retries(fn, max_attempts=3, base_delay=0.0, log=None,
                       correlation_id=None, agent=None):
    last_exc = None
    for attempt in range(1, max_attempts + 1):
        try:
            result = fn()
            if log is not None:
                log.append(event(correlation_id, "retry_attempt",
                                  agent=agent, attempt=attempt, ok=True))
            return result
        except Exception as e:
            last_exc = e
            if log is not None:
                log.append(event(correlation_id, "retry_attempt", agent=agent,
                                  attempt=attempt, ok=False, error=str(e)))
            if attempt < max_attempts:
                time.sleep(base_delay * (2 ** (attempt - 1)))
    if log is not None:
        log.append(event(correlation_id, "retries_exhausted", agent=agent,
                          attempts=max_attempts))
    raise RetriesExhausted(f"{max_attempts} attempts failed: {last_exc}")

attempts = {"n": 0}
def flaky():
    attempts["n"] += 1
    if attempts["n"] < 2:
        raise RuntimeError("transient failure")
    return "committed"

log = []
result = call_with_retries(flaky, max_attempts=3, log=log,
                            correlation_id="run-001", agent="dockscout")
print("result:", result, "| attempts used:", attempts["n"])
for line in log:
    print(line)
Output (real, executed) 
result: committed | attempts used: 2
{"agent": "dockscout", "correlation_id": "run-001", "event": "retry_attempt", "attempt": 1, "ok": false, "error": "transient failure", "ts": ...}
{"agent": "dockscout", "correlation_id": "run-001", "event": "retry_attempt", "attempt": 2, "ok": true, "ts": ...}

Pair this with Section 5: the retried call inside fn should wrap commit_once(idempotency_key(...), ...), not the raw effect directly, so a retry that happens to succeed on an attempt AFTER the side effect already landed never double-commits.

backoff_schedule.py
base_delay = 0.5
for attempt in range(1, 5):

Code breakdown
max_attempts
Bounded, the same guard-rail discipline as Chapter 1's max_iterations -- an unbounded retry loop is a hang with extra steps.
base_delay * (2 ** (attempt - 1))
Exponential backoff: each failed attempt waits longer than the last, so a transient outage doesn't get hammered with instant re-calls.

This session also tested what a real per-call timeout does when it fires, rather than asserting it in the abstract: an OpenAI client configured with timeout=0.5 seconds, pointed at this same local Ollama.

Output (real, unscripted) 
elapsed=3.07s  APITimeoutError: Request timed out.

Disclosed honestly: the timeout fired at 3.07 seconds, not exactly 0.5. A client-side timeout is a BUDGET the HTTP stack enforces approximately -- connection setup, retries inside the HTTP library itself, and OS-level buffering all add real overhead on top of the configured value. The lesson for a production system: treat every timeout value as a floor on how long you'll wait, never a guarantee of the exact clock, and budget headroom above it (this course's own 450-second live-call budget, used throughout Chapters 1-11, is exactly this kind of headroom).

8. Three timeout layers, and which failure each one catches

One timeout value cannot protect against all three failure shapes at once. This chapter uses three independent layers, each catching a failure the others cannot see:

timeout_layers.py
def call_with_timeout(fn, timeout_s):
    """LAYER 1 -- per-call. Protects against ONE network call hanging.
    Section 7's real 3.07s/0.5s result is this layer, live."""
    import time
    start = time.time()
    try:
        result = fn()
        return {"ok": True, "result": result, "elapsed_s": time.time() - start}
    except Exception as e:
        return {"ok": False, "error": str(e), "elapsed_s": time.time() - start}

def agent_within_step_timeout(steps_elapsed_s, max_agent_s):
    """LAYER 2 -- per-agent. Protects against ONE agent's own internal
    loop (its own retries, its own reflection passes, Chapter 5) running
    long even when every individual call inside it was within budget."""
    return steps_elapsed_s <= max_agent_s

def exchange_within_timeout(elapsed_s, max_exchange_s):
    """LAYER 3 -- per-exchange. This IS Chapter 10's deadlock timeout
    (check_for_deadlock), reused unchanged: it protects against the
    WHOLE multi-message exchange never converging, even if every call
    and every agent were individually healthy the entire time."""
    from chapter_10 import check_for_deadlock
    return check_for_deadlock(max_exchange_s, elapsed_s)["status"] != "deadlock_detected"

print("Layer 1 catches: one hung network call.")
print("Layer 2 catches: one agent's own loop running long overall.")
print("Layer 3 catches: the whole exchange never converging (Ch10's deadlock).")

All three layers must be enforced independently, at the layer each one protects.

9. Structured logging: one JSON line per event, one correlation id per run

Every message, dispatch, retry, timeout, and commit this chapter produces is written as one JSON line, all sharing a correlation_id unique to that run. This is what makes a run attributable AFTER it finishes, from the log alone, with no live process to interrogate.

structured_log.py
import json, time

def event(correlation_id, event_type, **fields):
    return json.dumps({
        "correlation_id": correlation_id,
        "event": event_type,
        "ts": round(time.time(), 3),
        **fields,
    }, sort_keys=True)

cid = "run-2026-10-04-0001"
log = [
    event(cid, "dispatch", agent="dockscout", shipment_id="S-104", ok=True),
    event(cid, "dispatch", agent="yardscout", shipment_id="S-104", ok=False,
          reason="already claimed"),
    event(cid, "duplicate_skipped", agent="yardscout", shipment_id="S-104"),
    event(cid, "commit", agent="dockscout", shipment_id="S-104"),
]
for line in log:
    print(line)
Output (real, executed) 
{"correlation_id": "run-2026-10-04-0001", "event": "dispatch", "agent": "dockscout", "shipment_id": "S-104", "ok": true, "ts": 1759...}
{"correlation_id": "run-2026-10-04-0001", "event": "dispatch", "agent": "yardscout", "shipment_id": "S-104", "ok": false, "reason": "already claimed", "ts": 1759...}

10. Attribution from logs alone -- Chapter 9 and 10's functions, answered after the fact

Chapter 9's which_agent_responsible and Chapter 10's which_agent_caused_miscommunication both take an in-memory trace built DURING a run. In production, the process that ran may be gone by the time someone investigates. The fix is not a new function -- it's reconstructing the SAME trace shape from the log.

attribution_from_log.py
def trace_from_log(log_lines, event_type="dispatch"):
    """Rebuilds Chapter 9's (agent, tool, ok) trace shape purely from
    structured log lines -- no in-process state required."""
    import json
    parsed = [json.loads(l) for l in log_lines]
    return [(e["agent"], e.get("tool", event_type), e["ok"])
            for e in parsed if e["event"] == event_type]

log = [
    '{"event": "dispatch", "agent": "dockscout", "ok": true}',
    '{"event": "dispatch", "agent": "yardscout", "ok": false}',
]
trace = trace_from_log(log)
print("reconstructed trace:", trace)
print("which_agent_responsible (Ch9, unchanged):",
      which_agent_responsible(trace))
Output (real, executed) 
reconstructed trace: [('dockscout', 'dispatch', True), ('yardscout', 'dispatch', False)]
which_agent_responsible (Ch9, unchanged): yardscout

Chapter 9's and 10's own attribution functions are not re-derived -- the log is shaped so its lines can be fed back into them, unchanged, days after the run that produced them finished.

11. Operating-state reporting: a run summary that survives a crash

An in-process counter (retries_used += 1 in a running Python variable) is gone the instant the process crashes. A summary computed by RE-PARSING the structured log survives exactly that crash, because the log was already flushed to disk one line at a time.

run_summary.py
import json

def run_summary_from_log(log_lines):
    parsed = [json.loads(line) for line in log_lines]
    dispatches = [e for e in parsed if e["event"] == "dispatch"]
    commits = [e for e in parsed if e["event"] == "commit"]
    retries = [e for e in parsed if e["event"] == "retry_attempt"]
    timeouts = [e for e in parsed if e["event"] == "timeout"]
    deadlocks_broken = [e for e in parsed if e["event"] == "deadlock_broken"]
    duplicates_skipped = [e for e in parsed if e["event"] == "duplicate_skipped"]
    n_dispatch = len(dispatches)
    n_ok = sum(1 for e in dispatches if e.get("ok"))
    return {
        "dispatches": n_dispatch,
        "success_rate": (n_ok / n_dispatch) if n_dispatch else 0.0,
        "commits": len(commits),
        "retries_used": len(retries),
        "timeouts_hit": len(timeouts),
        "deadlocks_broken": len(deadlocks_broken),
        "duplicates_skipped": len(duplicates_skipped),
    }

log = [
    '{"event": "dispatch", "agent": "dockscout", "ok": true}',
    '{"event": "dispatch", "agent": "yardscout", "ok": false}',
    '{"event": "commit", "agent": "dockscout", "shipment_id": "S-104"}',
    '{"event": "duplicate_skipped", "agent": "yardscout"}',
    '{"event": "deadlock_broken", "first_mover": "dockscout"}',
]
print(run_summary_from_log(log))
Output (real, executed) 
{'dispatches': 2, 'success_rate': 0.5, 'commits': 1, 'retries_used': 0, 'timeouts_hit': 0, 'deadlocks_broken': 1, 'duplicates_skipped': 1}

This function is called AFTER the run, against the log file on disk -- even if the process that produced the log crashed one line after the last event was written, the summary above is still exactly reproducible.

14. Harrowgate Logistics Exchange, operated end-to-end

Putting every mechanism together: DockScout and YardScout's Chapter 10 exchange, now wrapped in retries with idempotency keys, three timeout layers, a structured log with one correlation id, and a run summary computed from that log.

operate_harrowgate.py
def operate_run(shipments, correlation_id):
    log = []
    for agent, shipment_id in shipments:
        key = idempotency_key(agent, shipment_id, "confirm_claim")

        def do_claim():
            return coordinated_claim(agent, shipment_id)

        timed = call_with_timeout(do_claim, timeout_s=5.0)
        log.append(event(correlation_id, "dispatch", agent=agent,
                          shipment_id=shipment_id, ok=timed["ok"] and timed["result"]["ok"]))
        if timed["ok"] and not timed["result"]["ok"]:
            log.append(event(correlation_id, "duplicate_skipped",
                              agent=agent, shipment_id=shipment_id))
        elif timed["ok"]:

            log.append(event(correlation_id, "commit", agent=agent,
                              shipment_id=shipment_id, replayed=commit["replayed"]))
    return log

15. GenAI Builder Thought Process

Thought process: the natural first instinct when a multi-agent system "works" in testing is to assume it will keep working unattended. This chapter's own real Section 4 result is the direct rebuttal: the SAME prompt, retried, produced two DIFFERENT argument shapes from a real model -- a detail invisible in a single successful test run, and exactly the kind of drift that causes a double-commit in production if retries are built on raw argument equality instead of a deliberately narrow idempotency key. The habit that actually works, demonstrated this chapter: key idempotency on the fields that DEFINE the side effect, not the full payload (Section 5); bound every retry and back off between attempts (Section 6); enforce three INDEPENDENT timeout layers because no single one catches every failure shape (Section 8); log every event as one JSON line with a shared correlation id so a bad run can be attributed AFTER it ends, not only while watching it live (Section 9-10); and compute the run summary from that log, never from an in-process counter that disappears the instant the process crashes (Section 11). A strong prompt for an AI pair-programmer operationalizing a different multi-agent system: "I have a working multi-agent system (two or more agents that dispatch sub-tasks or exchange peer messages). Add production operating concerns WITHOUT changing how the agents decide anything: (1) an idempotency key built from the fields that define each side effect, not the raw call arguments; (2) a bounded retry wrapper with exponential backoff, wired so a retried call never re-commits a side effect already recorded under its idempotency key; (3) three independent timeout layers -- per-call, per-agent (its own internal loop), and per-exchange (the whole multi-message interaction) -- each with its own budget; (4) structured JSON-line logging of every dispatch, retry, timeout, and commit, tagged with one correlation id per run; (5) a function that reconstructs an attribution trace FROM the log alone, not from in-memory state; (6) a run summary computed by re-parsing the log, so it survives the process crashing mid-run. Use only the Python standard library and the plain openai client -- no LangGraph, CrewAI, AutoGen, or an external logging/observability framework; this is a from-scratch, minimal operating layer, not a wrapper around one."

16. Points to remember

  • Operating a multi-agent system unattended requires mechanisms AROUND the agents' decisions, not changes to those decisions: retries, timeouts, structured logging, and run summaries.
  • A real, unscripted retried call this session produced two different argument shapes for the "same" action -- the concrete reason idempotency keys must be built from the fields that define a side effect, never from raw argument equality.
  • commit_once plus an idempotency key guarantees a side effect lands exactly once, even across multiple retried attempts.
  • A bounded retry wrapper with exponential backoff must log every attempt -- including exhaustion -- not just the final outcome.
  • A real per-call timeout fired at 3.07 seconds against a configured 0.5-second budget this session: a client timeout is a floor to budget around, not an exact guarantee.
  • Three timeout layers are independent: per-call catches a hung network request, per-agent catches one agent's own loop running long, per-exchange (Chapter 10's deadlock timeout) catches the whole interaction never converging.
  • Structured logs are one JSON object per line, tagged with a shared correlation id, so Chapter 9's which_agent_responsible and Chapter 10's which_agent_caused_miscommunication stay answerable from the log alone, after the run ends.
  • A run summary must be computed by re-parsing the log, never from in-process counters, so it survives a crash mid-run.
  • Chapter 7's reliability measurement and Chapter 8's cost accounting are the measurement layer on top of this chapter's operating layer -- reused unchanged, not redefined.
  • Deep observability/evaluation methodology and infrastructure-layer production engineering are both deliberately deferred to llm-evaluation-for-everyone and ai-engineering-for-everyone respectively.
