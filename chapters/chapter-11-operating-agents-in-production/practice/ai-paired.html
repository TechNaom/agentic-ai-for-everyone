Now Pair With an AI

A ninth scenario, not in the eight above: an overnight confirmation system, "NotaryBot" (the specific company is left unnamed on purpose, the same way Chapter 10's "NegotiatorBot" scenario did), which confirms document approvals for two peer agents. Two real, layered problems were found in the same incident report. First: a retry wrapper de-duplicated "the same" confirmation call by comparing the FULL raw argument JSON of each attempt -- and a routine retry, whose arguments drifted slightly between attempts, was treated as a brand-new confirmation and committed a second time, double-billing the client. Second, in the same incident: the on-call engineer's only diagnostic was "something failed around 2 AM" -- there was no structured log and no correlation id, so there was no way to tell which agent, which call, or which retry attempt actually caused the duplicate.

Step 1: Diagnose it yourself, first

Before reading further: name the two distinct problems here using this chapter's vocabulary (one is about how "sameness" was defined for a retried call; the other is about what's missing to investigate an incident after the fact) and write your own fix for each. There's no grading here, just your own reasoning to compare against Step 3.

Step 2: Ask an AI assistant

Thought process: this scenario has two layered problems (a wrong idempotency definition AND missing structured logging), so the prompt needs to ask the AI to find both, not just the more obviously costly one -- a shallow prompt like "why was the client double-billed?" invites an answer that fixates on the idempotency bug (the one with a visible financial consequence) and never questions why the incident took hours to diagnose at all, which is a separate, equally real gap.

Write the prompt you'd give an AI assistant:

Paste your prompt into your assistant of choice and compare its answer against the critique below.
Show a strong version of this prompt 
Here's my production agent's incident report: [paste the scenario above]. Identify EVERY distinct problem in this report, not just the first one you notice -- there are two -- and name each using this chapter's vocabulary (a wrong idempotency-key definition, versus missing structured logging with a correlation id). Propose a concrete, specific fix for each, including exactly what fields the idempotency key should be built from and what the structured log line for each attempt should contain.

Step 3: Critique what came back

What a complete diagnosis catches
  • Problem 1 (idempotency keyed on raw arguments): this chapter's own Section 4 live result showed the SAME retried request produce two different argument shapes -- de-duplicating by comparing full argument JSON is exactly the mistake that lets a legitimate retry commit twice. The fix is an idempotency key built from the fields that DEFINE the side effect (agent, document id, action), run through commit_once.
  • Problem 2 (no structured log, no correlation id): this chapter's own Section 9-10 built structured JSON-line logging with a shared correlation id specifically so a bad run can be attributed AFTER it happens, without a live process to interrogate. "Something failed around 2 AM" is the symptom of having none of that.
  • A shallow AI answer often catches only Problem 1 (the more visible, costly bug) and misses that Problem 2 means EVERY future incident on this system will be just as hard to diagnose, not only this one.

Compare the AI's answer against your own Step 1 notes and the two-problem breakdown above. Did it catch both? Did it propose the right fix for each -- a narrower idempotency key and structured logging with a correlation id -- or did it conflate the two into one vague "add better error handling" suggestion?
