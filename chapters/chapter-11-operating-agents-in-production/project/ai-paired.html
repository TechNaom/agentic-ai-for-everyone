Chapter 11 Project — Solo → AI-Paired → Critique 25 min

Now Pair With an AI

You already built the project yourself on Wrenfield Dispatch Alliance's ClaimScout and ShipScout. Now a fourth scenario, Hollowgate Courier Network (a fictional regional courier network) and its two peer agents PickupScout and DropoffScout, gets built a second way: by prompting an AI assistant for an overnight operating harness, and reviewing what it hands back with the same skepticism you'd bring to a coworker's pull request before trusting its retry handling with real side effects.

Step 1: Design it yourself, first

PickupScout and DropoffScout must confirm overnight pickups and drop-offs unattended. Before reading further, sketch your own design: what should happen if the SAME confirmation call is retried and its arguments drift slightly between attempts (a genuine live quirk, not a hypothetical)? What should happen if a call fails every single time it's attempted? There's no grading here, just your own design to compare against Step 3.

Step 2: Ask an AI assistant to build the same thing

Thought process: the prompt needs to state explicitly that the idempotency key must be built from a NARROW set of fields that define the side effect, not the full call-argument payload, and that retries must be bounded with every attempt logged -- otherwise a rushed AI answer tends to write a "safe-looking" retry wrapper that de-duplicates on raw argument equality, which still leaves the exact double-commit risk this chapter's own Section 4 found live wide open, just harder to spot on a quick read.

Write the prompt you'd give an AI assistant:

Paste your prompt into your assistant of choice, save its response separately, and compare it against the checklist below before looking at this chapter's own lesson pattern.
Show a strong version of this prompt 
Write Python stdlib-only production-operating code for two agents, pickupscout and dropoffscout, confirming overnight courier steps unattended. I need: (1) an idempotency_key(agent, order_id, action) function built from exactly those three fields, NOT the raw call arguments; (2) a commit_once(key, effect_fn) function where the check-for-existing-key and the write happen inside ONE single lock -- not two separately-locked steps -- and a repeated key replays the FIRST result without re-running effect_fn; (3) a call_with_retries(fn, max_attempts, base_delay) function with exponential backoff that logs every attempt (success or failure) and raises a RetriesExhausted exception, never silently returning None, if every attempt fails; (4) a run_harness(cases) function that walks a list of confirmation cases through call_with_retries and commit_once together, reporting which cases succeeded, which were replayed (not double-committed), and which exhausted their retries. Use only the Python standard library -- no LangGraph, CrewAI, AutoGen, or external logging/observability framework.

Step 3: Review it against this checklist

What a rushed AI-generated operating harness tends to get wrong
  • An idempotency key built from raw arguments. Does the generated code de-duplicate by comparing the full call-argument payload rather than a deliberately narrow key -- the exact gap this chapter's own Section 4 live result exposes?
  • Two separately-locked steps instead of one atomic commit. Does the generated commit_once acquire a lock, check, release it, then acquire AGAIN to write -- leaving a window where a second call can slip through and re-run effect_fn -- or is the check-and-write genuinely one locked block, matching this chapter's own Section 5 pattern?
  • A retry wrapper that swallows total failure silently. Does the generated code return None or an empty result with no error and no log line when every attempt fails, or does it raise a specific exception AND log the exhaustion, matching this chapter's own Section 6 pattern?

Now compare the AI's code against this chapter's own lesson pattern (Sections 4-6, 11) and against solution.py in the project folder. Where do they differ? Does the AI's version genuinely key idempotency on a narrow, deliberate set of fields, or does it just add a check that LOOKS safe on a quick read?
