Chapter 11 — Solo → AI-Paired → Critique 20 min

Now Pair With an AI

You already worked the exercises yourself on Cindermoor Parcel Network's SortScout and RouteScout. Now a third scenario, Thistlebrook Fulfillment Co-op (a fictional order-fulfillment cooperative) and its two peer agents PickScout and PackScout, gets built a second way: by prompting an AI assistant for a production-operating layer, and reviewing what it hands back with the same skepticism you'd bring to a coworker's pull request before trusting its retry handling with real side effects.

Step 1: Design it yourself, first

PickScout and PackScout must run unattended overnight, confirming picks and packs for incoming orders. Before reading further, sketch your own plan: what field(s) would you build an idempotency key from, so a retried "confirm this pack" call never double-commits? How would you decide what counts as a per-call vs. a per-agent vs. a per-exchange timeout for this system? What would a structured log line for a single commit need to contain for you to answer "which agent caused this" a week later, from the log alone? There's no grading here, just your own design to compare against Step 3.

Step 2: Ask an AI assistant to build the same thing

Thought process: the prompt needs to state explicitly that the idempotency key must be built from the fields that DEFINE the side effect (not the raw call arguments), that retries must be BOUNDED with backoff (never silently unbounded), and that the run summary must be computed by RE-PARSING the log rather than from an in-process counter -- otherwise a rushed AI answer tends to produce a retry wrapper that de-duplicates on raw argument equality (which this chapter's own Section 4 live result shows can fail even for "the same" action) and a summary that reports zero for everything the moment the process is restarted mid-run.

Write the prompt you'd give an AI assistant:

Paste your prompt into your assistant of choice, save its response separately, and compare it against the checklist below before looking at this chapter's own lesson pattern.
Show a strong version of this prompt 
Write Python stdlib-only production-operating code for two agents, pickscout and packscout, confirming order fulfillment steps unattended overnight. I need: (1) an idempotency_key function built from the fields that DEFINE a side effect (agent, order_id, action), NOT the raw call arguments; (2) a commit_once function that runs an effect exactly once per key and replays the first result on any later call with the same key; (3) a bounded retry wrapper with exponential backoff that logs every attempt, including final exhaustion, and never retries unboundedly; (4) three independent timeout functions -- one for a single call, one for one agent's own overall loop, and one for a whole multi-message exchange between the two agents; (5) a structured logging function that writes one JSON line per event (dispatch, retry, timeout, commit) tagged with a shared correlation id for the whole run; (6) a run-summary function that computes success rate, retries used, timeouts hit, and commits ENTIRELY by re-parsing those log lines, not from any counter held in memory during the run. Use only the Python standard library -- no LangGraph, CrewAI, AutoGen, or external logging/observability framework.

Step 3: Review it against this checklist

What a rushed AI-generated operating layer tends to get wrong
  • An idempotency key built from raw arguments. Does the generated code de-duplicate by comparing the full call-argument payload rather than a deliberately narrow key (agent, order_id, action) -- the exact gap this chapter's own Section 4 live result exposes (two real calls for "the same" action had different raw JSON)?
  • An unbounded or un-logged retry loop. Does the generated retry wrapper have a hard `max_attempts`, and does it log EVERY attempt including the final exhaustion -- or does it retry "until it works," with no record of how many tries that actually took?
  • A run summary computed from in-memory counters. Does the generated summary function read from variables that were only ever held in the running process's memory, or does it re-parse the structured log file -- the distinction that determines whether the summary survives the process crashing mid-run?

Now compare the AI's code against this chapter's own lesson pattern (Sections 5-6, 9, 11) and against solution.py in the exercises folder. Where do they differ? Does the AI's version actually recompute its summary from durable state, or does it just look correct in a clean, uninterrupted test run?
