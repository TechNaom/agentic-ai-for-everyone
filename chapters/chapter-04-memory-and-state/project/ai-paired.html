Chapter 4 Project — Solo → AI-Paired → Critique 20 min

Now Pair With an AI

You already built CareBot's fact-promotion function yourself. Now try the reverse: describe the same task to an AI assistant without showing it your own solution, and review what it hands back with the same scrutiny you'd bring to a teammate's pull request before merging it into Hollowridge Wellness Clinic's real intake system.

Step 1: Have the AI build it independently

Thought process: the prompt needs to make explicit that a patient may already have OTHER facts on file before this write happens — otherwise the AI has no reason to load existing state first, and will likely write a version that only ever handles a patient's very first fact correctly, which is exactly the blind-overwrite bug this exercise is designed to surface.

Write the prompt you'd give an AI assistant:

Paste your prompt into your assistant of choice, save its response separately, and compare it against the checklist below before looking at this project's own solution.py.
Show a strong version of this prompt 
Write a Python function promote_worthy_and_persist(patient_id, user_messages, store) for a clinic intake agent. `store` is a MemoryStore instance with these methods already implemented: store.get(patient_id) -> {"conditions": [...], "preferences": [...]} (loads existing state, read-only), store.add_condition(patient_id, note) -> appends note to that patient's conditions and saves (already read-modify-write internally), store.add_preference(patient_id, note) -> same for preferences. `user_messages` is a list of strings from ONE visit. The function should classify each message with an already-given is_promote_worthy(text) helper that returns "condition", "preference", or None, call the matching store method for each promote-worthy message, and return store.get(patient_id) at the end reflecting everything just written. Assume this patient may ALREADY have prior conditions/preferences on file from an earlier, separate visit -- your function must not lose them. Do not use any agent framework.

Step 2: Review it against this checklist

What a rushed AI-generated fact-promotion function tends to get wrong
  • Bypassing the given `add_condition`/`add_preference` methods and writing to the store directly. Since those methods already do read-modify-write internally, a version that calls them correctly is safe by construction — but does the generated code actually call them, or does it reach into some other save path (or reconstruct a facts dict itself) that skips the existing-state load and silently reproduces the lesson's own blind-overwrite bug?
  • Only handling the first promote-worthy message per category. If a visit has TWO condition statements, does the generated code promote both, or does an early `return`/`break` after the first match silently drop the second?
  • Calling `store.get(patient_id)` once at the top and returning that stale value at the end, instead of re-fetching after all the writes have happened — this is the same stale-snapshot mistake the lesson's Section 15 caught in its own finished agent, just in a different function.

Now compare the AI's code against solution.py in this same folder. Where do they differ? Is the AI's version genuinely equivalent, or does it handle one of the three watch-outs above differently — and is that difference actually a bug, or a legitimate different design choice?
