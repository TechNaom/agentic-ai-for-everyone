Chapter 4 of 13 Intermediate 50 min read, hands-on

Memory and State

Chapters 1-3 built an agent that reasons, calls tools, and recovers from tool failure — all within one run, one process, one call to run_agent(). Every one of those agents forgets everything the instant the function returns. This chapter adds the layer that lets an agent carry state across runs: short-term working memory (what lives inside one run's own context — the conversation so far, tool results, the working plan) versus long-term persisted memory (what survives after the process exits and gets picked back up correctly in a genuinely separate, later run). Both halves are demonstrated for real this chapter: two truly separate Python processes, a real JSON file on disk between them, and a real bug (a blind overwrite that silently deleted an already-persisted fact) caught while testing and fixed on the page.

Larkspur Fitness Studio is a fictional gym. Its coaching agent, CoachBot, talks to each member across many separate sessions — a phone call today, a chat message next week, an in-app check-in the week after. Midway through today's session, a member mentions their left knee has been sore since Tuesday. CoachBot should never suggest a heavy squat day again until that's resolved — not just for the rest of today's conversation, but in every future session, including ones that start as a completely fresh process with no memory of today at all. Chapters 1-3's agents have no mechanism for this whatsoever: their entire "memory" is a Python list that dies with the process. This chapter builds the mechanism that fixes that, and nothing more exotic than a JSON file and a few functions is needed to do it honestly.

1. Two kinds of memory, defined against Chapters 1-3

Every agent this course has built so far already has working memory — it just never had a name, because there was never a second kind to distinguish it from:

What is... short-term working memory? The list of messages (conversation history, tool calls, tool results) that lives inside one run of the agent loop — exactly the messages list Chapter 1's run_agent() built and fed back into the model on every iteration. It exists only as long as the process holding it is alive. When the function returns, or the process exits, it's gone. This is not a flaw to fix; short-term memory is supposed to be scoped to one run — the problem this chapter solves is that some facts need to outlive that scope, and working memory alone has no way to do that.
What is... long-term persisted memory? Facts written to storage that survives past the process exiting — a file, a database row, anything durable — and gets read back and correctly merged into a later, separate run's own working memory. Unlike working memory, persisted memory is deliberately small and selective: it holds facts worth carrying forward (an injury, a stated preference, a past outcome), not the full transcript of every conversation that ever happened.

The tools CoachBot needs, mostly unrelated to memory itself — this chapter doesn't re-teach Chapters 1-3's tool-calling mechanics, but CoachBot still needs real tools to reason about:

tools.py
MEMBERS = {"mem-14": {"name": "Priya", "goal": "strength"}}
WORKOUT_LOG = {"mem-14": [{"date": "2026-09-10", "type": "squat_day", "notes": "5x5 at 185lb"}]}

def get_member_profile(member_id):
    return MEMBERS.get(member_id, {"error": f"no member on file for '{member_id}'"})

def get_last_workout(member_id):
    log = WORKOUT_LOG.get(member_id, [])
    return log[-1] if log else {"error": f"no workout history for '{member_id}'"}

def log_workout(member_id, workout):
    WORKOUT_LOG.setdefault(member_id, []).append(workout)
    return {"logged": True, "member_id": member_id, "workout": workout}

print(get_member_profile("mem-14"))
print(get_last_workout("mem-14"))

This chapter defers deep retrieval methodology — semantic search, embeddings, vector similarity — to context-engineering-for-everyone entirely, per this course's own cross-course boundary (see docs/discovery-notes.md). Every persisted-memory mechanism below is a plain key lookup: no vector database, no embedding model, because the architectural short-term/long-term split is this chapter's job, not retrieval quality.

3. The naive baseline: an agent with only working memory

The failure this chapter fixes, demonstrated directly before any fix is introduced — an agent whose only memory is its own working-memory list, with no persisted store at all:

Why this isn't a strawman
This is exactly what happens if a team builds Chapters 1-3's tool-calling agent, ships it, and never adds a persisted store — which is the default state of any agent built strictly from those three chapters. Nothing crashes. Nothing errors. The agent just behaves as if every session is the member's first, forever, because structurally, as far as its own code is concerned, it is.

4. A minimal persisted-memory store, in plain code

The fix doesn't need a database engine or a framework — a plain JSON file and three functions are the entire mechanism, matching this course's no-heavy-framework policy exactly:

memory_store.py
import json, os

MEMORY_PATH = "coachbot_memory.json"

def load_all_memory(path=MEMORY_PATH):
    if not os.path.exists(path):
        return {}
    with open(path, "r") as f:
        return json.load(f)

def load_member_memory(member_id, path=MEMORY_PATH):
    return load_all_memory(path).get(member_id, {"injuries": [], "preferences": [], "prs": {}})

def save_member_memory(member_id, facts, path=MEMORY_PATH):
    all_memory = load_all_memory(path)
    all_memory[member_id] = facts
    with open(path, "w") as f:
        json.dump(all_memory, f, indent=2)
    return facts

def remember_injury(member_id, injury_note, path=MEMORY_PATH):
    facts = load_member_memory(member_id, path)
    facts["injuries"].append(injury_note)
    return save_member_memory(member_id, facts, path)

Run for real, proving the round trip works before anything else is built on top of it:

Output (real) 
before any write: {'injuries': [], 'preferences': [], 'prs': {}}
after write: {'injuries': ['left knee soreness reported 2026-09-24'], 'preferences': [], 'prs': {}}
Why a plain JSON file is enough to teach this
A real production system would likely use a real database (SQLite, Postgres, Redis) instead of a single flat file, for concurrency and scale reasons this chapter doesn't need to solve. But the architectural mechanism — load existing state, read a key, write a key back, survive past process exit — is identical either way. Swapping this file's read/write functions for real database calls later doesn't change anything else in this chapter's design.

5. Proof across two genuinely separate processes

The strongest possible demonstration that this is real persistence, not just a variable living a bit longer in the same script: two separate files, run as two separate python3 invocations, with the second one started only after the first has fully exited.

session1.py
from memory_store import remember_injury

working_memory = []  # short-term: this process's own conversation history
working_memory.append({"role": "user", "content": "Hey CoachBot, what's on my plan today?"})
working_memory.append({"role": "assistant", "content": "Squat day, following your last block."})
working_memory.append({"role": "user", "content": "Actually my left knee has been sore since Tuesday."})

remember_injury("mem-14", "left knee soreness reported 2026-09-24")
print(f"Session 1 working memory has {len(working_memory)} messages.")
print("Session 1 persisted the injury fact and is now exiting -- working_memory is about to be lost.")
session2.py
from memory_store import load_member_memory
from tools import get_last_workout

def build_context(member_id):
    working_memory = []  # fresh -- proves nothing survived from session1.py's process
    facts = load_member_memory(member_id)
    if facts["injuries"]:
        injury_summary = "; ".join(facts["injuries"])
        working_memory.append({"role": "system", "content": f"Known member history (persisted, from a prior session): {injury_summary}"})
    return working_memory, facts

def suggest_todays_plan(member_id):
    working_memory, facts = build_context(member_id)
    last = get_last_workout(member_id)
    if facts["injuries"]:
        plan = f"Modified session (knee-aware) -- last logged: {last.get('type')}. Avoid heavy squats/lunges; suggest upper body + light mobility."
    else:
        plan = f"Standard progression from last logged session: {last.get('type')}."
    working_memory.append({"role": "assistant", "content": plan})
    return working_memory

convo = suggest_todays_plan("mem-14")
print(f"Session 2 starts with {len(convo)} messages already in working memory (0 would mean the fact was lost).")
for m in convo:
    print(f"  [{m['role']}] {m['content']}")
Output (real, run as two separate `python3` processes, second one after the first fully exited) 
$ python3 session1.py
Session 1 working memory has 3 messages.
Session 1 persisted the injury fact and is now exiting -- working_memory is about to be lost.

$ python3 session2.py
Session 2 starts with 2 messages already in working memory (0 would mean the fact was lost).
  [system] Known member history (persisted, from a prior session): left knee soreness reported 2026-09-24
  [assistant] Modified session (knee-aware) -- last logged: squat_day. Avoid heavy squats/lunges; suggest upper body + light mobility.

Session 2's own working_memory starts as a genuinely empty list, in a Python interpreter that has never run Session 1's code. The only reason it knows about the knee is the load_member_memory call at the top of build_context — remove that one call, and Section 3's naive failure returns immediately, in this exact scenario.

6. Deciding what to persist: promote-worthy vs. routine

Persisting every message would work mechanically but defeats the point — a store meant to hold a few durable facts would fill with "what's on my plan today?" and "cool, thanks!" a thousand times over. This decision — is this specific message worth writing to long-term storage? — was tested live against the local model this session:

promote_check.py
import time
from openai import OpenAI
client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

def classify_promote_worthy(message_text):
    t0 = time.monotonic()
    resp = client.chat.completions.create(
        model="llama3.2:latest",
        messages=[
            {"role": "system", "content": (
                "Classify whether the user's message states a durable fact worth "
                "remembering across future sessions (an injury, a lasting preference, "
                "a schedule constraint) versus routine small talk or a one-off question. "
                "Reply with exactly one word: PERSIST or SKIP."
            )},
            {"role": "user", "content": message_text},
        ],
        extra_body={"keep_alive": "120m"},
    )
    return resp.choices[0].message.content.strip(), time.monotonic() - t0

MESSAGES = [
    "what's on my plan today?",
    "my left knee has been sore since Tuesday",
    "can we start ten minutes earlier next time, mornings work better for me",
    "cool, thanks!",
]
for msg in MESSAGES:
    label, elapsed = classify_promote_worthy(msg)
    print(f"{elapsed:5.2f}s  {label!r:12}  <- {msg!r}")
Output (real, live Ollama call, captured this session) 
 9.51s  'SKIP'        <- "what's on my plan today?"
 1.34s  'PERSIST'     <- 'my left knee has been sore since Tuesday'
 1.66s  'PERSIST'     <- 'can we start ten minutes earlier next time, mornings work better for me'
 1.07s  'SKIP'        <- 'cool, thanks!'

All four real, live classifications were correct: the two durable facts (an injury, a scheduling preference) were flagged PERSIST; the routine question and the pure small talk were flagged SKIP. The finished agent in Section 15 uses a deterministic keyword-based stand-in for this same decision — the same policy Chapters 1-3's finished reference agents used for their own live-model steps, so the assembled file runs without Ollama for grading, but the mechanism itself, live, is proven right here.

What is... the actual promotion rule this chapter uses? A message is promote-worthy if it states something that should change future behavior — an injury or health note, a lasting preference, a schedule constraint, a correction to a previously stated fact. It is not promote-worthy if it's a one-off question, an acknowledgment, or small talk that has no bearing on any future session. Getting this filter wrong in either direction has a real cost: too permissive, and the store fills with noise that dilutes the facts that matter; too strict, and Section 3's exact failure returns for facts that should have been caught.

7. Multiple fact categories, and key-lookup isolation

Injuries and preferences aren't the only durable fact type CoachBot needs — a personal record (PR) is a third category, updated by a different tool entirely, but stored the same way:

memory_store.py (continued)
def record_pr(member_id, lift, weight_lb, path=MEMORY_PATH):
    facts = load_member_memory(member_id, path)
    facts["prs"][lift] = weight_lb
    return save_member_memory(member_id, facts, path)

record_pr("mem-14", "squat", 190)
record_pr("mem-14", "deadlift", 225)
print(load_member_memory("mem-14"))
Output (real) 
{'injuries': [], 'preferences': [], 'prs': {'squat': 190, 'deadlift': 225}}

Retrieval is a plain key lookup, keyed on member_id — no similarity search, no risk of one member's facts leaking into another's context, proven directly with two real members on file at once:

isolation_check.py
save_member_memory("mem-14", {"injuries": ["left knee soreness"], "preferences": [], "prs": {}})
save_member_memory("mem-22", {"injuries": [], "preferences": ["prefers evening sessions"], "prs": {}})
print("mem-14:", load_member_memory("mem-14"))
print("mem-22:", load_member_memory("mem-22"))
print("mem-14 sees mem-22's data:", "evening" in str(load_member_memory("mem-14")))
Output (real) 
mem-14: {'injuries': ['left knee soreness'], 'preferences': [], 'prs': {}}
mem-22: {'injuries': [], 'preferences': ['prefers evening sessions'], 'prs': {}}
mem-14 sees mem-22's data: False
Why this is worth proving, not just assuming
A dict keyed on member_id, one JSON file, is the entire isolation mechanism — no access-control layer, no query filter to get wrong. This is also exactly why this chapter's scope stays a plain key-value store: the moment retrieval needs to be "find facts similar to X across all members" rather than "get this one member's own facts," that's a different problem (semantic search), and this course hands it to context-engineering-for-everyone rather than solving it here.

8. A live, memory-grounded reply

Every mechanism so far has been about getting the right facts into a Python data structure. The actual point is feeding those facts to the model as real context, so its real reply reflects them — tested live, this session:

The model was never told anything about knees or mornings in its own training — every specific, correct detail in that reply (the knee, the morning-session preference) came entirely from the system_context string this session's own persisted-memory mechanism built. The contrast makes this unambiguous: the identical question, asked with no persisted facts injected at all:

live_ungrounded_reply.py
resp = client.chat.completions.create(
    model="llama3.2:latest",

No knee, no morning preference, no awareness anything was ever said before — a generic, plausible-sounding reply that would have been actively wrong to give a member with a sore knee. This is the whole payoff of Sections 4-8: a real, live, personalized reply is only as good as the memory mechanism that fed it, and the same model produces a materially different, worse answer the instant that mechanism is removed.

9. A genuine bug: blind overwrite, not merge

While building this chapter's finished agent, a first draft of a second promotion function — remember_preference, meant to add a scheduling preference alongside an already-persisted injury — was tested against a member who already had a fact on file, and it failed for real:

overwrite_bug.py (first draft, buggy)
def remember_preference_BUGGY(member_id, pref_text, path=MEMORY_PATH):
    # Bug: constructs a fresh facts dict instead of loading the existing one
    # first -- any injuries or other preferences already on file are lost.
    facts = {"injuries": [], "preferences": [pref_text], "prs": {}}
    return save_member_memory(member_id, facts, path)

save_member_memory("mem-14", {"injuries": ["left knee soreness reported 2026-09-24"], "preferences": [], "prs": {}})
print("before remember_preference_BUGGY:", load_all_memory()["mem-14"])
remember_preference_BUGGY("mem-14", "prefers morning sessions")
print("after remember_preference_BUGGY: ", load_all_memory()["mem-14"])
Output (real, the bug as actually observed) 
before remember_preference_BUGGY: {'injuries': ['left knee soreness reported 2026-09-24'], 'preferences': [], 'prs': {}}
after remember_preference_BUGGY:  {'injuries': [], 'preferences': ['prefers morning sessions'], 'prs': {}}
BUG CONFIRMED: the injury fact is gone -- overwritten, not merged.
Why this is the same class of bug as prior chapters' honest examples
This is the same "an unscripted failure surfaced by testing became the lesson's own honest example" pattern as Chapter 1's Cedar Hollow bug and Chapter 3's retry-timeout bug — not manufactured for the page. The function's own logic is completely correct in isolation; the bug only appears once a member already has a persisted fact on file before the second promotion call runs, which is precisely the scenario a real multi-visit member hits on their second-ever promoted fact.

10. The fix: read-modify-write

The fix loads the member's existing facts first, then appends to them — the same discipline Section 4's remember_injury already used correctly, which is why that first function never showed this bug:

overwrite_fix.py
def remember_preference_FIXED(member_id, pref_text, path=MEMORY_PATH):
    facts = load_all_memory(path).get(member_id, {"injuries": [], "preferences": [], "prs": {}})
    facts["preferences"].append(pref_text)
    return save_member_memory(member_id, facts, path)

save_member_memory("mem-14", {"injuries": ["left knee soreness reported 2026-09-24"], "preferences": [], "prs": {}})
print("before remember_preference_FIXED:", load_all_memory()["mem-14"])
remember_preference_FIXED("mem-14", "prefers morning sessions")
print("after remember_preference_FIXED: ", load_all_memory()["mem-14"])
Output (real, fixed) 
before remember_preference_FIXED: {'injuries': ['left knee soreness reported 2026-09-24'], 'preferences': [], 'prs': {}}
after remember_preference_FIXED:  {'injuries': ['left knee soreness reported 2026-09-24'], 'preferences': ['prefers morning sessions'], 'prs': {}}

Both facts now coexist after the fix, matching what actually happened across the member's real history. This pattern — read-modify-write, not blind-write — is this chapter's single most important persisted-memory rule, and it's used everywhere writes happen for the rest of this chapter, including the finished agent in Section 15.

One more edge case worth confirming before trusting the fix: a member with no prior file on disk at all — the very first write of their entire history — needs to work too, not just the already-has-a-record case shown above:

overwrite_fix.py (edge case)
if os.path.exists(MEMORY_PATH):
    os.remove(MEMORY_PATH)
print("no file on disk yet:", os.path.exists(MEMORY_PATH))
remember_preference_FIXED("mem-99", "prefers text reminders")
print(load_all_memory()["mem-99"])
Output (real) 
no file on disk yet: False
{'injuries': [], 'preferences': ['prefers text reminders'], 'prs': {}}

load_all_memory's own os.path.exists check (Section 4) is what makes this safe — the very first write for any member falls back to the default empty-facts shape instead of crashing on a missing file.

Read-modify-write fixes the blind-overwrite bug, but it introduces a second, related question: what happens when a new fact contradicts an old one, rather than just adding to it? A member reporting their knee is fine now shouldn't leave the original injury note sitting there, unqualified, forever:

correction.py
def naive_append_only(member_id, note, path=MEMORY_PATH):
    facts = get_member_memory(member_id, path)
    facts["injuries"].append(note)
    return save_member_memory(member_id, facts, path)

naive_append_only("mem-14", "left knee soreness reported 2026-09-24")
naive_append_only("mem-14", "knee feels fine now, no more soreness")
print(get_member_memory("mem-14"))
Output (real) 
{'injuries': ['left knee soreness reported 2026-09-24', 'knee feels fine now, no more soreness'], 'preferences': [], 'prs': {}}
BUG: both the original injury AND the all-clear are now permanently listed as separate 'injuries' -- a future session can't tell which is current.

Read-modify-write alone doesn't fix this — it correctly merged both facts in, which is exactly the problem. A correction needs its own handling, replacing the specific fact it resolves rather than appending alongside it:

correction.py (continued)
def resolve_injury(member_id, resolved_text, path=MEMORY_PATH):
    facts = get_member_memory(member_id, path)
    facts["injuries"] = [i for i in facts["injuries"] if "RESOLVED" not in i]
    facts["injuries"].append(f"RESOLVED: {resolved_text}")
    return save_member_memory(member_id, facts, path)

resolve_injury("mem-14", "knee soreness cleared as of 2026-09-24")
print(get_member_memory("mem-14"))
Output (real) 
{'injuries': ['left knee soreness reported 2026-09-24', 'RESOLVED: knee soreness cleared as of 2026-09-24'], 'preferences': [], 'prs': {}}
Why this is a distinct concern from read-modify-write, not a restatement of it
Read-modify-write answers "did this write destroy a fact that should have survived?" A correction answers a different question: "does the store's current state accurately reflect the world right now?" A member's original injury note stays visible as history (useful context), but a real system would also check whether injuries contains an unresolved entry before treating the member as currently injured — a detail Section 15's finished agent keeps simple on purpose, since the full correction-and-conflict-resolution problem belongs to this chapter's own broader "what to keep vs. forget" question, not a solved subproblem worth over-engineering here.

11. Token-budget pressure: working memory can't grow forever

Section 5 solved persisting a fact across sessions. A separate problem exists within one long session: working memory that just appends forever eventually doesn't fit in the model's context window. A rough token estimate (characters divided by 4, the common approximation used when a real tokenizer isn't wired in) is enough to see the shape of the problem — exact tokenizer accounting is this course's Chapter 8 cost/latency subject, not this chapter's:

token_pressure.py
def estimate_tokens(text):
    return max(1, len(text) // 4)  # rough approximation, not a real tokenizer

def running_token_count(messages):
    total, counts = 0, []
    for m in messages:
        total += estimate_tokens(m["content"])
        counts.append(total)
    return counts

counts = running_token_count(CONVERSATION)  # 12 real coaching-session turns
for i, (m, c) in enumerate(zip(CONVERSATION, counts), start=1):
    print(f"turn {i:2} ({m['role']:9}): +{estimate_tokens(m['content']):3} tokens -> running total {c:4}")
Output (real)

turn  2 (assistant): + 18 tokens -> running total   24
turn  3 (user     ): + 15 tokens -> running total   39
turn  4 (assistant): + 36 tokens -> running total   75

A real multi-hour coaching relationship easily reaches thousands of turns -- unbounded growth is not viable.
What is... the actual failure mode of unbounded working memory? Two, not one. First, cost and latency: every turn re-sends the entire growing history to the model, so cost per turn keeps climbing even though the useful new information per turn stays constant (Chapter 8's full subject). Second, and this chapter's concern: eventually the buffer exceeds what the model can actually attend to well, and the model's own reasoning quality degrades on the earliest, buried context — long before a hard token-limit error would even trigger.

12. Pruning and summarizing a working-memory buffer

The fix keeps the most recent turns verbatim (recency matters most for coherence) and replaces everything older with one rolling summary — generated live by the local model, not fabricated, and budgeted the same way as every other live call this chapter:

prune_summarize.py
BUDGET_TOKENS = 150
KEEP_LAST = 4

def summarize_for_real(messages_to_summarize):
    transcript = "\n".join(f"{m['role']}: {m['content']}" for m in messages_to_summarize)
    resp = client.chat.completions.create(
        model="llama3.2:latest",
        messages=[
            {"role": "system", "content": (
                "Summarize this coaching conversation excerpt in one short sentence, "
                "keeping any durable facts (injuries, preferences, numbers) and dropping "
                "small talk."
            )},
            {"role": "user", "content": transcript},
        ],
        extra_body={"keep_alive": "120m"},
    )
    return resp.choices[0].message.content.strip()

def prune_if_over_budget(messages, budget_tokens=BUDGET_TOKENS, keep_last=KEEP_LAST):
    total = sum(estimate_tokens(m["content"]) for m in messages)
    if total <= budget_tokens or len(messages) <= keep_last:
        return messages, False
    to_summarize, to_keep = messages[:-keep_last], messages[-keep_last:]
    summary_text = summarize_for_real(to_summarize)
    summary_msg = {"role": "system", "content": f"[rolling summary of {len(to_summarize)} earlier turns] {summary_text}"}
    return [summary_msg] + to_keep, True

But look closely at what it didn't capture: the real progress numbers from turn 4 ("up about 15lb on squat... since last month") are gone. The model's summary kept what it judged most salient, not everything — which is exactly Section 14's subject.

13. A prune-safety guard

Rather than hoping the promotion step (Section 6) always ran before pruning does, a guard function can check directly — refusing to let messages containing an unpersisted promote-worthy fact be summarized away:

prune_guard.py
def has_unpersisted_promote_worthy(messages_to_prune, already_persisted_texts):
    for m in messages_to_prune:
        if m["role"] != "user":
            continue
        text = m["content"].lower()
        if any(w in text for w in ["sore", "hurt", "pain", "injury"]):
            if m["content"] not in already_persisted_texts:
                return True
    return False

to_prune = [
    {"role": "user", "content": "My left knee has been sore since Tuesday."},
    {"role": "assistant", "content": "Noted."},
]
print("guard before persisting:", has_unpersisted_promote_worthy(to_prune, already_persisted_texts=set()))
persisted = {"My left knee has been sore since Tuesday."}
print("guard after persisting: ", has_unpersisted_promote_worthy(to_prune, already_persisted_texts=persisted))
Output (real) 
guard before persisting: True
guard after persisting:  False

A pruning function that calls this guard first and promotes anything it flags before summarizing is the concrete implementation of Section 14's central claim — it can't accidentally lose an unpersisted fact to summarization, because it refuses to prune past one until it's safely on disk.

14. Why summarization is not a substitute for persisting a fact

Section 12's own real output makes the point better than a hypothetical could: a real detail (the progress numbers) was silently dropped by summarization, because the summarizer has no way to know which details a different, future system (Section 4's persisted store) actually needs to keep forever. This is a structurally different mechanism from pruning, not a smaller version of it:

MechanismScopeWhat it optimizes forRisk if relied on alone
Pruning/summarizing (Section 12)Within one session's working memoryStaying under the token budget while keeping recent coherenceCan silently drop a detail the summarizer didn't judge important enough
Persisting (Sections 4, 9-10)Across separate sessions, indefinitelyKeeping a specific, deliberately chosen fact correct and available foreverNone, if the promotion step (Section 6) runs before the fact would ever be pruned away

The correct architecture, and this chapter's central claim: promote-worthy facts must be written to the persisted store before pruning/summarization ever runs on the messages that contain them — never rely on a rolling summary to be the thing that remembers an injury or a preference. Section 15's finished agent enforces this ordering directly.

15. The finished CoachBot agent

Persisted memory (Sections 4, 9-10), promotion (Section 6), and the working-context merge (Section 5), assembled into one file CoachBot would actually run across real, separate sessions:

coachbot_agent.py
class MemoryStore:
    """Minimal persisted long-term memory -- one JSON file, one dict per
    member, read-modify-write on every mutation so a save never clobbers
    facts a prior session already wrote."""
    def __init__(self, path=MEMORY_PATH):
        self.path = path

    def _load_all(self):
        if not os.path.exists(self.path):
            return {}
        with open(self.path, "r") as f:
            return json.load(f)

    def get(self, member_id):
        return self._load_all().get(member_id, {"injuries": [], "preferences": [], "prs": {}})

    def _save_all(self, all_memory):
        with open(self.path, "w") as f:
            json.dump(all_memory, f, indent=2)

    def add_injury(self, member_id, note):
        all_memory = self._load_all()
        facts = all_memory.get(member_id, {"injuries": [], "preferences": [], "prs": {}})
        facts["injuries"].append(note)
        all_memory[member_id] = facts
        self._save_all(all_memory)

    def add_preference(self, member_id, note):
        all_memory = self._load_all()
        facts = all_memory.get(member_id, {"injuries": [], "preferences": [], "prs": {}})
        facts["preferences"].append(note)
        all_memory[member_id] = facts
        self._save_all(all_memory)

def is_promote_worthy(message_text):
    """Deterministic stand-in for Section 6's live classification call --
    the assembled reference agent uses this so it's runnable without Ollama,
    the same pattern Chapters 1-3 used for their own finished agents."""
    text = message_text.lower()
    if any(w in text for w in ["sore", "hurt", "pain", "injury", "injured"]):
        return "injury"
    if any(w in text for w in ["prefer", "earlier", "later", "instead of", "rather"]):
        return "preference"
    return None

def build_working_context(member_id, store):
    working_memory = []
    facts = store.get(member_id)
    if facts["injuries"]:
        working_memory.append({"role": "system", "content": f"Known injuries (persisted): {'; '.join(facts['injuries'])}"})
    if facts["preferences"]:
        working_memory.append({"role": "system", "content": f"Known preferences (persisted): {'; '.join(facts['preferences'])}"})
    return working_memory, facts

def run_session(member_id, store, user_messages):
    working_memory, facts = build_working_context(member_id, store)
    for text in user_messages:
        working_memory.append({"role": "user", "content": text})
        category = is_promote_worthy(text)
        if category == "injury":
            store.add_injury(member_id, text)
        elif category == "preference":
            store.add_preference(member_id, text)
    last = get_last_workout(member_id)
    current_facts = store.get(member_id)  # re-check post-write: a fact stated THIS turn should count too
    if current_facts["injuries"]:
        reply = f"Knee-modified plan today -- last logged: {last['type']}. Avoiding heavy loading."
    else:
        reply = f"Standard progression from last logged session: {last['type']}."
    working_memory.append({"role": "assistant", "content": reply})
    return working_memory

Why `current_facts` is re-fetched instead of reusing the `facts` captured at session start
An earlier version of this function used the facts variable captured once at the very top of run_session to decide the reply — and Session 1's own reply came back wrong, still recommending a standard plan, because that snapshot was taken before the injury message was even processed. This is the exact "stale snapshot" bug this chapter's practice bank names directly (Scenario 6) — caught the same way every other bug in this course was: by actually running the code before writing it into the lesson.

16. A pre-production checklist for memory

Sections 3-15 generalize into a classifier, mirroring Chapter 3 Section 14's own checklist pattern, but for the memory layer instead of the tool layer:

checklist.py
def classify_memory_risk(scenario):
    if scenario.get("has_persisted_store") is False:
        return "no persistence -- Section 3's naive-baseline failure"
    if scenario.get("promotes_before_prune") is False:
        return "prune-before-promote -- Section 14's summarization-loss risk"
    if scenario.get("read_before_write") is False:
        return "blind overwrite -- Section 9's merge bug"
    if scenario.get("re_checks_after_write") is False:
        return "stale snapshot -- Section 15's re-fetch fix"
    return "no known risk pattern matched"

print(classify_memory_risk({"has_persisted_store": False}))
print(classify_memory_risk({"has_persisted_store": True, "promotes_before_prune": False}))
print(classify_memory_risk({"has_persisted_store": True, "promotes_before_prune": True, "read_before_write": False}))
print(classify_memory_risk({"has_persisted_store": True, "promotes_before_prune": True, "read_before_write": True, "re_checks_after_write": True}))
Output (real) 
no persistence -- Section 3's naive-baseline failure
prune-before-promote -- Section 14's summarization-loss risk
blind overwrite -- Section 9's merge bug
no known risk pattern matched

The four questions this classifier's branches encode:

  1. Does a fact stated in one session need to correctly inform a later, separate one? If yes, working memory alone can never satisfy that — a persisted store is required (Sections 3-5), not optional.
  2. Is every promote-worthy fact written to the persisted store before the working-memory turns that stated it could ever be pruned or summarized away? If the ordering is reversed, Section 14's exact loss risk applies.
  3. Does every write to the persisted store load the existing record first? If any write path constructs a fresh record instead, Section 9's blind-overwrite bug is waiting for the second fact any given user states.
  4. Does anything that decides behavior mid-session re-check the store after a write, or does it trust a variable captured before the write happened? The latter is Section 15's stale-snapshot bug.

17. GenAI Builder Thought Process

Thought process: the natural first instinct when adding "memory" to an agent is to reach for a vector database and embeddings immediately — but Sections 4-10 show that the actual architectural problem (does a fact survive past this process, and does writing it correctly merge with what's already there) has nothing to do with retrieval quality, and everything to do with two disciplined habits: promote selectively (Section 6) and always read-modify-write (Sections 9-10). A team that gets those two habits wrong will have the exact same bugs with a vector database as with a JSON file — a fancier retrieval layer doesn't fix a blind overwrite underneath it. A strong prompt for an AI pair-programmer extending this chapter's agent: "I have an agent that needs to persist a small number of durable facts about a user (not a full conversation log) to a JSON file, merge them correctly into a fresh session's working context, and never let a later write silently delete an earlier one. Write a MemoryStore class with get/add methods that always load existing state before writing, a promote-worthy classifier that distinguishes durable facts from routine chat, and a working-memory pruning function that only ever summarizes turns whose promote-worthy facts have already been persisted. Do not use an agent framework or a vector database -- plain Python and JSON, and the openai client against local Ollama only for the classification/summarization steps."

In the Real World
  • Customer-support agents that "forget" a customer already explained their issue in a prior chat are almost always missing Section 3's persisted-store step entirely, not failing at some more sophisticated retrieval problem.
  • Section 9's blind-overwrite bug is one of the most common real memory bugs in production agents, precisely because it's invisible on a user's very first interaction — it only appears the second time that same user's record needs to be updated, which is exactly the kind of bug that slips past a demo and only surfaces once real, repeat usage begins.
  • Section 14's summarization-loss risk is why serious production memory systems treat "what to summarize" and "what to persist as a durable fact" as two separate, deliberately designed decisions with two separate code paths — never one mechanism doing both jobs by accident.

Points to Remember

  • Short-term working memory is the conversation/tool-result list scoped to one run — it was already present in every agent Chapters 1-3 built, and it dies with the process, by design.
  • Long-term persisted memory is a deliberately small, selective set of facts written to storage that survives past process exit and gets correctly merged into a later, separate session's own working memory — proven this chapter across two genuinely separate python3 processes sharing one JSON file.
  • Deciding what to promote to long-term storage (Section 6) is its own decision, live-tested against the real model this session — durable facts (injuries, preferences, constraints) get promoted; routine chat doesn't.
  • Persisted writes must be read-modify-write, never blind-write (Sections 7-8) — a genuine bug this session showed a second promoted fact silently deleting the first one until the fix loaded existing state before writing.
  • Working memory needs pruning/summarizing under token-budget pressure (Sections 11-12), but summarization is not a substitute for persisting a fact (Section 14) — this session's own real summarization call silently dropped a real detail, which is exactly why promote-worthy facts must be persisted before the turns containing them are ever pruned.
  • No vector database or embedding framework was used anywhere in this chapter — every persisted-memory mechanism is a plain JSON file and a few read-modify-write functions, per this course's explicit deferral of retrieval methodology to context-engineering-for-everyone.
  • No agent framework was used anywhere in this chapter — every function is plain Python and, where a live reasoning step is genuinely needed (Sections 2, 6, 10), the plain openai client against local Ollama, the same pattern Chapters 1-3 used.
