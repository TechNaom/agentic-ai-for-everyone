Tool Use and Function Calling

Chapters 1-2 already called tools — a JSON schema, a decision, an execution, an observation fed back in. That mechanics is assumed knowledge now. What neither chapter had to face is what happens when more than one tool could plausibly answer the same question, when a real argument arrives in a format nobody planned for, or when a tool call comes back looking successful but isn't. This chapter treats the tool layer as its own discipline: choosing the right tool among genuine candidates, forming correct arguments under realistic drift, and handling three distinct kinds of tool failure with three distinct policies — not one undifferentiated "retry on error."

Palisade Broadband is a fictional regional internet provider. Its support agent, NetBot, has five tools, and three of them are genuine, overlapping candidates for the single most common request it receives: "my internet is down." An area outage explains it. A suspended account (non-payment) explains it. A bad physical line explains it. All three are real, all three are plausible, and picking the wrong one first doesn't crash anything — it just wastes a call, delays the actual answer, and (worst case) tells a customer their line was diagnosed as fine when the real problem was their bill. Chapters 1-2's tools never had this problem: their tool sets were built so each tool answered a distinct question. NetBot's aren't, on purpose, because production tool sets usually aren't either.

1. Five tools, three of which overlap

The tools themselves, plain functions again, no framework, matching Chapters 1-2's pattern exactly:

tools.py
OUTAGES = {
    "27601": {"outage": True, "eta_minutes": 45, "cause": "fiber cut on Elm St"},
    "27603": {"outage": False},
}
ACCOUNTS = {
    "acct-1029": {"status": "suspended", "reason": "non-payment", "balance_due": 214.50},
    "acct-2048": {"status": "active", "balance_due": 0},
}
LINE_DIAGNOSTICS = {
    "acct-2048": {"signal_db": -68, "packet_loss_pct": 0.4, "status": "nominal"},
}

def check_outage_status(zip_code):
    return OUTAGES.get(str(zip_code).strip(), {"error": f"no outage data for zip '{zip_code}'"})

def check_account_status(account_id):
    return ACCOUNTS.get(account_id, {"error": f"no account on file for '{account_id}'"})

def run_line_diagnostic(account_id, _simulate_hang=False):
    return LINE_DIAGNOSTICS.get(account_id, {"error": f"no diagnostic data for '{account_id}'"})

def restart_modem(account_id):
    return {"restarted": True, "account_id": account_id}

A fifth tool, get_ticket_history(account_id), exists too — it plays a supporting role in Section 9. Three of these five — check_outage_status, check_account_status, and run_line_diagnostic — are all genuine candidates for the same request. Every one of these three could plausibly explain "my internet is down," and only one of them is actually the cause for any given customer.

What is... a genuinely overlapping tool set? Tools whose descriptions all mention the same surface symptom, where more than one could plausibly be the right call for the same user request, and where picking wrong doesn't error — it just answers a question the user didn't actually have. Chapters 1-2's tool sets avoided this on purpose, to isolate loop mechanics and planning; this chapter builds it on purpose, because most real tool sets have it.

3. The naive baseline: topical-keyword selection fails

The tempting first implementation of tool selection is keyword matching against the tool's name or description — "internet," "down," "slow" all sound like they belong to run_line_diagnostic:

selection.py
def naive_first_match(problem_text):
    text = problem_text.lower()
    if "internet" in text or "down" in text or "slow" in text:
        return "run_line_diagnostic"  # always guesses the technical cause first
    return None

print(naive_first_match("my internet has been down for an hour"))
Output (real) 
run_line_diagnostic

Run this against the account that's actually suspended for non-payment, and the naive guess is simply wrong — not a crash, not an error, just the wrong tool, every time this exact wording is used:

Output (real) 
-- acct-1029 (actually suspended for non-payment) --
naive tool would have been: run_line_diagnostic -- wrong; the line was never the problem
correct tool: check_account_status -> {'status': 'suspended', 'reason': 'non-payment', 'balance_due': 214.5}
Why this isn't a strawman
The naive function isn't wrong because it's naive in some abstract sense — it's wrong because "internet is down" is genuinely, equally consistent with all three candidate causes. No amount of better keyword tuning fixes this, because the customer's wording doesn't carry the information needed to disambiguate; only the tools' own results do. This is the same class of lesson as Chapter 2 Section 4's free-text planning failure: a plausible-sounding shortcut that fails on contact with real ambiguity, kept in this lesson because it's the real, motivating failure, not a manufactured one.

4. Choosing the right tool: cheapest decisive signal first

The fix isn't a smarter keyword list — it's checking the cheapest, most decisive signal first, and only reaching for a more expensive or less certain tool if that signal doesn't already resolve the question:

selection.py (continued)
def diagnose_connectivity_issue(account_id, zip_code):
    account = check_account_status(account_id)
    if account.get("status") == "suspended":
        return "check_account_status", account
    outage = check_outage_status(zip_code)
    if outage.get("outage"):
        return "check_outage_status", outage
    diag = run_line_diagnostic(account_id)
    return "run_line_diagnostic", diag

Three real runs, exercising all three branches, confirming none of them is a strawman path that's never actually reached:

-- acct-1029, zip 27603 (suspended for non-payment) --
correct tool: check_account_status -> {'status': 'suspended', 'reason': 'non-payment', 'balance_due': 214.5}
Output (real, case 2 -- area outage, account fine) 
-- acct-2048, zip 27601 (active outage) --
correct tool: check_outage_status -> {'outage': True, 'eta_minutes': 45, 'cause': 'fiber cut on Elm St'}

-- acct-2048, zip 27603 (no outage, no suspension -- line diagnostic is correct) --
correct tool: run_line_diagnostic -> {'signal_db': -68, 'packet_loss_pct': 0.4, 'status': 'nominal'}
What is... "cheapest, most decisive" actually mean here? check_account_status goes first not because it's topically closest to "internet," but because a suspension is a single boolean check that, when true, fully explains the symptom — no further evidence needed. check_outage_status goes second because it's still a fast, area-wide lookup that, when true, also fully explains it. run_line_diagnostic goes last because it's the most expensive (a real diagnostic, Section 8's subject) and the least likely to be needed, once the two cheaper explanations are ruled out. This ordering is itself a design decision under this chapter's subject, not an afterthought.

5. Argument-formatting drift, beyond strip-and-lower

Chapters 1-2 each fixed exactly one argument-formatting mismatch with one pattern: strip whitespace, lowercase, done. Real account IDs drift in more ways than that. A strip-and-lower-only normalizer, tested for real against a realistic variant, simply fails to find a record that exists:

normalize.py
def naive_normalize_account_id(raw):
    return raw.strip().lower()

key = naive_normalize_account_id("acct1029")
print(f"naive key: {key!r}, in ACCOUNTS: {key in ACCOUNTS}")
Output (real) 
naive key: 'acct1029', in ACCOUNTS: False

The real fix extracts the digits and rebuilds the canonical key, tolerating dashes, spaces, and a stray # — none of which strip-and-lower alone can handle:

normalize.py (continued)
import re

def normalize_account_id(raw):
    digits = re.sub(r"\D", "", raw)  # strip everything but digits
    if not digits:
        return raw.strip().lower()
    return f"acct-{digits}"

for v in ["ACCT-1029", "acct1029", "Acct #1029", "  acct-1029  ", "1029"]:
    print(repr(v), "->", normalize_account_id(v))
Output (real) 
'ACCT-1029' -> acct-1029
'acct1029' -> acct-1029
'Acct #1029' -> acct-1029
'  acct-1029  ' -> acct-1029
'1029' -> acct-1029

ZIP codes drift differently — a ZIP+4 suffix and a raw int both need handling, and neither is a case normalize_account_id's logic covers, because the drift pattern is specific to the argument's own shape, not a generic string-cleanup routine:

normalize.py (continued)
def normalize_zip(raw):
    return str(raw).strip().split("-")[0]

for v in ["27601-4821", 27601, " 27603 "]:
    print(repr(v), "->", normalize_zip(v))
Output (real) 
'27601-4821' -> 27601
27601 -> 27601
' 27603 ' -> 27603
Why one normalize pattern doesn't generalize
Chapters 1-2's single normalize-and-guard pattern (trim, lowercase, retry) was enough because each chapter only ever hit one specific mismatch. In production, every distinct argument type — an account ID, a ZIP code, an order number, a date — drifts in its own way, shaped by whatever upstream systems produce it. normalize_account_id and normalize_zip are deliberately different functions, not one shared helper, because pretending one strip-and-lower routine covers both would silently under-handle at least one of them.

That last result is itself a genuine, useful failure — ACCOUNTS is keyed on the raw string "acct-2048", and this fixture data happens to use a hyphen already, so check_account_status's own dict lookup (not wrapped in the same normalize step) is stricter than the normalizer that fed it. This is exactly the kind of mismatch this section exists to surface: normalizing the argument going into a selection function doesn't automatically mean every tool behind it was built to accept the same normalized shape — each tool's own input contract still has to be checked, not assumed.

7. Tool failure as a first-class case: three distinct types

Chapters 1-2 each handled one clean failure shape: a tool returns {"error": "..."}, and the caller checks for the "error" key. Real tool failures don't all look like that. This chapter treats three genuinely different failure types as first-class, because each one needs a different response:

What is... the three failure types this chapter treats distinctly? Timeout — the call never returns at all, clean or otherwise, inside any reasonable budget. Malformed output — the call returns something, but not the shape every other tool call returns (not a dict, missing expected fields). Succeeds but wrong answer — the call returns a perfectly well-formed, successful-looking result that simply doesn't mean what it appears to mean. Sections 8-10 build each one against a real NetBot tool; Section 11 shows why one retry policy can't serve all three.

8. Failure type 1: timeout

run_line_diagnostic stands in for a real, slow upstream diagnostic call. A bounded wait, using Python's own thread pool rather than hoping a library call respects a deadline, is the honest way to cap how long any single tool call is allowed to block the loop:

failures.py
import concurrent.futures

def call_with_timeout(fn, kwargs, budget_seconds):
    with concurrent.futures.ThreadPoolExecutor(max_workers=1) as ex:
        future = ex.submit(fn, **kwargs)
        try:
            return {"ok": True, "result": future.result(timeout=budget_seconds)}
        except concurrent.futures.TimeoutError:
            return {"ok": False, "failure_type": "timeout"}

print(call_with_timeout(run_line_diagnostic, {"account_id": "acct-2048", "_simulate_hang": True}, budget_seconds=1))
print(call_with_timeout(run_line_diagnostic, {"account_id": "acct-2048"}, budget_seconds=2))
Output (real) 
{'ok': False, 'failure_type': 'timeout'}
{'ok': True, 'result': {'signal_db': -68, 'packet_loss_pct': 0.4, 'status': 'nominal'}}

A timeout is often transient — the same call can succeed a moment later — so the right policy is a bounded retry, mirroring Chapter 1's max_iterations and Chapter 2's max_replans discipline: bound it, don't retry forever:

retry_policy.py
def call_line_diagnostic_with_retry(account_id, simulate_hang=False, max_retries=2, budget_seconds=1):
    for attempt in range(max_retries + 1):
        outcome = call_with_timeout(
            run_line_diagnostic,
            {"account_id": account_id, "_simulate_hang": simulate_hang and attempt == 0},
            budget_seconds,
        )
        if outcome["ok"]:
            return outcome["result"], attempt
        print(f"  [retry policy] attempt {attempt} timed out -- retrying (timeouts are treated as transient)")
    return None, max_retries

result, attempts = call_line_diagnostic_with_retry("acct-2048", simulate_hang=True)
print(f"result: {result}, attempts used: {attempts}")
Output (real) 
  [retry policy] attempt 0 timed out -- retrying (timeouts are treated as transient)
result: {'signal_db': -68, 'packet_loss_pct': 0.4, 'status': 'nominal'}, attempts used: 1

9. Failure type 2: malformed output

NetBot's fifth tool models a real production pattern: a legacy endpoint that, on certain inputs, returns a raw string instead of the dict shape every other tool call returns:

failures.py (continued)
def legacy_ticket_lookup(account_id):
    key = account_id.strip().lower()
    if key == "acct-9999":
        return "ERR: account not found in legacy system"  # malformed -- not a dict
    return get_ticket_history(account_id)

def call_with_malformed_check(fn, kwargs):
    result = fn(**kwargs)
    if not isinstance(result, dict):
        return {"ok": False, "failure_type": "malformed_output", "raw": result}
    return {"ok": True, "result": result}

print(call_with_malformed_check(legacy_ticket_lookup, {"account_id": "acct-9999"}))
print(call_with_malformed_check(legacy_ticket_lookup, {"account_id": "acct-2048"}))
Output (real) 
{'ok': False, 'failure_type': 'malformed_output', 'raw': 'ERR: account not found in legacy system'}
{'ok': True, 'result': {'tickets': [{'ticket_id': 't-777', 'issue': 'slow speeds', 'opened_days_ago': 2}]}}

Unlike a timeout, a malformed response is not transient — the same input produces the same malformed output every time, proven by actually retrying it three times:

retry_policy.py (continued)
attempts = [legacy_ticket_lookup("acct-9999") for _ in range(3)]
print(f"attempt 1: {attempts[0]!r}")
print(f"attempt 2: {attempts[1]!r}")
print(f"attempt 3: {attempts[2]!r}")
print(f"all three identical: {attempts[0] == attempts[1] == attempts[2]}")
Output (real) 
attempt 1: 'ERR: account not found in legacy system'
attempt 2: 'ERR: account not found in legacy system'
attempt 3: 'ERR: account not found in legacy system'
all three identical: True

The correct policy is therefore no retry at all — a defensive check, then an immediate flag for a parse fix or escalation, not a wasted retry loop that will only reproduce the same malformed string:

retry_policy.py (continued)
def call_ticket_lookup_no_retry(account_id):
    outcome = call_with_malformed_check(legacy_ticket_lookup, {"account_id": account_id})
    if outcome["ok"]:
        return outcome["result"], "ok"
    print(f"  [retry policy] malformed output detected -- NOT retrying, flagging for a defensive parse instead")
    return None, "malformed_output_no_retry"

result2, status2 = call_ticket_lookup_no_retry("acct-9999")
print(f"result: {result2}, status: {status2}")
Output (real) 
  [retry policy] malformed output detected -- NOT retrying, flagging for a defensive parse instead
result: None, status: malformed_output_no_retry

10. Failure type 3: succeeds but wrong answer

restart_modem is the most deceptive failure type NetBot has, because nothing about calling it looks wrong:

tools.py (recap)
def restart_modem(account_id):
    return {"restarted": True, "account_id": account_id}

print(restart_modem("acct-1029"))
Output (real) 
{'restarted': True, 'account_id': 'acct-1029'}

A clean, well-formed, unconditional success. But if the real root cause was an area outage (Section 4's second branch), restarting the modem doesn't do anything — the modem was never the problem. No exception, no "error" key, no malformed shape: this call is invisible to both of Sections 8-9's failure detectors. The only real defense is checking independent evidence against the claimed outcome:

retry_policy.py (continued)
def restart_modem_with_outcome_check(account_id, zip_code):
    result = restart_modem(account_id)
    outage = check_outage_status(zip_code)
    if outage.get("outage"):
        print(f"  [outcome check] restart_modem reported success, but an outage is active in {zip_code} -- "
              f"the restart did NOT actually address the problem")
        return {"restart_result": result, "actually_resolved": False, "real_cause": "area outage"}
    return {"restart_result": result, "actually_resolved": True}

print(restart_modem_with_outcome_check("acct-1029", "27601"))
Output (real) 
  [outcome check] restart_modem reported success, but an outage is active in 27601 -- the restart did NOT actually address the problem
{'restart_result': {'restarted': True, 'account_id': 'acct-1029'}, 'actually_resolved': False, 'real_cause': 'area outage'}

The same function, run where the restart genuinely was the right fix, correctly reports a real success instead of a false negative — the outcome check isn't pessimistic by default, it's accurate:

Output (real) 
>>> restart_modem_with_outcome_check("acct-2048", "27603")
{'restart_result': {'restarted': True, 'account_id': 'acct-2048'}, 'actually_resolved': True}
Why no retry policy applies here at all
Sections 8-9 both eventually answer the question "should this call be retried?" This failure type doesn't have that question, because nothing failed in a way either call_with_timeout or call_with_malformed_check could detect. The call succeeded exactly as designed. The bug isn't in the call; it's in trusting the call's own report of success as proof the underlying problem was solved.

11. Why "retry on error" is the wrong abstraction

Sections 8-10 together make one point concrete: a single try/except: retry wrapper is actively wrong for at least two of these three failure types. Applied uniformly, it would retry a malformed-output failure uselessly (Section 9 proved the result doesn't change) and it would never even notice Section 10's failure, because nothing raised or errored in the first place.

Failure typeDetectable howCorrect policy
TimeoutA bounded wait (call_with_timeout) never returns in budgetRetry with a small bound, since it's often transient
Malformed outputResult isn't the expected shape (not a dict, missing fields)Never retry -- flag for a defensive parse or escalate immediately
Succeeds but wrong answerCannot be detected from the call itself -- needs independent evidenceNo retry concept applies -- verify the outcome against real evidence instead

This table is this chapter's central claim, stated as plainly as possible: the correct response to a tool failure depends entirely on which kind of failure it is, and conflating the three into one generic error-handling code path silently under-serves at least two of them.

12. A unified dispatcher, routed by failure policy

Rather than scattering these three policies across call sites, a small dispatcher routes each tool call by its own declared policy — the same discipline as Section 5's per-argument-type normalizers, applied to failure handling:

dispatcher.py
FAILURE_POLICY = {
    "run_line_diagnostic": "retry_on_timeout",
    "get_ticket_history_legacy": "no_retry_on_malformed",
    "restart_modem": "verify_outcome",
}

def call_tool_with_policy(tool_name, fn, kwargs, zip_code_for_outage_check=None):
    policy = FAILURE_POLICY.get(tool_name, "none")
    if policy == "retry_on_timeout":
        for attempt in range(3):
            attempt_kwargs = dict(kwargs)
            if attempt > 0:
                attempt_kwargs["_simulate_hang"] = False  # the hang was transient -- don't force it again
            outcome = call_with_timeout(fn, attempt_kwargs, budget_seconds=1)
            if outcome["ok"]:
                return {"status": "ok", "result": outcome["result"], "attempts": attempt + 1}
        return {"status": "failed_after_retries", "attempts": 3}
    if policy == "no_retry_on_malformed":
        result = fn(**kwargs)
        if not isinstance(result, dict):
            return {"status": "malformed_no_retry", "raw": result}
        return {"status": "ok", "result": result}
    if policy == "verify_outcome":
        result = fn(**kwargs)
        outage = check_outage_status(zip_code_for_outage_check)
        resolved = not outage.get("outage")
        return {"status": "ok", "result": result, "actually_resolved": resolved}
    return {"status": "ok", "result": fn(**kwargs)}

{'status': 'ok', 'result': {'restarted': True, 'account_id': 'acct-2048'}, 'actually_resolved': True}
What FAILURE_POLICY buys, structurally
Every tool declares its own failure-handling policy in one place, instead of each call site guessing at (or forgetting) the right response. Adding a new tool means adding one dictionary entry and, if needed, one new branch — not re-deriving the retry logic from scratch at every call site that happens to use it.

13. The finished NetBot agent

Selection (Sections 3-4), normalization (Section 5), and differentiated failure handling (Sections 8-12), assembled into one file NetBot would actually run:

netbot_agent.py
import re, time, concurrent.futures

OUTAGES = {"27601": {"outage": True, "eta_minutes": 45, "cause": "fiber cut on Elm St"}, "27603": {"outage": False}}
ACCOUNTS = {"acct-1029": {"status": "suspended", "reason": "non-payment", "balance_due": 214.50},
            "acct-2048": {"status": "active", "balance_due": 0}}
LINE_DIAGNOSTICS = {"acct-2048": {"signal_db": -68, "packet_loss_pct": 0.4, "status": "nominal"}}

def check_outage_status(zip_code):
    return OUTAGES.get(str(zip_code).strip(), {"error": f"no outage data for zip '{zip_code}'"})
def check_account_status(account_id):
    return ACCOUNTS.get(account_id, {"error": f"no account on file for '{account_id}'"})
def run_line_diagnostic(account_id, _simulate_hang=False):
    if _simulate_hang:
        time.sleep(3)
    return LINE_DIAGNOSTICS.get(account_id, {"error": f"no diagnostic data for '{account_id}'"})
def restart_modem(account_id):
    return {"restarted": True, "account_id": account_id}

def normalize_account_id(raw):
    digits = re.sub(r"\D", "", raw)
    return f"acct-{digits}" if digits else raw.strip().lower()
def normalize_zip(raw):
    return str(raw).strip().split("-")[0]

def diagnose_connectivity_issue(account_id_raw, zip_code_raw):
    account_id = normalize_account_id(account_id_raw)
    zip_code = normalize_zip(zip_code_raw)
    account = check_account_status(account_id)
    if account.get("status") == "suspended":
        return {"tool": "check_account_status", "result": account, "root_cause": "billing"}
    outage = check_outage_status(zip_code)
    if outage.get("outage"):
        return {"tool": "check_outage_status", "result": outage, "root_cause": "area_outage"}
    with concurrent.futures.ThreadPoolExecutor(max_workers=1) as ex:
        future = ex.submit(run_line_diagnostic, account_id)
        try:
            diag = future.result(timeout=2)
            return {"tool": "run_line_diagnostic", "result": diag, "root_cause": "line"}
        except concurrent.futures.TimeoutError:
            return {"tool": "run_line_diagnostic", "result": None, "root_cause": "unknown_timeout"}

def resolve_and_verify(account_id_raw, zip_code_raw):
    diagnosis = diagnose_connectivity_issue(account_id_raw, zip_code_raw)
    if diagnosis["root_cause"] == "line":
        restart_modem(normalize_account_id(account_id_raw))
        outage_recheck = check_outage_status(normalize_zip(zip_code_raw))
        resolved = not outage_recheck.get("outage")
        return {**diagnosis, "action_taken": "restart_modem", "actually_resolved": resolved}
    return {**diagnosis, "action_taken": None, "actually_resolved": False}

14. A pre-production checklist for tool use

Sections 3-13 generalize into four questions worth asking about any tool before it ships, mirroring Chapter 2 Section 12's single-question heuristic, but for the tool layer instead of the planning layer:

checklist.py
def classify_failure_type(outcome):
    if outcome.get("failure_type") == "timeout":
        return "timeout"
    if "raw" in outcome and not isinstance(outcome.get("raw"), dict):
        return "malformed_output"
    if outcome.get("ok") and isinstance(outcome.get("result"), dict) and "error" not in outcome["result"]:
        return "clean_success"
    return "unknown"

print(classify_failure_type({"ok": False, "failure_type": "timeout"}))
print(classify_failure_type({"ok": False, "failure_type": "malformed_output", "raw": "ERR: not found"}))
print(classify_failure_type({"ok": True, "result": {"signal_db": -68}}))

The four questions this classifier's branches encode, as a checklist:

  1. Does another tool in this set plausibly answer the same request? If yes, order candidates by cost and decisiveness (Section 4), never by surface-keyword similarity to the request's wording (Section 3).
  2. What real formatting drift will this argument see in production? Write a normalizer specific to that argument's own drift pattern (Section 5) — don't assume one strip-and-lower routine covers every argument type.
  3. Can this call hang, return a malformed shape, or return a clean-but-wrong result? Each of these three needs its own detection and its own policy (Sections 8-11) — decide which apply to this specific tool before writing one generic try/except.
  4. If nothing throws, how would a wrong-but-successful result actually get caught? If the answer is "it wouldn't," that tool needs an outcome-verification step (Section 10) before it ships.

15. GenAI Builder Thought Process

Thought process: the natural first instinct when a tool call "fails" is to wrap it in one generic retry loop and move on — but Sections 8-11 show that instinct actively backfires for two of the three failure types this chapter identified: it wastes calls retrying a malformed response that will never change, and it does nothing at all for a failure that never raises in the first place. The discipline this chapter teaches isn't "handle tool failures" as one undifferentiated bucket — it's classifying which of three distinct shapes a given failure took (Section 14's classifier) before deciding what to do about it, and for tool selection, ordering candidates by cost and decisiveness rather than surface wording. A strong prompt for an AI pair-programmer extending this chapter's agent: "I have three tools that all plausibly answer the same user request, and one tool that always returns a clean success dict regardless of whether the underlying problem was actually fixed. Write a selection function that checks the cheapest, most decisive signal first, and an outcome-verification function for the always-succeeds tool that checks independent evidence before reporting the problem as resolved. Separately, write a dispatcher that applies a bounded retry for timeouts, no retry at all for malformed (non-dict) responses, and no retry concept for the outcome-verification case. Do not use an agent framework — plain Python and, where a real reasoning step is needed, the openai client against local Ollama."

In the Real World
  • Multi-tool customer-support agents are the canonical home of Section 3's problem: "my order hasn't arrived" is often answerable by a shipping-status tool, a payment-status tool, or a warehouse-inventory tool, and which one is right depends on the specific order, not the wording of the question.
  • A tool that always reports success (Section 10) is one of the hardest production bugs to catch precisely because it never shows up in error-rate dashboards — it shows up in customer complaints about a problem that was supposedly already fixed.
  • Legacy and third-party API integrations are the most common real source of Section 9's malformed-output failures — an upstream provider's own error format frequently doesn't match the JSON shape their happy-path responses use, and code written only against the happy path breaks the first time that upstream provider has a bad day.

Points to Remember

  • Tool selection among overlapping candidates should be ordered by cost and decisiveness (cheapest, most conclusive signal first), never by surface-keyword similarity to the request's wording — the naive keyword approach fails precisely when candidates genuinely overlap, which real tool sets usually do.
  • Argument-formatting drift is specific to each argument's own shape — an account-ID normalizer and a ZIP-code normalizer are legitimately different functions, not one shared strip-and-lower routine stretched to cover both.
  • Tool failure is not one undifferentiated case. This chapter names three: timeout (the call never returns — retry with a small bound, since it's often transient), malformed output (the call returns the wrong shape — never retry, since the same input reproduces the same malformed result), and succeeds but wrong answer (the call returns a clean, well-formed result that doesn't mean the problem is solved — no retry policy applies; only independent outcome verification catches it).
  • A single generic try/except: retry wrapper actively under-serves at least two of these three failure types — it wastes calls on a malformed response and misses a false success entirely.
  • A unified dispatcher that routes each tool call by its own declared failure policy (Section 12) keeps this logic in one place instead of re-derived ad hoc at every call site.
  • No agent framework was used anywhere in this chapter — every selection, normalization, and failure-handling function is plain Python and, where a live reasoning step is genuinely needed, the plain openai client against local Ollama, the same pattern Chapters 1-2 used.
