Chapter 3 Project — Solo → AI-Paired → Critique 20 min

Now Pair With an AI

You already built RepairBot's outcome-verification function yourself. Now try the reverse: describe the same task to an AI assistant without showing it your own solution, and review what it hands back with the same scrutiny you'd bring to a teammate's pull request before merging it into Kestrel Appliance Service's real dispatch system.

Step 1: Have the AI build it independently

Thought process: the prompt needs to make explicit that schedule_repair_visit always returns a clean success — otherwise the AI has no reason to add an independent outcome check at all, and will likely just return whatever schedule_repair_visit reported, which is exactly the bug this exercise is designed to surface.

Write the prompt you'd give an AI assistant:

Paste your prompt into your assistant of choice, save its response separately, and compare it against the checklist below before looking at this project's own solution.py.
Show a strong version of this prompt 
Write a Python function verify_repair_outcome(ticket_id) for an appliance-repair agent. It has access to two tools from a TOOL_IMPLS-style dict: schedule_repair_visit(ticket_id), which ALWAYS returns {"scheduled": True, "ticket_id": ticket_id} regardless of whether the repair actually happens -- and get_repair_ticket_status(ticket_id), which returns real ticket data like {"status": "completed"} or {"status": "scheduled"} (or an error dict if the ticket doesn't exist). verify_repair_outcome should call schedule_repair_visit, then independently check get_repair_ticket_status, and only report the repair as resolved if the real ticket status is exactly "completed" -- NOT just because schedule_repair_visit reported success. Return {"schedule_result": ..., "resolved": bool}. Do not use any agent framework.

Step 2: Review it against this checklist

What a rushed AI-generated outcome-check tends to get wrong
  • Trusting schedule_repair_visit's own success flag as proof of resolution. The whole point of this function is that a tool's own reported "success" is not evidence the underlying problem is solved — check whether the generated code actually calls get_repair_ticket_status at all, or just returns schedule_result["scheduled"] renamed to resolved.
  • Treating any non-error status as resolved. A ticket with {"status": "scheduled"} is not an error, but it's also not "completed" — does the generated code correctly distinguish "no error" from "actually done," or does it collapse the two?
  • Not handling a ticket that doesn't exist. What does the generated code do if get_repair_ticket_status returns an error dict with no "status" key at all — does it crash with a KeyError, or does it degrade to resolved: False the way a missing/unknown ticket should?

Now compare the AI's code against solution.py in this same folder. Where do they differ? Is the AI's version genuinely equivalent, or does it handle one of the three watch-outs above differently — and is that difference actually a bug, or a legitimate different design choice?
