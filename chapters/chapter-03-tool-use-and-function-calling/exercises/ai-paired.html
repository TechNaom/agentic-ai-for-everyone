Chapter 3 — Solo → AI-Paired → Critique 20 min

Now Pair With an AI

You already worked the exercises yourself on Thornbury Insurance Group's ClaimBot. Now a third scenario, Wrenhollow Auto Rentals (a fictional car rental chain) and its dispatch agent FleetBot, gets diagnosed a second way: by prompting an AI assistant, and reviewing what it hands back with the same skepticism you'd bring to a coworker's write-up before it ships to Wrenhollow's real dispatch desk.

Step 1: Diagnose it yourself, first

FleetBot has three tools: get_vehicle_location(vehicle_id), check_maintenance_flag(vehicle_id), and extend_reservation(reservation_id). Wrenhollow's ops lead reports three real, observed problems:

  1. A customer asked "why is my rental late for pickup?" FleetBot called check_maintenance_flag first, because the word "rental" felt closer to "car" than to "location" in the prompt — but the real, cheaper-to-check answer was sitting in get_vehicle_location: the car was simply stuck in traffic ten minutes out, nothing was wrong with it mechanically.
  2. get_vehicle_location talks to a known-flaky third-party GPS provider that occasionally hangs for 20+ seconds with no response at all. Instead of a bounded timeout-and-retry, FleetBot's code path assumed any bad outcome from this tool meant a malformed response to parse — so on a real hang, it tried to parse a response that had never arrived, and the whole request handler crashed instead of giving up cleanly.
  3. extend_reservation(reservation_id) always returns {"extended": True} — even for a vehicle that already has a scheduled next renter, which makes the extension actually impossible to honor. Customers only discovered the truth when they showed up for their extended day and the car was already gone.

Before reading further, write your own diagnosis: for each of the three problems, name the concept it's really about (using this chapter's vocabulary: wrong-tool-choice, a missing timeout/malformed-output distinction, or a succeeds-but-wrong-answer failure) and propose one concrete fix. Use a notes app or scratch file — there's no grading here, just your own reasoning to compare against Step 3.

Step 2: Ask an AI assistant the same question

Thought process: the prompt needs to hand over all three problems with their real, specific evidence — not a vague "why is my agent's tool use bad" — or the AI has nothing concrete to diagnose and will produce generic advice instead of a checkable answer.

Write the prompt you'd give an AI assistant:

Paste your prompt into Claude, ChatGPT, Copilot, or whatever assistant you use, and compare what it builds against this page's own critique in Step 3.
Show a strong version of this prompt 
I have an agent called FleetBot with three tools: get_vehicle_location(vehicle_id), check_maintenance_flag(vehicle_id), extend_reservation(reservation_id). Here are three real, observed problems: [paste the three numbered problems above verbatim]. For each problem, name which tool-use concept it's really about (wrong-tool-choice among plausible candidates, a missing timeout-vs-malformed-output distinction, or a succeeds-but-wrong-answer failure) and propose one concrete, specific code-level fix for each -- not a general "improve error handling" suggestion.

Step 3: Critique what came back

A plausible-but-flawed AI answer to this exact prompt tends to make three specific mistakes worth watching for:

Common AI diagnosis mistakes on this scenario
  • Mislabeling Problem 1 as "the tool descriptions need better wording." Better descriptions can help, but the real issue is that FleetBot never checked the cheaper, more decisive signal first — the lesson's Section 6 fix isn't a wording tweak, it's re-ordering which tool gets tried first based on cost and decisiveness, not topical similarity to the customer's phrasing.
  • Treating Problem 2 as "just add error handling." The real bug is more specific: a timeout and a malformed response are different failure types that need different code paths (Sections 10-11 of the lesson) — a hang should be caught by a bounded timeout wrapper and possibly retried, while a malformed response should never be retried and should never reach a parser that assumes it's well-formed. Collapsing both into one generic "try/except everything" often still crashes on the actual hang case, because the wait itself was never bounded.
  • Proposing "just check if extend_reservation returns True" as sufficient for Problem 3. It already does — that's exactly the bug. The fix has to check independent evidence (whether a next renter is actually scheduled), the same outcome-check discipline the lesson's restart_modem_with_outcome_check and this chapter's exercises' verify_resolution both use, not trust the tool's own reported success.

Compare the AI's actual answer against your own Step 1 notes and the three watch-outs above. Which one(s) did it get right? Which, if any, did it get wrong the way described here? That comparison — not the AI's fluency — is the real test.
