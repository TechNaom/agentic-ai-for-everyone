Now Pair With an AI

A ninth scenario, not in the eight above: "HandoffBot", a shipment-tracking agent at a fictional logistics service (left unnamed on purpose, the same way Chapter 2's EscalationBot scenario did — a small scenario doesn't need an invented company). HandoffBot has three tools: track_shipment(tracking_id) (a fast, local lookup against the last known scan), check_customs_hold(tracking_id), and request_carrier_update(tracking_id) (an expensive, rate-limited call to the carrier's own system). Asked "where's my package?", HandoffBot calls request_carrier_update first, every time, because it "sounds most authoritative" — even though track_shipment's already-cached answer would resolve most questions immediately and for free. Separately: request_carrier_update returns {"requested": True} the instant it's called, but the carrier's real answer only arrives asynchronously, minutes later, through a separate webhook — and HandoffBot has been treating {"requested": True} as if it were the answer itself, telling customers their tracking info is "up to date" when nothing new has actually been learned yet.

Step 1: Diagnose it yourself, first

Before reading further: name the two distinct problems here using this chapter's vocabulary (one is about picking among several plausible tools; the other is a specific failure class from Sections 10-13 of the lesson) and write your own fix for each. There's no grading here, just your own reasoning to compare against Step 3.

Step 2: Ask an AI assistant

Thought process: this scenario has two layered problems (a wrong-tool-choice AND a succeeds-but-wrong-answer failure), so the prompt needs to ask the AI to identify both, not just one — a shallow prompt like "what's wrong with this agent's tool use" invites a single, incomplete answer, usually just the more expensive-sounding API call.

Write the prompt you'd give an AI assistant:

Paste your prompt into your assistant of choice and compare its answer against the critique below.
Show a strong version of this prompt 
Here's my agent HandoffBot, which has three tools: track_shipment(tracking_id), check_customs_hold(tracking_id), request_carrier_update(tracking_id): [paste the scenario above]. Identify EVERY distinct tool-use problem in this description, not just the first one you notice -- there are two -- and name each using this chapter's vocabulary (wrong-tool-choice among plausible candidates, or a succeeds-but-wrong-answer failure). Propose a concrete, specific fix for each.

Step 3: Critique what came back

What a complete diagnosis catches
  • Problem 1 (wrong-tool-choice): track_shipment is cheap, fast, and already has the answer most of the time — calling the expensive, rate-limited request_carrier_update first, based on which tool "sounds" most authoritative rather than which one is cheapest and most likely to already answer the question, is exactly the ordering mistake this chapter's Section 6 fixes.
  • Problem 2 (succeeds-but-wrong-answer): {"requested": True} means the request was accepted, not that an answer arrived — treating a tool's own "success" as proof the underlying question was answered, without checking whether the real data (the webhook's eventual payload) actually showed up, is exactly Section 11's failure class.
  • A shallow AI answer often catches only Problem 1 (the more visible cost/ordering issue) and misses that Problem 2 is a separate, independent issue — reordering the tool calls alone doesn't fix the false "up to date" claim, and vice versa.

Compare the AI's answer against your own Step 1 notes and the two-problem breakdown above. Did it catch both? Did it propose the right fix for each — reordering by cost and decisiveness, and checking for the webhook's real payload before claiming the tracking info is current — or did it conflate the two into one vague "improve the tool logic" suggestion?
