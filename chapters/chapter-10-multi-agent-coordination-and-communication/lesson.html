1. Hand-off from Chapter 9: dispatch vs. communication

Chapter 9's TripScout was a supervisor: it decided which sub-tasks existed and which worker handled each one. FlightScout, StayScout, and ExcursionScout never spoke to each other -- every interaction was supervisor-to-worker, one-directional, and TripScout's own architecture never needed worker-to-worker messages because its three workers were genuinely independent. This chapter's problem is different: DockScout and YardScout are PEERS. Neither dispatches to the other. Both independently see incoming shipments and must talk directly to avoid colliding.

What is... peer-to-peer agent communication, precisely? In supervisor/worker (Chapter 9), one agent's tool surface is "dispatch to X" and the other agents never call each other. In peer-to-peer communication, two or more agents of EQUAL standing exchange messages directly -- agent A can send to agent B, and B can send back to A, across MULTIPLE turns, with no third agent deciding who talks to whom. This is a genuinely new coordination shape, not dispatch with extra steps.

3. A minimal message schema

Every message DockScout and YardScout exchange has exactly four required parts: who sent it, who it's for, what kind of message it is, and its content:

message_schema.py
from dataclasses import dataclass, field
import itertools

_id_counter = itertools.count(1)

@dataclass
class Message:
    sender: str
    recipient: str
    type: str          # "claim", "ack", "reject", "query", "inform"
    payload: dict
    id: int = field(default_factory=lambda: next(_id_counter))

m = Message(sender="dockscout", recipient="yardscout", type="claim",
            payload={"shipment_id": "S-104"})
print(m)
Output (real, executed) 
Message(sender='dockscout', recipient='yardscout', type='claim', payload={'shipment_id': 'S-104'}, id=1)
No protocol framework, deliberately
This is plain Python -- a dataclass, stdlib itertools for a monotonic id. A real production system might carry these same five fields over MCP, AMQP, or a REST webhook; the WIRE format is a separate concern from the five fields every message genuinely needs, which is this chapter's own scope.

4. A shared message bus -- not a supervisor mediating every message

Chapter 9's blackboard (Section 9) was shared STATE both workers read and wrote. A message bus is a related but distinct primitive: a shared inbox per agent, where any agent can deposit a message for any other agent to pick up later -- no third agent routes it.

message_bus.py
import threading

class MessageBus:
    def __init__(self):
        self._lock = threading.Lock()
        self._inbox = {}   # recipient -> list[Message]
        self._log = []

    def send(self, msg):
        with self._lock:
            self._inbox.setdefault(msg.recipient, []).append(msg)
            self._log.append(msg)

    def receive_all(self, recipient):
        with self._lock:
            msgs = self._inbox.get(recipient, [])
            self._inbox[recipient] = []
            return msgs

    def history(self):
        with self._lock:
            return list(self._log)

bus = MessageBus()
bus.send(Message("dockscout", "yardscout", "claim", {"shipment_id": "S-104"}))
print("yardscout's inbox, first read:", bus.receive_all("yardscout"))
print("yardscout's inbox, second read (already drained):", bus.receive_all("yardscout"))
Output (real, executed) 
yardscout's inbox, first read: [Message(sender='dockscout', recipient='yardscout', type='claim', payload={'shipment_id': 'S-104'}, id=2)]
yardscout's inbox, second read (already drained): []
The lock, and the drain-on-read semantics, are both load-bearing
Without the lock, two agents sending at the same instant could corrupt the shared _inbox dict. Draining on read (replacing the list with [] inside the SAME locked block) means a message is delivered to exactly one read, not re-delivered every time receive_all is called -- the same "read it once" guarantee a real message queue provides.

7. Failure mode 1: miscommunication -- validating a message before trusting it

Section 6's real result is this chapter's own first failure mode: a receiving agent that trusts a message's shape without checking it will either crash on a malformed key or silently act on the wrong field. A normalizing parser, tested against Section 6's EXACT real output:

parse_message_safely.py
def parse_message_safely(raw_args, required_fields=("recipient", "type", "shipment_id")):
    """Normalizes whitespace-padded keys (Section 6's own real bug), then
    checks every required field is present. Returns {"ok": False, ...}
    rather than raising -- a receiving agent must NEVER let a malformed
    message crash it, the same fail-closed discipline Chapter 9's
    dispatch-retry logic (Section 5) used for a missing tool_call."""
    normalized = {k.strip(): v for k, v in raw_args.items()}
    missing = [f for f in required_fields if f not in normalized]
    if missing:
        return {"ok": False, "reason": f"missing required fields after normalization: {missing}"}
    return {"ok": True, "fields": normalized}

import json
section6_raw = json.loads('{" recipient ":"DockScout","note":"Claiming highest priority shift for me","shipment_id ":"S-104","type":"query"}')
result = parse_message_safely(section6_raw)
print(result)
Output (real, executed against Section 6's own real output) 
{'ok': True, 'fields': {'recipient': 'DockScout', 'note': 'Claiming highest priority shift for me', 'shipment_id': 'S-104', 'type': 'query'}}

Whitespace-stripping recovers this specific malformation. A field renamed outright (not just padded) is a DIFFERENT, unrecoverable case -- the next example shows that one failing closed instead of guessing:

unrecoverable_miscommunication.py
renamed_field = {"recipient": "DockScout", "note": "...", "shipment": "S-104", "type": "query"}
print(parse_message_safely(renamed_field))
Output (real, executed) 
{'ok': False, 'reason': "missing required fields after normalization: ['shipment_id']"}
Normalize what's safe to normalize; fail closed on what isn't
Stripping whitespace is safe -- it can never change WHICH field a value belongs to. Guessing that "shipment" means "shipment_id" is NOT safe -- a receiving agent that silently maps unrecognized field names is one keyword-collision away from acting on the wrong value entirely. parse_message_safely deliberately does the first and refuses the second.

9. The fix: a shared claim-check through the bus, with a lock

The naive version, reproducing Section 8's exact shape deterministically:

naive_claim.py
def naive_claim(agent_name, shipment_id, local_claims):
    local_claims.add(shipment_id)
    return f"{agent_name} will handle {shipment_id}"

dock_local, yard_local = set(), set()
r1 = naive_claim("dockscout", "S-104", dock_local)
r2 = naive_claim("yardscout", "S-104", yard_local)
print(r1, "|", r2)
Output (real, executed) 
dockscout will handle S-104 | yardscout will handle S-104

The fix: a single shared set of claims, guarded by one lock, that EVERY agent checks before committing -- the same "check shared state before acting" discipline Chapter 9's blackboard (Section 9) used, now applied to claims instead of a budget:

coordinated_claim.py
import threading

shared_claims = set()
shared_lock = threading.Lock()

def coordinated_claim(agent_name, shipment_id):
    with shared_lock:
        if shipment_id in shared_claims:
            return f"{agent_name} SKIPPED {shipment_id} -- already claimed"
        shared_claims.add(shipment_id)
        return f"{agent_name} claimed {shipment_id}"

print(coordinated_claim("dockscout", "S-104"))
print(coordinated_claim("yardscout", "S-104"))
Output (real, executed) 
dockscout claimed S-104
yardscout SKIPPED S-104 -- already claimed
Why this must be a check-THEN-add inside ONE lock, not two separate calls
If "check whether claimed" and "add to claims" were two separate locked calls, two agents could both pass the check (neither sees it claimed yet) before either one adds it -- the exact race Chapter 9's blackboard section warned about, now for claims. One locked block covering both the read and the write is what actually prevents Section 8's real duplication from recurring.

11. Consensus/voting when agents disagree without a supervisor

Section 10 worked because DockScout voluntarily backed down. A system can't rely on voluntary resolution alone -- a deterministic tie-breaker is needed for when both agents dig in instead:

consensus.py
from collections import Counter

def resolve_conflicting_claims(votes):
    """votes: dict agent -> who-should-get-it. Majority wins; an exact
    tie returns None -- escalate, never guess which agent 'really'
    deserves it."""
    counts = Counter(votes.values())
    top = counts.most_common()
    if len(top) > 1 and top[0][1] == top[1][1]:
        return None
    return top[0][0]

print("clear majority (a 3rd observer agent breaks the tie):", resolve_conflicting_claims(
    {"dockscout": "yardscout", "yardscout": "yardscout", "observer": "dockscout"}))
print("exact tie, 2 agents, no majority possible -- escalate:", resolve_conflicting_claims(
    {"dockscout": "dockscout", "yardscout": "yardscout"}))
Output (real, executed) 
clear majority (a 3rd observer agent breaks the tie): yardscout
exact tie, 2 agents, no majority possible -- escalate: None
A 2-agent system can ALWAYS tie -- voting alone is not sufficient
With exactly two peers voting for themselves, a majority vote can never break the tie mathematically -- this is why Section 14's deadlock-breaker uses an independent rule (lowest agent ID goes first), not a vote, and why a real 3+-agent system benefits from an odd number of voters or a designated, narrow tie-breaking authority for exactly this unavoidable case.

13. Constructing deadlock deterministically, and detecting it with a timeout

A deadlock is a STRUCTURAL property (two agents each conditioned on the other's prior message, with neither one ever sending first), not a one-off model quirk -- it's demonstrated reliably by code that enforces the condition directly:

construct_deadlock.py
def deadlocked_turn(agent_name, inbox):
    """Both agents run THIS exact logic: if my inbox is empty, I wait.
    If BOTH agents only ever run this, and neither one is ever given
    a reason to speak first, nothing breaks the cycle."""
    if not inbox:
        return None   # waits forever if the other side also waits
    return f"{agent_name} responds to {inbox[0]}"

print("dockscout, empty inbox:", deadlocked_turn("dockscout", []))
print("yardscout, empty inbox:", deadlocked_turn("yardscout", []))
print("neither agent ever sends -- this IS the deadlock, by construction")
Output (real, executed) 
dockscout, empty inbox: None
yardscout, empty inbox: None
neither agent ever sends -- this IS the deadlock, by construction

Detecting it needs a wall-clock budget, the same discipline Chapter 8's cost/latency budgets used for a runaway loop, now applied to elapsed WAITING time instead of steps or cost:

deadlock_timeout.py
def check_for_deadlock(agent_name, inbox, timeout_s, elapsed_s):
    if inbox:
        return {"status": "progressed", "reply": f"{agent_name} responds"}
    if elapsed_s >= timeout_s:
        return {"status": "deadlock_detected", "waited_s": elapsed_s}
    return {"status": "waiting", "waited_s": elapsed_s}

print(check_for_deadlock("dockscout", [], timeout_s=5, elapsed_s=2))
print(check_for_deadlock("dockscout", [], timeout_s=5, elapsed_s=6))
Output (real, executed) 
{'status': 'waiting', 'waited_s': 2}
{'status': 'deadlock_detected', 'waited_s': 6}
Detecting is not the same as resolving
check_for_deadlock only NAMES the problem once elapsed_s crosses timeout_s -- it does nothing to break the cycle on its own. Without Section 14's own fix, a detected deadlock just becomes a detected, still-unresolved deadlock.

14. Breaking a deadlock: a forced-first-move tie-breaker

The fix needs a rule BOTH agents already agree on before any deadlock happens, so neither one needs the other's permission to apply it -- an independent, pre-agreed tie-breaker, not a negotiation:

break_deadlock.py
def break_deadlock_if_needed(agent_name, inbox, timeout_s, elapsed_s, all_agent_names):
    status = check_for_deadlock(agent_name, inbox, timeout_s, elapsed_s)
    if status["status"] != "deadlock_detected":
        return status
    # Pre-agreed, independent rule: the alphabetically FIRST agent name
    # sends first. Neither agent needs to ask the other -- both can
    # compute this unilaterally from the same fixed roster.
    first_mover = sorted(all_agent_names)[0]
    if agent_name == first_mover:
        return {"status": "deadlock_broken", "action": f"{agent_name} sends the first proposal"}
    return {"status": "deadlock_detected_but_not_my_turn_to_break_it"}

print(break_deadlock_if_needed("dockscout", [], timeout_s=5, elapsed_s=6,
      all_agent_names=["dockscout", "yardscout"]))
print(break_deadlock_if_needed("yardscout", [], timeout_s=5, elapsed_s=6,
      all_agent_names=["dockscout", "yardscout"]))
Output (real, executed) 
{'status': 'deadlock_broken', 'action': 'dockscout sends the first proposal'}
{'status': 'deadlock_detected_but_not_my_turn_to_break_it'}
Why alphabetical, not "whoever notices the timeout first"
If BOTH agents independently decided "I noticed a timeout, so I'll break it," they might both send a proposal simultaneously -- a smaller, resolvable version of Section 8's own duplication, but still avoidable. A rule both agents can compute identically and in advance (sort the roster, lowest name goes first) guarantees exactly ONE agent acts, with no coordination message needed to agree on who.

15. Trajectory attribution across communicating agents

Chapter 9's which_agent_responsible (Section 14) answered "which agent's DISPATCH step failed." A peer-to-peer system needs the same question answered at the MESSAGE level: which agent's message was the one a receiver misinterpreted or mishandled.

which_agent_caused_miscommunication.py
def which_agent_caused_miscommunication(exchange):
    """
    exchange: list of (sender, msg_type, interpreted_ok) tuples across
    a WHOLE multi-turn peer exchange. Returns the SENDER of the first
    message a receiver failed to interpret correctly -- extends
    Chapter 9's which_agent_responsible from "which agent's dispatch
    step failed" to "which agent's MESSAGE was misread," since in a
    peer exchange the failure can originate in either direction, not
    just supervisor-to-worker.
    """
    for sender, msg_type, interpreted_ok in exchange:
        if not interpreted_ok:
            return sender
    return None

full_exchange = [
    ("dockscout", "claim", True),
    ("yardscout", "claim", False),   # Section 8's real duplicated-work claim
    ("dockscout", "reject", True),
]
print("which agent's message caused this exchange's failure:",
      which_agent_caused_miscommunication(full_exchange))
print("which agent caused failure in an all-clean exchange:",
      which_agent_caused_miscommunication([("dockscout", "claim", True), ("yardscout", "ack", True)]))
Output (real, executed) 
which agent's message caused this exchange's failure: yardscout
which agent caused failure in an all-clean exchange: None
Why message-level attribution is a genuinely different question than dispatch-level
In Chapter 9, "which agent" and "which TOOL call" were almost the same question, since a supervisor's own dispatch call and the worker's execution were tightly coupled. In a peer exchange, a message can be WELL-FORMED (Section 7 passes it) and still cause a bad outcome because it was sent at the wrong TIME, to the wrong ASSUMPTION about shared state (Section 8's duplicated claim), or with the wrong message TYPE (Section 6's "query" that was actually a "claim") -- three distinct ways a perfectly valid-looking message still causes a coordination failure.

This chapter's own continuation of llm-evaluation-for-everyone's boundary, restated per this course's standing positioning discipline: deep trajectory-evaluation methodology for multi-agent exchanges is that sibling course's own territory; this section deliberately reuses Chapter 9's own mechanism, extended one more level (message, not just dispatch), rather than re-deriving a new evaluation framework from scratch.

16. A fail-closed guardrail before a peer agent commits

Chapter 6's fix made human_approved default to False; Chapter 9 Section 15 applied that same default-deny discipline to a worker's own spend-commit step. The same discipline applies here, now gated on BOTH a message-level consensus AND a value threshold:

fail_closed_commit.py
def commit_shipment_assignment(shipment_id, agreed_by_both, human_approved=False):
    """Fail closed on TWO independent axes: no peer consensus at all
    blocks the commit outright, and a high-value shipment additionally
    requires explicit human approval even WITH peer consensus."""
    if not agreed_by_both:
        return {"committed": False, "reason": "no consensus between peers (fail closed)"}
    if shipment_id in ("S-900",) and not human_approved:   # high-value lane
        return {"committed": False, "reason": "high-value lane requires human approval; none given (default-deny)"}
    return {"committed": True}

print("high-value lane, peers agree, no human approval:", commit_shipment_assignment("S-900", True))
print("high-value lane, peers agree, WITH approval:", commit_shipment_assignment("S-900", True, human_approved=True))
print("ordinary lane, peers agree, no approval needed:", commit_shipment_assignment("S-104", True))
print("ordinary lane, peers DISAGREE -- blocked regardless of value:", commit_shipment_assignment("S-104", False))
Output (real, executed) 
high-value lane, peers agree, no human approval: {'committed': False, 'reason': 'high-value lane requires human approval; none given (default-deny)'}
high-value lane, peers agree, WITH approval: {'committed': True}
ordinary lane, peers agree, no approval needed: {'committed': True}

In a peer system, this checkpoint belongs INSIDE each agent's own commit step, not in some third mediating process -- there is no supervisor here to hold it centrally, which is exactly why "fail closed by default" matters even more than it did in Chapter 9's supervisor-mediated system.

17. Harrowgate Logistics Exchange, assembled end-to-end

All of Sections 3-16's pieces, combined into one run: message validation (Section 7), a coordinated claim-check (Section 9), deadlock detection and breaking (Sections 13-14), and attribution (Section 15):

harrowgate_assembled.py
def run_harrowgate_exchange(claim_attempts, deadlock_elapsed_s, timeout_s=5):
    shared = set()
    exchange = []
    for agent_name, shipment_id in claim_attempts:
        if shipment_id in shared:
            exchange.append((agent_name, "claim", False))   # Section 8's duplication, caught
            continue
        shared.add(shipment_id)
        exchange.append((agent_name, "claim", True))

    deadlock_status = break_deadlock_if_needed(
        "dockscout", [], timeout_s=timeout_s, elapsed_s=deadlock_elapsed_s,
        all_agent_names=["dockscout", "yardscout"])

    return {
        "exchange": exchange,
        "first_miscommunication": which_agent_caused_miscommunication(exchange),
        "deadlock_status": deadlock_status,
    }

demo = run_harrowgate_exchange(
    claim_attempts=[("dockscout", "S-104"), ("yardscout", "S-104"), ("yardscout", "S-205")],
    deadlock_elapsed_s=6,
)
print(demo)

A peer system built this way is honest about the outcome: it catches a duplicate claim the instant it happens, says EXACTLY which agent's message caused it, and has a pre-agreed way to break a deadlock without either agent needing the other's permission to do so -- the three capabilities this chapter's own brief named, combined in fewer than twenty lines because each piece was already built and tested separately above.

18. GenAI Builder Thought Process

Thought process: the natural first instinct when two agents need to "talk" is to assume a bigger, smarter model will simply coordinate sensibly on its own. This chapter's own real, unscripted Sections 5-6 results are the direct rebuttal: DockScout and YardScout, each individually reasoning well about ITS OWN half of the problem, still landed on the exact same shipment with no supervisor and no shared check to catch it -- not because either model reasoned badly, but because neither had the OTHER agent's decision visible when it made its own. The habit that actually works, demonstrated this chapter: validate a message's fields before trusting its shape, normalizing what's safely recoverable (whitespace) and failing closed on what isn't (a renamed field, Section 7); never let two agents commit to the same piece of work without a SHARED, locked check first (Section 9); treat deadlock as a structural property to guard with a timeout, not a hope that an LLM will spontaneously break its own stated policy (Section 12's honest non-reproduction, Section 13's deterministic construction); have a pre-agreed, independently computable tie-breaker ready BEFORE a deadlock happens, not a negotiation attempted during one (Section 14); and always be able to name which AGENT's MESSAGE caused a bad exchange, not just that the exchange went wrong (Section 15). A strong prompt for an AI pair-programmer building peer-to-peer coordination for a different domain: "I'm building two or more PEER agents (not a supervisor and workers) that must exchange multiple messages to reach an outcome. Build: (1) a minimal message dataclass with sender, recipient, type, and payload; (2) a thread-safe shared message bus with a per-recipient inbox that drains on read; (3) a parser that normalizes safely-recoverable malformation (whitespace in keys) but returns ok=False rather than guessing on an unrecoverable one (a renamed field); (4) a shared, LOCKED claim-check so two peers can never commit to the same unit of work without one of them seeing it's already taken; (5) a deadlock timeout keyed on elapsed waiting time, not step count; (6) a pre-agreed, independently computable tie-breaker (e.g., sort agent names, lowest goes first) that needs no negotiation to apply; (7) a which_agent_caused_miscommunication function that walks a (sender, type, interpreted_ok) exchange and returns the first sender whose message was misread. Use only the Python standard library and the plain openai client -- no LangGraph, CrewAI, or AutoGen, and no message-queue framework."

In the Real World
  • Section 8's genuine duplicated-work result is a real, common distributed-systems problem with a specific name: a "lost update" or "double-booking" race condition. Production systems solve it the same way Section 9 does conceptually -- a single, atomic check-and-claim against shared state -- whether that shared state is a Python set with a lock, a database row with a unique constraint, or a distributed lock service.
  • Section 12's honest non-reproduction of a live deadlock is itself a real finding worth internalizing: small local models do not reliably obey a behavioral constraint stated only in a system prompt. Production multi-agent systems that genuinely need a "never speak first" guarantee enforce it in CODE (gating whether the message-send function is even callable), not by asking the model nicely and hoping.
  • Section 14's pre-agreed tie-breaker is the same idea behind distributed systems' "leader election" by lowest node ID or highest term number -- a rule every participant can compute identically, with no negotiation round needed, is what actually breaks a tie reliably at scale.

Points to Remember

  • Peer-to-peer communication is architecturally different from dispatch (Section 1) -- no third agent routes every interaction; agents message each other directly, across multiple turns.
  • A message needs validation before it's trusted, not just a schema it was supposed to follow (Sections 6-7) -- a real, unscripted result this session showed a model emitting whitespace-padded keys and a mismatched message type on an otherwise-correct claim.
  • Duplicated work is a DIFFERENT failure shape than Chapter 9's redundant dispatch (Section 8) -- two independent peers, not one supervisor re-dispatching, both genuinely reasoning well and still colliding with no shared check.
  • The fix is one locked check-and-claim against shared state (Section 9) -- check and commit must happen inside the SAME lock, or the race recurs.
  • Voluntary resolution works until it doesn't (Sections 10-11) -- a real live self-resolution succeeded this session, but a 2-agent vote can always tie, so a deterministic tie-breaker is still required.
  • Deadlock is a structural property, not a one-off model quirk (Sections 12-13) -- this session's own live attempt to reproduce it did NOT succeed (both agents broke their own stated policy), disclosed honestly; a deterministic construction demonstrates the real structural risk instead.
  • A pre-agreed, independently computable tie-breaker breaks a deadlock with no negotiation needed (Section 14) -- sorting a fixed roster is enough; asking the deadlocked agents to agree on who goes first just adds a second deadlock.
  • Attribution extends to the MESSAGE level, not just the dispatch level (Section 15) -- a well-formed message can still cause a bad outcome by arriving at the wrong time or with the wrong assumption about shared state.
  • Fail-closed commit checkpoints matter MORE without a supervisor (Section 16) -- there is no central process to hold the guardrail; it must live inside each peer's own commit step.
  • No agent framework or message-queue product was used anywhere in this chapter -- every mechanism is plain Python (stdlib threading, dataclasses, collections.Counter) or the plain openai client against local Ollama.
