Chapter 10 Project — Solo → AI-Paired → Critique 25 min

Now Pair With an AI

You already built the project yourself on Ravenshollow Talent Agency's CastingScout and BookingScout. Now a fourth scenario, Pemberwick Salvage Co. (a fictional marine-salvage cooperative) and its two peer agents WreckScout and PartsScout, gets built a second way: by prompting an AI assistant for a peer coordination harness, and reviewing what it hands back with the same skepticism you'd bring to a coworker's pull request before trusting its claim-handling.

Step 1: Design it yourself, first

WreckScout and PartsScout must claim salvage sites from a shared registry by exchanging messages directly -- no supervisor adjudicates. Before reading further, sketch your own design: what should happen if two claim messages for the SAME site arrive within the same second (a genuine race, not a sequential duplicate)? What should happen if both agents are configured to wait for the other to propose a site split first? There's no grading here, just your own design to compare against Step 3.

Step 2: Ask an AI assistant to build the same thing

Thought process: the prompt needs to state explicitly that the check-for-existing-claim and the add-new-claim must happen inside ONE lock, not two separate locked steps -- otherwise a rushed AI answer tends to write a "safe-looking" claim function that locks each half separately, which still leaves the exact race window this chapter's own Section 8 found live wide open, just harder to spot on a quick read.

Write the prompt you'd give an AI assistant:

Paste your prompt into your assistant of choice, save its response separately, and compare it against the checklist below before looking at this chapter's own lesson pattern.
Show a strong version of this prompt 
Write Python stdlib-only peer-coordination code for two EQUAL agents, wreckscout and partsscout, who claim salvage sites from a shared registry with no supervisor adjudicating. I need: (1) a parse_message_safely(raw_args, required_fields) function that normalizes whitespace-padded keys but returns ok=False (never guesses) when a required field is missing or renamed; (2) a coordinated_claim(agent_name, site_id) function where the check-for-existing-claim and the add-new-claim happen inside ONE single lock -- not two separately-locked steps -- so two concurrent calls can never both succeed on the same site_id; (3) a run_harness(cases) function that walks a list of cases, each a list of (agent, site_id) claim attempts, routes each through coordinated_claim, and reports which agent's claim was rejected as a duplicate, if any. Use only the Python standard library -- no LangGraph, CrewAI, AutoGen, or message-queue framework.

Step 3: Review it against this checklist

What a rushed AI-generated coordination harness tends to get wrong
  • Two separately-locked steps instead of one atomic operation. Does the generated coordinated_claim acquire a lock, check, release it, then acquire AGAIN to write -- leaving a window between the two acquisitions where a second call can slip through -- or is the check-and-write genuinely one locked block, matching this chapter's own Section 9 pattern?
  • A message parser that guesses at unrecognized fields. Given a key like "site" when the schema expects "site_id", does the generated parser silently map one to the other, or does it correctly refuse and report the mismatch -- the distinction this chapter's own Section 7 insists on?
  • No handling for the deadlock case at all. Does the generated harness have ANY mechanism for a case where two agents are each waiting on the other, or does it only handle the duplicate-claim case and leave deadlock entirely unaddressed?

Now compare the AI's code against this chapter's own lesson pattern (Sections 7, 9, 13-14) and against solution.py in the project folder. Where do they differ? Does the AI's version genuinely close the race window with one atomic lock, or does it just add a check that LOOKS safe on a quick read?
