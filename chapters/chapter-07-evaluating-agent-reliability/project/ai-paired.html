Chapter 7 Project — Solo → AI-Paired → Critique 20 min

Now Pair With an AI

You already built TriageScout's trajectory_correctness() function yourself. Now try the reverse: describe the same task to an AI assistant without showing it your own solution, and review what it hands back with the same scrutiny you'd bring to a teammate's pull request before trusting the reliability numbers it would produce.

Step 1: Have the AI build it independently

Thought process: the prompt needs to make explicit that a deliberate, consecutive re-check of the SAME tool should NOT count as an order violation -- otherwise the AI has no reason to add duplicate-collapsing logic at all, and will likely implement a naive list-equality check that fails a legitimately cautious trace, which is exactly the edge case this exercise is designed to surface.

Write the prompt you'd give an AI assistant:

Paste your prompt into your assistant of choice, save its response separately, and compare it against the checklist below before looking at this project's own solution.py.
Show a strong version of this prompt 
Write a Python function trajectory_correctness(trace, expected) for an agent-eval harness. `trace` is a list of tool-name strings representing every tool an agent actually called, in order (it may include tool names NOT in `expected` -- distractor calls that should be ignored, not treated as violations). `expected` is a list of tool-name strings representing the correct ground-truth order. The function must: (1) filter trace down to only the names that also appear in expected; (2) collapse consecutive DUPLICATE tool names in that filtered list down to a single occurrence (a deliberate, cautious re-check of the same tool immediately after itself should NOT count as an extra or out-of-order step); (3) return True only if the resulting collapsed list is EXACTLY equal to expected, including order; False otherwise. Do not use any agent framework or external library -- Python standard library only.

Step 2: Review it against this checklist

What a rushed AI-generated trajectory check tends to get wrong
  • Skipping the consecutive-duplicate collapse entirely. A naive implementation often just filters and compares directly against `expected`, which fails a legitimate cautious-recheck trace (e.g. calling the same verification tool twice in a row on purpose) as if it were an error -- does the generated code actually collapse duplicates, or does it silently penalize careful behavior?
  • Collapsing ALL duplicates, not just consecutive ones. A subtly different bug: removing every duplicate occurrence of a tool name anywhere in the trace (not just consecutive ones) would incorrectly treat a trace like [A, B, A, C] as equivalent to [A, B, C], hiding a real, non-adjacent repeated-call problem that a stricter check should flag.
  • Crashing or returning the wrong type on an empty trace. What does the generated code return for trajectory_correctness([], expected) when `expected` is non-empty -- a clean False, or an exception?

Now compare the AI's code against solution.py in this same folder. Where do they differ? Is the AI's version genuinely equivalent, or does it handle one of the three watch-outs above differently -- and is that difference actually a bug, or a legitimate different design choice?
