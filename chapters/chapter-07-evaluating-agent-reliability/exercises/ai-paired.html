Chapter 7 — Solo → AI-Paired → Critique 20 min

Now Pair With an AI

You already worked the exercises yourself on Larkmoor Archive Service's RecordScout. Now a third scenario, Thornmere Public Transit (a fictional transit authority) and its route-planning agent TransitScout, gets built a second way: by prompting an AI assistant for an eval harness, and reviewing what it hands back with the same skepticism you'd bring to a coworker's pull request before trusting its reported reliability numbers.

Step 1: Design it yourself, first

TransitScout can check real-time delays, look up a rider's fare balance, recompute a route around a closure, and escalate a complex accessibility request to a human dispatcher. Before reading further, sketch your own task set: what would a ground-truth trajectory look like for "a rider reports a closed station," and what's the difference between that run reaching a working replacement route (task success) versus reaching it through the correct diagnostic order (trajectory correctness)? There's no grading here, just your own design to compare against Step 3.

Step 2: Ask an AI assistant to build the same thing

Thought process: the prompt needs to state explicitly that BOTH a forgiving task-success metric AND a strict trajectory-correctness metric must be computed, and that the harness must run each task more than once -- otherwise a rushed AI answer tends to produce one single-run "did it work" boolean and call that an evaluation, which is exactly the naive baseline this chapter's own Section 4 demonstrated as insufficient.

Write the prompt you'd give an AI assistant:

Paste your prompt into your assistant of choice, save its response separately, and compare it against the checklist below before looking at this chapter's own lesson pattern.
Show a strong version of this prompt 
Write a Python stdlib-only eval harness for an agent, TransitScout, that has tools check_delays(station), check_fare_balance(rider_id), recompute_route(origin, destination, closed_station), and escalate_to_dispatcher(reason). I need: (1) a list of at least 4 tasks, each with an explicit ground-truth "expected_trajectory" (an ordered list of tool names) AND a separate, more forgiving "success_field" describing what outcome actually counts as success regardless of order; (2) a trajectory_correctness(trace, expected) function that does exact-order comparison after collapsing consecutive duplicate tool calls; (3) a task_success(trace, task) function that is deliberately more forgiving than trajectory_correctness -- it should only check that the outcome-producing tool calls are present; (4) a harness that runs each task N times (use a seeded random.Random, not real randomness) and reports BOTH metrics' rates per task, not just one combined number; (5) a pass_at_k(successes, k) function using the standard unbiased estimator (1 - C(n-c,k)/C(n,k)) with Python's math.comb. Do not use numpy, pandas, or any agent framework -- standard library only. Do not conflate task success and trajectory correctness into a single score anywhere in the harness.

Step 3: Review it against this checklist

What a rushed AI-generated eval harness tends to get wrong
  • Collapsing task success and trajectory correctness into one score. A shallow reading of the prompt often produces a single "correct": True/False per run, silently picking whichever of the two definitions was easier to implement -- does the generated harness genuinely report BOTH rates, separately, per task, the way this chapter's own Section 10 output does?
  • Running each task only once. "N times" gets ignored or defaulted to 1 more often than expected, especially if the AI's example code happens to work correctly on its first (and only) simulated run -- check whether the harness actually loops N times with a fixed seed, not just once with the appearance of a loop.
  • A pass@k implementation that isn't actually the unbiased estimator. A naive "count how often at least one success appeared in a random sample of k" using actual repeated random sampling is a valid but noisy approximation; the exact combinatorial formula this chapter uses is deterministic and exact for the same n, c, and k every time. Does the AI's version give the same pass@k answer on repeated calls, or does it vary because it's resampling randomly instead of computing the formula?

Now compare the AI's code against this chapter's own lesson pattern (Sections 6-11) and against solution.py in the exercises folder. Where do they differ? Does the AI's version genuinely keep task success and trajectory correctness as two separate, disagreeing-on-purpose numbers, or does it quietly merge them into one score that would have missed this chapter's own $12M/$9.4M bug?
