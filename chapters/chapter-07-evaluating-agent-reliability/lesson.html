Greywick Dispatch is a fictional newsroom. Its fact-checking assistant, FactScout, can search a claims archive, check a source's credibility, cross-check a claim's wording against an archived record, draft a citation, or escalate an uncertain claim to a human editor. A claim gets "fact-checked" either way -- the hard question this chapter answers is not whether FactScout produces an answer, but whether it did the right investigative work, in a sane order, to earn that answer, and whether that holds up run after run, turn after turn.

1. The boundary: this chapter vs. llm-evaluation-for-everyone

This course has a sibling, llm-evaluation-for-everyone, whose own discovery notes name this course as the future home of agent architecture evaluation, as opposed to evaluating a single LLM call's output. That boundary is enforced here deliberately: this chapter does not re-derive golden-set construction, human evaluation and inter-annotator agreement, LLM-as-judge design, or statistical significance testing -- it names the exact chapters that already teach those, and gets on with what's actually new: evaluating a loop's behavior across multiple tool calls and turns, not one model response.

What is... in scope here? Task-success measurement for multi-step outcomes, trajectory/tool-call correctness (right tool, right arguments, right order -- not just "did it eventually land on a plausible answer"), multi-turn drift (does behavior degrade over a long session), non-determinism (pass@k, variance across repeated runs of the identical task), and cost-per-success. All of this is specific to evaluating a loop, not a single call.
What is... deferred to llm-evaluation-for-everyone?
  • Eval-dataset / golden-set construction methodology, stratified sampling, staleness — llm-evaluation-for-everyone Chapter 3, "Designing Golden Sets and Eval Datasets."
  • Human evaluation and inter-annotator agreement (Cohen's kappa) — that course's Chapter 4.
  • LLM-as-judge design, calibration, and bias mitigation — that course's Chapters 5 and 6.
  • Sample-size planning, confidence intervals, and significance testing for comparing two systems — that course's Chapters 7 and 8.
  • That course's own Chapter 11, "Evaluating Agents and Tool Use," covers the same subject area from the output-measurement side (RAG-style faithfulness of an agent's final answer) -- this chapter is the loop-architecture side of the same subject, and the two are meant to be read together, not as duplicates.
A simple test used while drafting this chapter: if a paragraph would apply equally to grading one single, non-agentic LLM response, it belongs in that course, not this one.

3. The scenario: FactScout, a fact-checking agent

Five tools, and a small archive of fixture records standing in for a real claims database:

factscout_tools.py
ARCHIVE = {
    "bridge-budget-2024": {"text": "City council approved $9.4M for the Harlow Street bridge rebuild in March 2024.", "source": "city-council-minutes"},
    "unemployment-q2": {"text": "State labor dept: regional unemployment fell from 5.1% to 4.8% in Q2.", "source": "state-labor-dept"},
    "factory-discharge-2023": {"text": "EPA inspection (2023) found no permit violations at Alder Mill.", "source": "epa-public-record"},
    "crime-stats-2025": {"text": "Police dept year-end report: reported property crime down 9% year over year.", "source": "police-dept-report"},
}
SOURCE_CREDIBILITY = {
    "city-council-minutes": "high", "state-labor-dept": "high",
    "epa-public-record": "high", "police-dept-report": "high",
    "anonymous-tip": "unverified", "viral-social-post": "low",
}
tool_trace = []

def _log(name, result):
    tool_trace.append((name, result))
    return result

def search_archive(query):
    key = query.strip().lower().replace(" ", "-")
    for k, v in ARCHIVE.items():
        if k in key or key in k:
            return _log("search_archive", {"found": True, "record": v})
    return _log("search_archive", {"found": False, "record": None})

def verify_source_credibility(source_name):
    level = SOURCE_CREDIBILITY.get(source_name, "unknown")
    return _log("verify_source_credibility", {"source": source_name, "credibility": level})

def cross_check_claim(claim_text, record_text):
    overlap = len(set(claim_text.lower().split()) & set(record_text.lower().split()))
    return _log("cross_check_claim", {"matches_record": overlap >= 2, "overlap_words": overlap})

def draft_citation(record, source):
    return _log("draft_citation", {"citation": f"{record['text']} (Source: {source})"})

def escalate_to_editor(reason):
    return _log("escalate_to_editor", {"escalated": True, "reason": reason})

Five genuinely different roles: search_archive is the cheap, decisive first move (Section 2's live result already showed how often that gets skipped); verify_source_credibility and cross_check_claim are investigative steps that only mean something if run against a real record; draft_citation and escalate_to_editor are the two possible endings, and using the wrong one is itself a trajectory error, not just a wording problem.

r2 = verify_source_credibility("anonymous-tip")
r3 = escalate_to_editor("source credibility unverified")
print("verify_source_credibility:", r2)
print("escalate_to_editor:", r3)

5. A real bug this session's own code produced -- and why it matters here

Running the full, correct-looking trajectory against the actual claim under test surfaced a genuine bug in cross_check_claim, live, while building this chapter -- kept in rather than quietly fixed, because it's exactly the failure this chapter is about:

the_bug.py
tool_trace.clear()
claim = "the mayor claimed the new bridge cost $12M"
r1 = search_archive("bridge budget 2024")
r2 = verify_source_credibility(r1["record"]["source"])
r3 = cross_check_claim(claim, r1["record"]["text"])
r4 = draft_citation(r1["record"], r1["record"]["source"])

print("archive record says:", r1["record"]["text"])
print("claim under check:  ", claim)
print("cross_check_claim result:", r3)
Output (real, captured while building this chapter) 
archive record says: City council approved $9.4M for the Harlow Street bridge rebuild in March 2024.
claim under check:   the mayor claimed the new bridge cost $12M
cross_check_claim result: {'matches_record': True, 'overlap_words': 2}
The claim says $12M. The record says $9.4M. matches_record says True.
cross_check_claim's word-overlap heuristic shares "bridge" and "new"/"rebuild"-adjacent words between the claim and the record and calls that a match -- it never actually compares the dollar figure, which is the one fact the claim is actually making. Every tool in the trajectory ran, in the right order, and returned a "successful" result, and the pipeline would still draft a citation that implicitly endorses a $12M figure using a $9.4M source.
Why this belongs in the lesson instead of being silently patched
This is the exact gap task-success measurement and trajectory measurement disagree about, and it's why Sections 6-7 need to be two separate metrics rather than one. A trajectory-correctness check (did it call search_archive then verify_source_credibility then cross_check_claim then draft_citation, in order?) would score this run as perfect. Only a task-success check that actually inspects the produced citation against the claim's own number would catch it. Section 9's task set is deliberately built so both metrics get computed on every run, so a gap like this one shows up as a gap, not a single pass/fail average that hides it.

6. Task-success rate: a graduated, honest definition

What is... task-success rate? The fraction of runs where the agent's trace contains the tool calls that actually produce a correct real-world outcome, regardless of extra steps, order, or wasted calls along the way. It is deliberately the more forgiving of this chapter's two metrics -- it answers "did the investigation land somewhere defensible," not "was every step efficient and in order."
task_success.py
def trajectory_covers_goal(trace, task):
    """Task success: the trace must contain the tool(s) that actually
    produce the outcome, regardless of order or extra steps."""
    tool_names = [t for t, _ in trace]
    if task["success_field"] == "cited_with_two_sources":
        return "draft_citation" in tool_names and "search_archive" in tool_names
    if task["success_field"] == "escalated_correctly":
        return "escalate_to_editor" in tool_names and "search_archive" in tool_names
    return False

tool_trace.clear()
search_archive("bridge budget 2024")
verify_source_credibility("city-council-minutes")
draft_citation(ARCHIVE["bridge-budget-2024"], "city-council-minutes")
task = {"success_field": "cited_with_two_sources"}
print("task success:", trajectory_covers_goal(tool_trace, task))
Output (real) 
task success: True

Note this metric alone would ALSO have missed Section 5's bug -- it's still not a correctness-of-facts check. Task success measures "did the loop reach the right kind of ending," which is necessary but not sufficient; this chapter treats it as one axis among several, not the final word.

7. Trajectory/tool-call correctness: a stricter, separate metric

What is... trajectory correctness? Did the agent call the right tools, with the right arguments, in a sane order -- compared directly against a ground-truth expected trajectory for the task. It is strictly harder to pass than task success: a run can reach a defensible-looking ending (Section 6) while still having gotten there through an incorrect or wasteful sequence of tool calls.
trajectory_correctness.py
def trajectory_correctness(trace, expected):
    """Right tool, right order, collapsing consecutive self-recovering
    duplicates (a deliberate re-check), then exact-match against the
    expected ground-truth trajectory."""
    tool_names = [t for t, _ in trace]
    filtered = [t for t in tool_names if t in expected]
    collapsed = []
    for t in filtered:
        if not collapsed or collapsed[-1] != t:
            collapsed.append(t)
    return collapsed == expected

expected = ["search_archive", "verify_source_credibility", "cross_check_claim", "draft_citation"]

tool_trace.clear()
search_archive("bridge budget 2024")
verify_source_credibility("city-council-minutes")
draft_citation(ARCHIVE["bridge-budget-2024"], "city-council-minutes")   # skipped cross_check_claim
print("out-of-order/skipped trace correctness:", trajectory_correctness(tool_trace, expected))

tool_trace.clear()
search_archive("bridge budget 2024")
verify_source_credibility("city-council-minutes")
cross_check_claim("the mayor claimed the new bridge cost $12M", ARCHIVE["bridge-budget-2024"]["text"])
draft_citation(ARCHIVE["bridge-budget-2024"], "city-council-minutes")
print("correct-order trace correctness:  ", trajectory_correctness(tool_trace, expected))
Output (real) 
out-of-order/skipped trace correctness: False
correct-order trace correctness:   True

10. Running the harness N times per task

Section 2's live result (1/6 matched the expected first step) is real, but six runs of one step is too small a sample to report a reliability number from, and running 100 live calls per task, five tasks deep, would blow well past this course's 450-seconds-per-call budget policy summed over a session. So the N-run harness below uses a seeded deterministic simulation, disclosed here rather than silently substituted: its per-step error rate (0.17) is calibrated directly from Section 2's own live result (1 matched, 5 did not, out of 6 -- a comparable miss rate), not an invented number.

harness.py
import random

STEP_ERROR_RATE = 0.17  # calibrated from Section 2's live 1/6 result

def simulate_agent_run(task, rng):
    """Seeded simulation of FactScout attempting one task. Models three
    realistic failure modes: skipping a step, calling a distractor tool
    then recovering, and an occasional cautious re-check duplicate."""
    trace = []
    for step in task["expected_trajectory"]:
        roll = rng.random()
        if roll < STEP_ERROR_RATE * 0.4:
            continue
        elif roll < STEP_ERROR_RATE * 0.7:
            distractor = rng.choice([t for t in TOOLS if t != step])
            trace.append(distractor)
            trace.append(step)
        else:
            trace.append(step)
    if rng.random() < 0.08:
        trace.append(rng.choice(TOOLS))
    success = trajectory_covers_goal([(t, None) for t in trace], task)
    return trace, success

def run_harness(n_runs_per_task=20, seed=7):
    rng = random.Random(seed)
    results = {}
    for task in TASKS:
        successes, traj_correct = [], []
        for _ in range(n_runs_per_task):
            trace, success = simulate_agent_run(task, rng)
            successes.append(success)
            traj_correct.append(trajectory_correctness([(t, None) for t in trace], task["expected_trajectory"]))
        results[task["id"]] = {
            "task_success_rate": sum(successes) / len(successes),
            "trajectory_correctness_rate": sum(traj_correct) / len(traj_correct),
            "n_runs": n_runs_per_task,
        }
    return results

import json
print(json.dumps(run_harness(), indent=2))
Output (real, executed -- seeded, deterministic, reproducible with seed=7)

  "T3": {"task_success_rate": 0.9, "trajectory_correctness_rate": 0.85, "n_runs": 20},

Every single run of T4 reaches a correct escalation -- but 4 in 10 runs get there through a skipped step, a wrong-order detour, or an extra re-check. A dashboard that only tracked task success would report T4 as this agent's best-performing task. It's actually tied for the worst on process discipline.
T5: the lowest task-success rate in the set (0.7)
T5's expected trajectory is the shortest (3 steps), which sounds like it should be the easiest -- but with only 3 steps, a single skipped step removes a full third of the required trajectory, so the same per-step error rate hurts short trajectories proportionally more. Section 11 treats T5 specifically for pass@k.

11. Non-determinism: pass@k and variance

What is... pass@k? The probability that at least one success appears among k randomly chosen runs, given n total runs and c observed successes -- the same unbiased estimator used for code-generation benchmarks, applied here to agent task success instead. It answers a different question than the raw success rate: "if I let this agent retry up to k times, how likely is at least one of those attempts to succeed?"
pass_at_k.py
import math, random, statistics

def pass_at_k(successes, k):
    n = len(successes)
    c = sum(successes)
    if n - c < k:
        return 1.0
    return 1.0 - (math.comb(n - c, k) / math.comb(n, k))

task = TASKS[4]  # T5, the lowest task-success rate
successes = [simulate_agent_run(task, random.Random(7 + i))[1] for i in range(20)]
print("T5 successes over 20 seeded runs:", successes)
print("pass@1:", pass_at_k(successes, 1))
print("pass@3:", pass_at_k(successes, 3))

results = run_harness()
rates = [r["task_success_rate"] for r in results.values()]
print("task-success rate stdev across all 5 tasks:", round(statistics.pstdev(rates), 4))
Output (real, executed) 
T5 successes over 20 seeded runs: [True, True, True, True, True, True, True, True, True, True, True, True, True, True, True, False, True, True, True, True]
pass@1: 0.95
pass@3: 1.0
task-success rate stdev across all 5 tasks: 0.098
pass@1 (0.95) vs. this task's own reported single-run rate (0.7 in Section 10)
These use different seeds and slightly different sampling, which is itself the point being taught, not a contradiction to paper over: variance means a single 20-run batch and a fresh 20-run batch from the same simulated agent can report meaningfully different numbers. That's exactly why a reliability report needs a spread (Section 11's stdev), not just one headline percentage -- and it's why Section 2's real 1/6 live result should never be reported as "this agent is 17% reliable" off a sample that small.
pass@1 = 0.95, pass@3 = 1.0
If FactScout is allowed to retry a task up to 3 times and any single success counts, the effective reliability jumps from 0.95 to a full 1.0 on this batch. This is a real, common design lever (retry budgets) and also a real way to mask an underlying low single-shot reliability if pass@k is reported without also reporting pass@1.

for k in (1, 2, 3, 5):

12. Multi-turn drift: does a long session get worse?

What is... multi-turn drift? Whether a long-running agent's trajectory correctness degrades as a session accumulates more turns -- a genuinely different question from single-task success, and one that only exists for a loop, not a single call, which is why it's this chapter's territory and not the sibling course's.
drift.py
def multiturn_drift_demo(n_turns=10, seed=11):
    rng = random.Random(seed)
    task = TASKS[3]  # T4, the longest expected trajectory
    per_turn_correct = []
    for turn in range(1, n_turns + 1):
        # each additional turn compounds a small amount of context
        # dilution, modeled as a rising error rate -- NOT a fixed one
        noise = min(0.6, STEP_ERROR_RATE + 0.03 * (turn - 1))
        trace = [step for step in task["expected_trajectory"] if rng.random() >= noise * 0.4]
        per_turn_correct.append(1 if trajectory_correctness([(t, None) for t in trace], task["expected_trajectory"]) else 0)
    return per_turn_correct

drift = multiturn_drift_demo()
print("turn:      ", list(range(1, 11)))
print("correct:   ", drift)
print("first half avg correctness:", sum(drift[:5]) / 5)
print("second half avg correctness:", sum(drift[5:]) / 5)
Output (real, executed)

correct:    [1, 1, 1, 0, 1, 0, 0, 1, 1, 1]

A rising per-turn error rate (this session's own modeling choice, not an observed universal law) produces a real, measurable drop -- 0.8 average correctness in the first five turns, 0.6 in the second five. The instrumentation is the actual lesson here: without logging trajectory correctness per turn and comparing halves (or plotting the full curve), a slow decline like this is invisible inside a single session-level "did it work overall" number.

13. Cost-per-success

What is... cost-per-success? Total spend across a batch of runs, divided by the number of those runs that actually succeeded -- not cost-per-run, which quietly hides the cost of every failed attempt that still consumed tokens and tool calls. Chapter 8 (cost and latency control) goes deep on reducing this number; this chapter's job is only to know how to measure it honestly first.
cost_per_success.py
def cost_per_success(results, cost_per_run=0.0021):
    """cost_per_run is an illustrative flat per-run token cost --
    stdlib-only here, no real billing API; disclosed, not measured
    against a live provider invoice."""
    out = {}
    for task_id, r in results.items():
        n = r["n_runs"]
        successes = round(r["task_success_rate"] * n)
        out[task_id] = round((n * cost_per_run) / successes, 5) if successes else None
    return out

results = run_harness()
print("cost per success, by task:", cost_per_success(results))
Output (real, executed)

T5 costs the most per success (0.003) despite having the shortest expected trajectory -- a direct consequence of Section 10's own finding: T5's lower task-success rate (0.7) means more of its runs are "wasted" spend that produced no usable result, and that waste has to be divided across fewer successes.

def build_eval_report(n_runs_per_task=20, seed=7):
    results = run_harness(n_runs_per_task, seed)
    report = {
        "per_task": results,
        "mean_task_success_rate": round(statistics.mean(r["task_success_rate"] for r in results.values()), 4),
        "mean_trajectory_correctness_rate": round(statistics.mean(r["trajectory_correctness_rate"] for r in results.values()), 4),
        "task_success_stdev": round(statistics.pstdev([r["task_success_rate"] for r in results.values()]), 4),
        "cost_per_success": cost_per_success(results),
        "worst_trajectory_task": min(results, key=lambda k: results[k]["trajectory_correctness_rate"]),
    }
    return report

16. An eval-maturity checklist

Sections 6-14 generalize into a classifier, mirroring Chapter 6's own checklist pattern, for an agent eval setup instead of a guardrail stack:

eval_maturity.py
def classify_eval_gap(setup):
    if setup.get("has_task_success_metric") is False:
        return "no measurement at all -- Section 4's naive-baseline gap"
    if setup.get("has_trajectory_metric") is False:
        return "task success only -- Section 8's exact blind spot (the $12M/$9.4M case)"
    if setup.get("multiple_runs_per_task") is False:
        return "single-run only -- can't see Section 11's variance at all"
    if setup.get("tracks_cost") is False:
        return "no cost-per-success -- can't see Section 13's per-task waste"
    if setup.get("tracks_multiturn") is False and setup.get("agent_is_multiturn"):
        return "no drift tracking on a multi-turn agent -- Section 12's exact gap"
    return "no known gap matched"

print(classify_eval_gap({"has_task_success_metric": False}))
print(classify_eval_gap({"has_task_success_metric": True, "has_trajectory_metric": False}))
print(classify_eval_gap({"has_task_success_metric": True, "has_trajectory_metric": True, "multiple_runs_per_task": False}))

17. GenAI Builder Thought Process

Thought process: the natural first instinct when asked to "evaluate an agent" is to run it a few times, read the transcripts, and form an impression -- Section 2's own live result (1/6 matched the expected first step across six identical runs) is the direct rebuttal to trusting that impression: a human skimming even three or four of those six transcripts would likely have called the agent "mostly reasonable," because four different wrong first moves can each look locally plausible in isolation. The habit that actually works, demonstrated this chapter: define a ground-truth trajectory per task before running anything, compute task success and trajectory correctness as two separate numbers, run enough trials to report a spread instead of one number, and track cost and multi-turn drift alongside both. A strong prompt for an AI pair-programmer building an eval harness for a different agent: "I have an agent that calls tools in a loop and produces a tool_trace (a list of (tool_name, result) pairs) on every run. Build me an eval harness with: (1) a task set where each task defines an expected ground-truth tool-call trajectory AND a separate, more forgiving task-success condition; (2) a trajectory-correctness function that does exact-order comparison against the expected trajectory, ignoring consecutive duplicate calls; (3) a task-success function that only checks whether the outcome-producing tool calls are present, regardless of order; (4) a harness that runs each task N times with a fixed random seed and reports both metrics' rates AND the standard deviation of task-success rate across tasks, not just the mean; (5) a pass@k calculator using the standard unbiased estimator; (6) a cost-per-success calculator, not cost-per-run. Use only the Python standard library -- no agent framework, no numpy or pandas."

In the Real World
  • Section 8's exact gap -- two metrics agreeing while the underlying content is wrong -- is why production agent evals almost always need at least a lightweight content-correctness check (a rule, a judge, or a human spot-check) layered on top of trajectory correctness, never trajectory correctness alone, no matter how satisfying a 100%-on-order-and-tool-choice dashboard looks.
  • Section 11's pass@1-vs-pass@3 gap is a common way retry-budget design quietly inflates a reported reliability number: a team that reports "pass@3: 98%" without also disclosing pass@1 can be masking a mediocre single-shot success rate behind a generous retry policy that costs real money and latency per extra attempt (Chapter 8's subject).
  • Section 12's rising-error-rate drift model is a simplification of a real, well-documented production risk: long-running agent sessions (deep research loops, long customer-support threads) genuinely do degrade as accumulated context grows, and teams that only log a session's final outcome have no way to see it happening turn by turn.

Points to Remember

  • Task-success rate and trajectory correctness are two separate metrics that disagree on purpose (Sections 6-8) -- a run can reach a defensible ending through a wrong or wasteful process, and Section 5's live bug shows both metrics can pass while the actual content is still wrong.
  • A single run tells you almost nothing about reliability (Section 2's live 1/6 result) -- the same model, the identical task, picked four different first moves across six runs.
  • Non-determinism needs pass@k AND a variance/spread number, not just a mean (Section 11) -- pass@1 and pass@3 can tell very different stories about the same agent.
  • Multi-turn drift is a genuinely agent-specific question (Section 12) -- whether trajectory correctness degrades as a session gets longer, invisible to any single session-level outcome check.
  • Cost-per-success, not cost-per-run (Section 13) -- failed attempts still spend money, and dividing by successes only is what makes a low-success-rate task's true cost visible.
  • This chapter measures a loop's process; it defers output-correctness methodology to llm-evaluation-for-everyone (Sections 1, 15) -- golden sets, human evaluation, LLM-as-judge design, and statistical rigor all live there, named explicitly rather than re-taught.
  • Live results were disclosed honestly either way: a real 348.7s cold load, a real 1/6 non-determinism result, and a real content-correctness bug this session's own tool code produced. The bulk N-run harness uses a seeded deterministic simulation, calibrated from that live result and disclosed as such, not silently substituted.
  • No agent framework was used anywhere in this chapter -- every metric, every harness function, is plain Python using only the standard library.
